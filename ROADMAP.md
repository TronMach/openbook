# OpenBook — Roadmap (.NET 10)

Source: `accounting-app-feature-list.pdf` (QuickBooks alternative feature checklist).
Feature counts from the PDF: **35 MVP**, **73 V1**, **~110 LATER**.

## Stack decisions

| Concern | Choice | Why |
|---|---|---|
| Runtime | .NET 10 (LTS) | Target from the PDF |
| UI | **Blazor Web App** (Interactive Server), run locally via Kestrel | One UI serves both the MVP "local web UI" and the V1 "self-hosted / Docker" mode. Avalonia would need a second UI later. |
| API | ASP.NET Core Minimal APIs | V1 requires "everything the UI can do" over REST; UI and API call the same application layer from day one |
| Data | EF Core 10 — SQLite (MVP), PostgreSQL (V1) | Keep provider-neutral from the start: no SQLite-only SQL, migrations per provider |
| Money | `decimal` everywhere + a `Money` value object | Exact math; ban `double`/`float` in Domain via an analyzer |
| PDFs | PDFsharp-MigraDoc 6.2.4 (MIT, pinned: 6.5+ is AGPL) | Invoices, statements, checks, reports |
| Spreadsheets | ClosedXML | XLSX export |
| Testing | xUnit + Verify (snapshot reports) + property tests (FsCheck/CsCheck) for ledger invariants | |

### Solution layout

```
src/
  OpenBook.Domain          // entities, Money, posting rules, invariants (no EF, no ASP.NET)
  OpenBook.Application     // use cases / commands / queries, validation
  OpenBook.Infrastructure  // EF Core, migrations (Sqlite + Postgres), file storage, SMTP, PDF
  OpenBook.Api             // Minimal API endpoints
  OpenBook.Web             // Blazor UI
tests/
  OpenBook.Domain.Tests
  OpenBook.Application.Tests
  OpenBook.Integration.Tests   // runs against SQLite and Postgres (Testcontainers)
```

### Design rules to lock in at the start (expensive to retrofit)

1. **Every business document posts through one ledger engine.** Invoices, bills, payments, deposits, inventory moves → `JournalEntry` with lines. The engine rejects anything that doesn't balance, and the DB enforces it too (check + trigger / deferred constraint).
2. **Accrual is stored, cash basis is derived** at report time from payment application data.
3. **Void, never delete posted data**, and write an append-only audit record for every change. The PDF lists these as V1 but they're pulled into M0 below; adding them after 50 screens exist means touching all 50.
4. **Closed periods are enforced in the engine**, not the UI.
5. **Provider-neutral persistence** so the Postgres switch in V1 is a config change plus a migration set, not a rewrite.

**Plugin design (decided 2026-10-29):** two kinds, both kept away from the books themselves.
- Add-ins that run inside OpenBook fill the slots that already exist: import formats (migration readers), reports (reading from the report ledger), payment providers (payment gateway: Square, PayPal), bank-feed providers (bank connection client: Plaid, GoCardless), and form or export layouts. Code running inside OpenBook can't be fenced off, so installing one is treated like installing software: admin only, listed with its version on a plugins page, each can be turned off, and a "start without plugins" switch for one that breaks startup. Add-ins read through the same services the pages use and change things only through the normal services.
- Connected apps run outside OpenBook and use the API and webhooks (online shops, CRMs, payroll totals), so everything they post follows the same rules, closed periods and approvals as a person, and the audit log names the app. New: scoped API keys (e.g. create invoices and read customers, nothing else), built together with L7's granular permissions.
- No plugin writes ledger lines directly or bypasses the posting engine, changes the schema or its protections (a plugin gets a small private store of its own, not new tables), sees secrets (passwords, bank details, tax IDs, keys), or adds arbitrary screens; version one offers a menu link to the app's own page instead, and plugin pages can come later if there's demand.

**Offline capture design (decided 2026-10-29):** the device never keeps its own copy of the books; it collects drafts that the server enters when the connection returns.
- Offline work is a draft, never a posting. On sync the server enters each draft through the same services as the online forms, so every ledger rule applies (posting engine, closed periods, stock checks, approvals, audit). Nothing is merged.
- A draft that can't be entered (date now in a closed period, item out of stock, customer deactivated) goes to a "needs attention" review list with the reason, like the bank feed review queue, instead of becoming a conflict.
- Each draft carries an ID made on the device; the server ignores a draft it has already entered, so retries never duplicate.
- Document numbers (invoices, checks) are given out by the server at sync; the device shows "Draft" until then.
- Offline only creates records, never edits or voids existing ones.
- Offline: expenses and receipt photos (through the existing receipt reader), time and timers, mileage, notes, new customers and vendors, estimates and invoice drafts. Online only: payments and applying credits, reconciliation, stock transfers, builds and adjustments, closing the books, editing or voiding, reports beyond a cached snapshot.
- Forms check drafts on the device with the same Domain rules (the Domain project has no database or web dependencies, so it can run in the browser), so most drafts sync cleanly.
- The device caches what forms need (customers, vendors, items, prices, accounts, projects) and a few balances labelled with when they were updated; never bank details or tax IDs.
- Sync is automatic when the connection returns, with a "3 waiting to send" badge, a send-now button and a status on each draft (sent, waiting, needs attention).
- Cache and drafts are encrypted on the device; each device has its own sign-in that can be revoked from Settings, which also clears what it holds next time it connects. The audit log records the device a draft came from.
- First version: time, mileage, expenses and receipt photos; invoice drafts after. Medium size. It matters mostly for the Server edition (L13's Desktop edition is local and never offline).

**Editing posted documents (design decided 2026-10-31; slices 1–6, invoices, bills, sales receipts, credit memos, vendor credits, and expenses, checks and deposits, built the same day):** bookkeepers expect to correct an invoice rather than void it and enter a new one under another number, and voiding isn't possible once anything is applied. A document is pointed at by its id from about fifteen places (payments, credits, write-offs, retainer applications, late fees, reminders, scheduled emails, payment links, billable expenses, time and mileage, sales order and estimate quantities, custom field values by line number, stock movements, attachments, notes), so the correction happens in place.
- **Reverse and repost (decided).** "Change invoice" keeps the invoice's id and number. In one save it voids the invoice's current journal entry (reversal dated the original date, as a void is), posts a new entry from the edited invoice on its date (possibly a new one), points the invoice at the new entry, reverses the old stock movements and plans the sale again (`PlanReversalAsync` + `PlanSaleAsync`, which see each other's unsaved movements), and recalculates tax. Posted entries stay immutable: the original, its reversal and the new entry are all on record, and reports read as if the invoice had always been right. Both dates must be open, or the closing password given, as for any posting.
- **Invoices only in the first slice (decided).** Bills followed (slice 2): the same mechanism, plus approvals run again (held again even if approved, the changer can't approve it), stock received again (refused once used), billable-marked lines kept on their line, and bills from a purchase order left out for now (their entry clears received-not-billed accruals the order supplies). Sales receipts followed (slice 3): the customer and deposit account can change too, but not the total or deposit account while the receipt is in a bank deposit. Credit memos followed (slice 4): what's applied and refunded stays, so the total can't go below it nor the date past the first application, and refund dates must be open when the lines change. Vendor credits followed (slice 5) with the credit memo rules. Expenses, checks and deposits followed (slice 6): the account stays; feed-backed transactions keep the bank's amount (matches follow the new entry, for sales receipts too); printed or positive-pay checks keep amount, payee and number; billable-marked splits stay in place; cash count over/shorts are left out. Transfers followed (slice 7: accounts, amount and date; feed-backed ones keep amount and accounts). Customer payments followed (slice 8): applications replaced and invoices settled again, later credit applications keep their dates, refunds stay covered, and deposited, feed-matched or online payments keep their money. Bill payments followed (slice 9): bills paid again among the vendor's, issued checks (printed, ACH, positive pay) keep amount, account and number, feed-matched ones keep amount and account. Bills from purchase orders followed (slice 10): planned again against the order's other bills, so received stock clears "Received Not Billed" again, the 3-way match runs again and the order closes or reopens. Every posted document with a page can now be corrected in place. Expenses and checks whose bank line is reconciled stay uncorrectable, as voids are.
- **Paid invoices can be changed (decided)** while the new total is at least what's settled (payments, early payment discounts, credits, write-offs and retainer applications; `AmountPaid`) and the customer stays the same. Cash basis allocates payments across the invoice's current lines, so a change to the income lines of an invoice paid in a closed period moves that period's cash-basis figures: it needs the closing password too.
- **Lines are renumbered in their new order and their custom field values move with them** (decided while building, instead of leaving gaps: nothing else is keyed by an invoice's line numbers, and other code expects them in order). Lines that came from somewhere stay locked in this slice: lines billed from a sales order or estimate (their quantities are recorded against the source's line numbers) and billable expense, time and mileage lines (voiding the invoice still releases them). Everything else can change: date, due date, number (if free), memo, terms, tax code, location, warehouse, tags, and the other lines.
- **History and audit:** a reason is required; one `Updated` audit record keeps the before and after snapshots (the snapshot already includes the lines), so webhooks get `invoice.updated`. The invoice page shows "Changed on … by …: reason" and a history listing each change with its entries. Links from ledger lines already lead to the invoice for all three entries.
- **Unchanged by design:** reminders and scheduled emails render the invoice as it is when they go; an open payment link for the old balance isn't reused (a new one is made for the new balance), and a payment through the old link is applied up to the balance with the rest as credit. Early payment discount dates move with a new invoice date. Standard role, like creating and voiding. API: `PUT /api/sales/invoices/{id}` (date, lines, reason, and optionally number, due date, memo, tax code, location, tags, warehouse and which old line each line continues).

**L7 Security (design decided 2026-10-31):** four slices, each committed on its own: two-factor sign-in, invitations, permissions per area, single sign-on. Sign-in stays local first (username and password hashed by `IPasswordHasher`, sessions in `UserSessions`, the cookie checked on every request); each slice adds to that path rather than replacing it, and `AccessRules.Required` stays the one place that decides access.
- **Two-factor sign-in (slice 1).** Authenticator apps (TOTP, RFC 6238: SHA-1, 6 digits, 30-second steps, one step either side accepted, a step never accepted twice). The secret (20 random bytes) is stored through `ISecretProtector` and left out of the data export and audit snapshots. Setting up on `/account/two-factor`: a QR code of the `otpauth://` URI plus the secret as text, confirmed by a first code; then 10 one-time recovery codes shown once and stored as SHA-256 hashes (a used code is marked, never reused; "make new codes" replaces them all). Sign-in becomes two steps: after the password, a short-lived (5 minutes) protected token in a separate cookie carries "password checked for user X, stamp Y" to `/login/two-factor`, which takes a code or a recovery code; wrong codes count toward the existing lockout. Turning 2FA off needs the password and a code. An admin can switch it off for someone who lost their phone (`UserService`, audited, sessions end), and `reset-password --clear-two-factor` does it from the command line. Requiring it: `Company`-level setting "Require two-factor sign-in for" nobody / admins / accountants and admins / everyone; someone who must have it and hasn't set it up signs in to a session that can only reach the setup page (and sign out) until they do. API keys aren't affected (they're separate secrets). Audit `Updated` on the user ("two-factor turned on/off", "recovery codes replaced"). QR codes drawn as SVG by QRCoder (MIT; decided), the TOTP math written in OpenBook and tested against the RFC vectors. "Remember this browser" for 30 days (decided): a protected cookie naming the user, their stamp and a `TwoFactorRemembered` row skips the code there; changing the password, ending sessions or turning 2FA off forgets every remembered browser (the row carries the stamp).
- **Invitations (slice 2).** `UserInvite` (audit `user_invite`): email, role (any, admin included; decided), optional name, who invited, expiry (default 7 days, 1–30), token `obi_…` shown in the link only (SHA-256 hash stored, excluded from the export), Pending → Accepted (user id) / Revoked / Expired. Admins invite from Settings → Users; the email goes through `EmailService.SendMessageAsync` when email is set up, and the link is always shown to copy. `/invite/{token}` (anonymous) lets the person choose a username (suggested from the email) and password, creating the user with the invite's role and signing them in; if 2FA is required for that role they set it up next. Users gain `Email` (optional, unique ignoring case; filled from the invite, editable by admins) for SSO matching later. Revoking or resending (new token, old one dead) from the list. Access can end on a date (decided): `User.AccessEndsOn` (set on the invite or the Users page, cleared by admins); from that date the user signs in like a wrong password and the hourly job makes them inactive (audited, actor "system").
- **Permissions per area (slice 3).** Every path already maps to a role; slice 3 also maps it to an area (sales, purchases, banking, inventory, projects and time, assets, nonprofit, sales channels, documents, books (accounts, journal, closing, company settings), reports), from one table beside `AccessRules.Rules`, reusing the API scope areas so both lists agree. Named permission sets (decided): `PermissionSet` rows (audit `permission_set`) each with a level per area, None / View / Standard / Accountant, assigned to a user in place of a built-in role. A user's level for a request = the set's level for the path's area; `AccessRules.Required(path, method)` still returns the role the request needs, and the middleware compares it with the user's level in that area (a missing area means none). Admin things (users, backups, export, webhooks, add-ins, system) stay admin only and no set can grant them. Changing a set ends its users' sessions (claims carry the set and its version). Menus hide areas at None; search, the dashboard and the home page leave out what the user can't view. API keys act with their user's permissions and scopes narrow them further.
- **Single sign-on (slice 4).** One OpenID Connect provider at a time (`Microsoft.AspNetCore.Authentication.OpenIdConnect`, Microsoft's, MIT): authority (with presets for Microsoft Entra ID and Google), client id, client secret through `ISecretProtector`, button label; admin page `/settings/sign-in`, audit `sign_in_settings`. The handler reads its options from the settings at sign-in time, so a save applies without a restart. A sign-in matches a user by the provider's subject (remembered on the user after the first match) or else by a verified email equal to `User.Email`; inactive users are refused like a wrong password; the session is an ordinary `UserSession` (device "… via Microsoft"). OpenBook's own 2FA is skipped for SSO sign-ins (the provider does it). Unknown people are refused unless they hold a pending invite for that email, which the sign-in accepts (decided). "SSO only" refuses password sign-in for everyone but admins, who keep password + 2FA as a way in when the provider is down (decided); `reset-password` still works from the command line.

**L7 Security (slices 1–4, 2026-11-01): complete.** Two-factor sign-in with authenticator apps (QR code setup, ten one-time recovery codes, "remember this browser" for 30 days, required per role by admins, turned off by an admin or `reset-password --clear-two-factor` for a lost phone). Invitations by email with a role and an optional end to the person's access (made inactive by the hourly job on that day); links last 1–30 days, can be sent again or withdrawn. Permission sets: a level (none, view, standard, accountant) per area of the books, given in place of a role; menus, home shortcuts and search follow them, API keys too, and admin things stay admin-only. Single sign-on through one OpenID Connect provider (Microsoft Entra ID, Google or any other): existing users matched by their linked account or verified email, waiting invitations accepted on first sign-in, nobody else let in; "single sign-on only" keeps passwords for admins. Not done (later added: invitations can give a permission set; buttons and links on pages follow the area they post to; the API's search is filtered by area like the page): single sign-on was checked up to the provider's sign-in page, not through a real provider account; SAML and more than one provider at a time.

**L13 Desktop and Server editions (design decided 2026-11-01):** one build, two ways to install it. Code calls this the *install* (`OpenBook:Install` = `Desktop` or `Server`, default `Server`), never "edition", which already means the industry editions of L11; pages say "OpenBook Desktop" / "OpenBook Server". The install only decides defaults, where files go and what pages offer; data and rules never depend on it, so a company file moves between the two.
- **Desktop (slice 1).** `Installation` (Web, a singleton read once at startup) gives the paths. Company file `Documents/OpenBook/openbook.db`, backups `Documents/OpenBook/Backups`, Data Protection keys and logs under the user's local app data (`%LOCALAPPDATA%\OpenBook`, `~/Library/Application Support/OpenBook`), keys stored unencrypted at rest like Docker's so they can go with the file to a server. Kestrel listens on `127.0.0.1` only, on a fixed port (falling back to a free one), whatever the configuration says; a `running.json` beside the keys records the address so a second start just opens the browser (one copy per user). At startup, when no backup schedule exists yet, one is saved switched on: daily at noon to the backups folder, keeping 14 (audited, actor "system"). Pages: the System page shows the company file, backups and log folders and version, not database, key or network settings; a "Quit OpenBook" button (admin) stops the server; pages whose point is to be reached from elsewhere (invitations, customer portal links, the capture app, Stripe's webhook address) say that people on other computers can't reach a desktop install and point to moving to Server. Nothing is hidden or refused.
- **Server (slice 1).** Docker image sets `OpenBook__Install=Server`. With PostgreSQL the backup page replaces download/restore/schedule (SQLite-only) with pg_dump / pg_restore guidance (the compose commands, with the database name from the connection string); export stays. With SQLite on a server, as today.
- **Moving to PostgreSQL (slice 2).** `move-to-postgres --from <company file> --to "Host=…"` (Web command like `encrypt-database`; `--source-keys` / `--target-keys` folders, both defaulting to this install's keys). Steps: copy the SQLite file with the online backup API to a temporary file and migrate the copy (the original is never touched; an encrypted file is opened with `OpenBook:EncryptionKey`); validate it like a restore (integrity, triggers, company, balanced, sealed); migrate the target and refuse unless it's empty (no company, no rows anywhere); copy every table of the EF relational model in foreign-key order (self-references parent first), reading each value through the SQLite type mapping and writing through the PostgreSQL one, inside one PostgreSQL transaction. Ledger protections stay on during the copy: journal entries go in unsealed, their lines after, then one `UPDATE … SET "IsSealed" = true` lets the seal trigger check every entry's balance again; audit records are inserted (the append-only triggers allow it). Identity sequences are moved past the copied ids. Secrets (`Protected*` columns) are unprotected with the source keys and protected with the target's. Checks before committing: row count per table, journal and audit counts, balance per account, every entry sealed and balanced, the ledger triggers present; then one `Restored` audit record on the company in the target saying where it came from. Any difference rolls everything back. Secrets are re-encrypted, never dropped (decided): if one can't be read with the source keys the command stops and changes nothing. Tests on PostgreSQL only (skipped without `OPENBOOK_TEST_POSTGRES`).
- **Packaging (slice 3).** Desktop opens in the browser (decided), not its own window, so downloads, PDFs and printing work as they do now. `src/OpenBook.Desktop`: a small launcher (no console window on Windows) that starts the self-contained server in the background with `--OpenBook:Install=Desktop`, waits for `/healthz`, opens the browser, and exits; if one is already running it only opens the browser. `tools/package-desktop.ps1` publishes both self-contained for `win-x64` and builds `OpenBook-Setup.exe` with Inno Setup (free; per-user install, no admin rights, Start menu shortcut, unsigned for now). Windows only for now (decided); macOS later. No auto-update. Server: `docs/admin/server.md` (compose, HTTPS behind Caddy or nginx with forwarded headers, Data Protection keys and what they protect, pg_dump schedules and restore, moving a desktop company in, upgrades), compose healthcheck for the app; the user guide's chapter 8 gets "Desktop or Server" and "Moving to a server".

**L13 Desktop and Server editions (slices 1–3, 2026-11-01): complete.** One build, two installs. OpenBook Desktop (Windows): a per-user installer (no administrator rights) with a Start menu entry; it runs in the background, opens in the browser, reachable from that computer only; the company file in Documents\OpenBook with daily backups beside it from the start; starting it again opens the browser; Quit in Settings → System; pages say where something needs other people to reach OpenBook (invitations, portal links, the capture app, Stripe's webhook). OpenBook Server: the Docker image and compose stack with an admin guide (HTTPS behind Caddy or nginx, Data Protection keys, pg_dump schedules and restores); with PostgreSQL the Backup page shows the pg_dump commands. Moving from Desktop to Server: `move-to-postgres` copies the company file into an empty PostgreSQL database with the ledger triggers on, re-encrypts stored secrets with the server's keys, compares row counts, balances and the audit log before committing, and records the move in the audit log; the desktop file is left unchanged. Not done: macOS packaging (decided: Windows first), code signing, automatic updates, a health check inside the compose file (the image has no curl; `/healthz` is there for outside probes).

**L14 Simple view (plan proposed 2026-11-01, not started).** A second way to see the same books, for a one-person business that mostly needs customers, items and inventory, estimates and invoices, and wants it to feel like QuickBooks Desktop (decided 2026-11-01). Nothing is removed and nothing is refused: simple view only changes what is shown first and how forms look, like editions (`Editions.cs`). Data, rules, posting and access never depend on it, every page still works by its address, and anyone can switch to the full view and back at any time. Code calls it the *view* (`ViewMode` = `Simple` / `Full`), never "edition" (L11) or "install" (L13); it combines with both (a simple-view professional services company still has time tracking in its menu).
- **Familiar, not copied (decided 2026-11-01).** We borrow the way QuickBooks Desktop is organized: a home page drawn as a workflow, centers for customers, vendors and items, a menu bar grouped by task, and plain task names for screens ("Create Invoices", "Receive Payments", "Enter Bills", "Pay Bills", "Write Checks", "Make Deposits"), which are ordinary descriptions. We don't copy Intuit's icons, artwork, screen images, colors, logos or wording beyond those generic labels, and we don't use the QuickBooks name except to say factually what we import from. Our drawings, icons and help text are our own, and no QuickBooks screenshots go into the repo.
- **The setting (slice 1).** `User.ViewMode` (null = the company's) and `Company.DefaultViewMode` (audited in the company snapshot; new companies are asked at `/setup`, with simple suggested for one person). A per-user preference, not audited, like the dashboard's panels. A "Switch to full view" / "Switch to simple view" link in the top bar posts to `/account/view` and returns to the same page. Not a permission: `AccessRules` and permission sets are unchanged, and links in simple view may lead to full-view pages.
- **Menu and home page (slice 1).** Simple view has a menu bar across the top with drop-down menus by task (Company, Customers, Vendors, Inventory, Banking, Reports) and a short shortcut column (Home, Customers, Vendors, Items, Banking, Reports), plus each edition's lead area (time for professional services, sales channels for e-commerce, gifts for nonprofits) and a "Full view" link. Every label goes through `L[…]`. The home page is a workflow diagram drawn as our own inline SVG: Customers (Estimates → Create Invoices → Receive Payments → Make Deposits, with Sales Receipts beside), Vendors (Purchase Orders → Receive Inventory → Enter Bills → Pay Bills), Banking (Write Checks, Register, Reconcile) and Company (Items, Chart of Accounts, Backup). Each box is a link that shows what's waiting: open estimates, overdue invoices, payments to deposit, bills due. Every box stays visible, even for features the company doesn't use yet (decided 2026-11-01), so people can find them. An unused one says in a line what it's for (for example "Order stock from vendors" on Purchase Orders) instead of showing a count. Works in light and dark themes and on a phone.
- **Centers (slice 2).** Customer Center, Vendor Center and Item Center: a searchable list with open balances on the left, and the chosen record on the right (details, open balance, notes, its transactions filtered by kind and date, a "New transaction" menu with the record filled in). Static pages keyed by `?id=` so they work without script and links can be shared, with the full-view record page one click away. Both views can use them; the simple menu links to them.
- **Simpler forms (slice 3).** On the everyday forms (invoice, estimate, sales receipt, receive payment, deposit, bill, pay bills, write checks/expense, item, customer, vendor), simple view puts accounting choices under "More options": per-line accounts, deposit and A/R accounts, entry basis, adjusting and reversing, segments. Defaults are used when the box stays closed: Undeposited Funds, the item's accounts, the vendor's category. A field whose value isn't the default always shows, so nothing is ever hidden from someone looking at a record. Items are created from a plain question ("Do you keep this in stock?", "What do you sell it for?", "What does it cost you?"), with the inventory accounts filled in for you. Error messages: every `DomainException` an everyday form can raise gets a message that says what happened and what to do next, without debits, credits or account types. These are improved for both views wherever the current wording allows it.
- **Getting started and the guide (slice 4).** Simple setup asks a few questions (what you sell, whether you keep stock, whether you charge sales tax) and picks the starter chart, so a new company skips the accounts step. A short Reports page lists Profit & Loss, Balance Sheet, A/R aging, sales by customer and by item, expenses by vendor, stock status, sales tax liability and the tax summary, with "All reports" below. A simpler dashboard (decided 2026-11-01) from the same `KpiService` snapshot: money in the bank, money owed to you (and how much is overdue), bills due, this month's and this year's sales and profit against last year, and the twelve-month chart. Current and quick ratios, DSO and gross margin are left for the full view. Panels can still be hidden per person. The user guide gets a "Simple view" chapter with the menu paths as simple view shows them.
- **Left in the full view:** journal entries, editing the chart of accounts, closing the books, budgets, segments, fixed assets and loans, projects (outside professional services), approvals, ACH, positive pay, sales channels (outside e-commerce), users and permission sets, add-ins and webhooks. Each is reached through "Full view", or Settings for the settings pages.

### How to read these numbers

In an agentic coding session, every tool call re-sends the conversation so far. Most tokens processed are therefore **cached input re-reads** (typically 85–95%), which are billed and rate-limited far more cheaply than fresh input or output. Figures below are:

- **Total**: all tokens processed (cache reads + fresh input + output)
- **Output**: tokens Claude writes (code, tests, explanations)

### Confidence and calibration

These are order-of-magnitude estimates (±50%). The biggest swing factors are how long sessions run before `/clear`, how much debugging a feature needs, and file sizes. **Calibrate after M0:** check what the foundation actually used, divide by the M0 estimate, and scale the rest of the table by that ratio.

### Keeping usage down

- One feature per session; `/clear` between features. Context size multiplies every call.
- Keep a short `CLAUDE.md` with the design rules above so they don't have to be rediscovered each session.
- Keep files small (one entity / one endpoint group / one component per file) so reads are cheap.
- Use a cheaper model (Sonnet / Haiku) for CRUD screens, CSV importers and report formatting; save Opus for the ledger engine, reconciliation, FIFO, sales tax and the Postgres migration.
- Let `dotnet test` with filtered output do the verification, not repeated file re-reads.

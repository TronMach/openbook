# Custom fields and merging

Developer notes moved out of `CLAUDE.md` (index there). Read this file before changing this area; keep it up to date in the same commit.

## Custom fields

- `CustomField` (Domain/CustomFields; audit `custom_field`, page `/settings/custom-fields/{id}`): a field for items, customers, vendors or documents (`CustomFieldTarget`), with a `CustomFieldType` (text, long text, whole number, decimal, money, date, yes/no, pick list, link, email, phone), help, required, default, length/range limits, order, `ShowInList`, `PrintOnForms`, item `Placement` (under the description or its own column) and `Documents` (`CustomFieldDocuments` flags: for a document field the documents that have it; for the others, those its value is copied onto; `CustomField.Reach` limits customers to sales documents and vendors to purchase ones). Switched off, never deleted; the type is locked once anything has a value. `Normalize` checks a value and returns its stored form (invariant numbers, yyyy-MM-dd, "Yes"/"No", the pick list's own spelling); `Display` formats it.
- Values: `CustomFieldValue` rows (field, entity type and id, `LineNumber` 0 for the record, n for a document line; unique per entity, field and line). `CustomFieldService.EntityTypes` lists the record types that take them (item, customer, vendor, invoice, estimate, sales_order, sales_receipt, credit_memo, purchase_order, bill). `SaveAsync` audits an `Updated` record on the owning record with the named values. Records show only active fields; documents also keep showing what they carry.
- `CustomFieldStamper.StampAsync` runs inside each document service's create (and estimate / sales order / PO edits, with `replaceLines`), before the document's save: the source document's values (invoice from a sales order or estimate, bill from a PO), then the customer's or vendor's fields marked for that document (into the document field of the same name when there is one, so "Sales rep" on a customer fills an invoice's "Sales rep"), then document field defaults; then each line's item fields. Later changes to items, customers or vendors never touch documents; a document's own values stay editable on its page.
- Ready-made fields: `CustomFieldPresets.All` (stable keys stored as `PresetKey`; one with an existing field's name counts as added). `AddPresetsAsync` adds them in one save.
- Showing them: `<CustomFieldPanel EntityType=… EntityId=… />` (posts to `/custom-fields`, `f:{fieldId}` per field) beside `<Notes>`; `<LineFields DocumentId LineNumber>` under line descriptions (per-request `LineFieldCache`; `SalesDocument` takes `DocumentId`); list columns via `ListColumnsAsync`. PDFs: `CustomFieldService.DecorateAsync` adds printed values as facts, `FormLine.Details` and `SalesForm.ExtraColumns`/`FormLine.Extra` (FormService and PurchaseOrderForms call it; `FormLine.LineNumber` ties lines back).
- Also: search matches values (customers, vendors, items, invoices, bills, receipts); customer/vendor/item CSV imports read a column named after a field (`CustomFieldImport`); the report builder takes `fields` (customer, vendor or document field columns) and `fieldId`/`fieldValue` (filter). Form posts in `Web/Endpoints/CustomFieldEndpoints.cs`; API `/api/settings/custom-fields` (accountant to change; `/presets`) and `/api/custom-fields/{entityType}/{id}` (PUT `{ "field id or name": value }`, `/lines`), scope area `data`.

## Merging duplicates (2026-11-03)

- Merges also carry a vendor's 1099 details to the kept one (different tax IDs are refused), move ACH bank details and per-item level prices, and refuse moving a project onto a customer that isn't one (`merge.has_project`).
- `MergeService` (Application/Lists): `MergeCustomersAsync`/`MergeVendorsAsync`/`MergeItemsAsync(mergeId, keepId)` in one `IUnitOfWork` transaction: `IRecordMerger.MoveReferencesAsync` (Infrastructure `EfRecordMerger`) updates, straight in the database, every Guid column of the EF model that's a foreign key to the record's table or named for it (`CustomerId`, `DonorId`, `FunderId`, `PartyId`, `TargetId`; `VendorId`, `PreferredVendorId`; for items anything ending `ItemId`), plus the `EntityId` of notes, attachments and custom field values; GUIDs never collide, so a column that can't hold that id updates nothing. Never touched: `JournalEntries`, `JournalLines`, `AuditRecords`, `SentEmails`, `IdempotentRequests`, segments; nor rows owned by the record (an item's quantity breaks) except their other references. Rows unique per owner and something else (custom field values, price rule targets, document item codes, bundle components) keep the kept record's and drop the duplicate's; any other unique clash is `merge.conflict` and nothing changes. The duplicate is deactivated and renamed "… (merged)" (`Rename`), with `Updated` audit records on both. Refused: sub-customers (`merge.has_children`), an inactive record to keep, tracked items or bundles (`merge.item_stock`), different item types. A new column that refers to a customer, vendor or item without a foreign key needs a name the merger knows. `MergeCard` on customer, vendor and item pages posts to `/merge/{customers|vendors|items}` (`MergeEndpoints`; accountant, area `data`); API `POST /api/merge/{kind}` with `MergeId`/`KeepId`. Tests: `MergeTests` (both providers).

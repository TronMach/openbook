# Ledger, chart of accounts and accountant tools

Developer notes moved out of `CLAUDE.md` (index there). Read this file before changing this area; keep it up to date in the same commit.

## Chart of accounts and reporting

- `AccountType` is QuickBooks' list (Bank, AccountsReceivable, …); `AccountClass` groups them for statements. Pick the narrowest type; M2–M4 key off Bank/CreditCard/AR/AP.
- Rules spanning accounts live in `ChartOfAccounts` (subaccount = parent's type, max 5 levels, unique sibling names and numbers, no cycles, class change blocked once posted). `AccountService` also refuses a type change to or from A/R or A/P once posted (`account.type_receivable`). Full names use `Parent:Child`. Accounts are deactivated, never deleted.
- CSV import (`ChartImportService`, parser in `Application/Import/Csv.cs`) matches headers loosely and is all-or-nothing. The starter chart at `Web/wwwroot/samples/chart-of-accounts.csv` is covered by a test.
- `ReportBasis` (Accrual/Cash) per report, default from company settings. `EntryBasis` on each entry (Both / AccrualOnly / CashOnly) decides inclusion. Cash basis for invoices and bills is payment-driven; see Reporting below.
- Dev preview: `.claude/launch.json` → `openbook-web` on port 5188, data in `src/OpenBook.Web/openbook.dev.db`.

## Ledger hardening (V1.1)

- Closing date and password live on `Company`. `PostingEngine` checks every staged entry and void against it (`EnsureOpen`): `period.closed` without a password, `period.password_required` / `period.wrong_password` with one. The password comes from the scoped `ClosedPeriodOverride` (API: `X-Closing-Password` header; interactive pages: `Operations.RunAsync(..., closingPassword)`; static forms: set it before calling the service). Each override writes an `AuditAction.ClosedPeriodOverride` record on the company. Show `ClosedPeriodPassword` on any interactive form that posts, once `ClosedPeriod.NeedsPassword(ex)`. A static form needs nothing of its own: a post sent back with the refusal in its query shows `ClosingPasswordBox` (MainLayout), `shortcuts.js` sends it with the next form, and `ClosingPasswordMiddleware` sets the override.
- `CloseBooksService`: moving the closing date earlier, clearing it, or changing/removing the password needs the current closing password; closing more doesn't. Year-end close only moves the closing date; nothing is posted.
- Journal-sourced entries (`JournalEntry.IsJournalSource`: manual, auto-reversal, recurring, opening balance) are voided from the journal page; anything else from its document.
- Schedules: a template's place in its schedule is `OccurrencesPosted + IndexOffset`, and any maximum counts `OccurrencesPosted` alone. Changing frequency, interval or first date with occurrences made rebases the schedule (`Recurrence.Rebase`: from the date that was next, or the new first date, which must be after the last one reached), so only the future changes; other edits leave it alone. `Reactivate(today)` passes over what was missed unless `SetActiveAsync(..., catchUp: true)` (API `?catchUp=true`; **Make active and catch up**).
- `ReverseOn` posts a mirror entry (`AutoReversalSource`, `SourceId` = original). `PostingEngine.VoidAsync` voids a standing mirror with the entry, in one save (`StandingAutoReversalAsync`; a mirror's void shares its source, so look at `Kind`). Recurring templates (`RecurringEntry`) compute each date from `StartDate` and the occurrence index, so month ends don't drift; `RecurringEntryService.PostDueAsync` saves each occurrence separately and stops a template at its first error. `RecurringPostingService` (Web) runs it hourly for auto-post templates as actor "system".
- `JournalEntryFilter` can filter by `Source`/`SourceId`; use it rather than scanning entries.
- `OpeningBalance.ClassId` (optional, API and services) puts an opening balance or a year-to-date figure on a class, so a nonprofit's program history comes in by class.
- Opening balances post against "Opening Balance Equity" (created on first use); A/R and A/P are excluded (enter open invoices/bills instead). `OpeningBalanceService.PostYearToDateAsync(through, amounts)` posts income and expense accounts' year so far (natural sign) against the same account, source `ledger.opening_balance`, memo "Year to date before OpenBook" (page section "Year to date so far", API `POST /api/opening-balances/year-to-date`).
- Starter charts are embedded CSVs in `Application/Accounts/Templates`, imported through `ChartImportService`; each has a top-level "Retained Earnings" equity account. Their last column is the tax line, every income and expense row filled in (`ChartTemplateTaxTests`); the corporation chart is written for Form 1120-S and `ApplyAsync` turns it to Form 1120 for a C corporation by line name (`TaxLines.Equivalent`).
- `AuditLogQuery` filters and pages in the database (`ILedgerStore.PageAuditAsync`; dates by the company's day, tested on each record's time without its snapshots; `AuditChoicesAsync` for the filter lists) and diffs top-level JSON fields (null = absent). `Links.ForAuditEntity` maps an entity type to its page; add new entity types there.
- `JournalLinesEditor` (Components/Journal) is the shared debit/credit grid; the parent owns the `JournalLineModel` list and checks it with `JournalLines`.

## Segments (L1)

- Domain in `Domain/Segments/Segment.cs`: one `Segment` entity for classes (per line), locations (per transaction; `Company.LocationLabel` renames them, e.g. "Department") and tags (per entry, flat). Classes and locations nest (full names "Parent:Child", max 5 levels, unique among siblings, rules in `SegmentRules`); deactivated, never deleted. `Company.TrackClasses` / `TrackLocations` only show or hide the form fields.
- Segments live beside the ledger, never in it: `LineSegments` (one row per journal line with a class or location) and `EntryTags`. Posted lines stay immutable and their triggers untouched, while segments can be reclassified. `JournalLineDraft.ClassId` and `PostJournalEntryCommand.LocationId` / `TagIds` are written by `PostingEngine.StageAsync` (validated: right kind, active); voids and auto-reversals copy them, so reports by segment net to zero.
- Documents record them too: `SalesLine.ClassId`, `BillLine.ClassId`, `BankSplit.ClassId`, and `LocationId` on invoices, receipts, credit memos, estimates, bills, vendor credits and bank transactions (set with `SetLocation`; every line of the entry carries it). Sales postings are one line per income account and class. Inventory cost lines take the class the item's lines share, else none. Cash basis (`ReportLedger`) allocates payments with `AllocateByClass` and the paid document's location, so cash-basis segments come from the documents.
- `SegmentService`: lists (tree order), tracking, `SetTagsAsync` (tags are editable after posting; the reversal follows; not on reversals) and `ReclassifyAsync` (class and/or location of posted lines; closed periods need the closing password; a document's location applies to its whole entry; documents follow: sales lines by income account and old class, bill lines by position). Each change is an `Updated` audit record on the journal entry.
- `JournalLineDraft.LocationId` is a line's own location (else the entry's). An early payment discount and a bad debt go in the invoice's classes (`Invoice.ByClass`, in proportion to its income) and location, on those lines only; `PostingEngine.Carry` lets them use segments deactivated since, and `SegmentsOfAsync` gives an entry's location only when every line has it.
- Reports: `SegmentFilter` (class and location include subsegments; `Guid.Empty` = "Not specified", query value `none`) via `ReportLedger.LinesAsync(basis, from, to, filter)`; `ReportInputs.Segments` (`classId/locationId/tagId`) on P&L, GL, sales by customer and expenses by vendor. `profit-and-loss-by-class` / `-by-location` give a column per segment plus "Not specified" and Total. Budgets can be for a class and/or location (budget vs. actual and prior-year seeding filter by it). Tag filters on cash basis use the payment's entry tags.
- Web: `SegmentOptions.LoadAsync` (interactive forms, through `Operations`), `ClassSelect` and `LocationField`; the line editors take `Classes` (null hides the column). `<EntryTags EntryId=…/>` on detail pages, `<SegmentFilterFields>` on report filters. Pages `/segments`, `/segments/{id}`, `/segments/reclassify` (accountant); form posts in `Web/Endpoints/SegmentEndpoints.cs`. API under `/api/segments` (tags at `/api/segments/tags/{entryId}`). Audit entity type `segment`.
- Recurring templates (journal, invoice, bill) store a class per line, a `LocationId` and tags (`Tags`: comma-separated ids as text, at most `Recurrence.MaxTags`; `TagIds` parses them), checked when saved (`PostingEngine.EnsureSegmentsAsync`) and passed to every entry or document they make. Forms use `LocationField` and `TagChecks` (`SegmentOptions.Tags`). Journal entry CSV imports take optional class (per line), location (per entry; lines must agree) and tags (`;`-separated) columns by full name. The migration importers carry classes too (`SourceLine.Class`: IIF `CLASS`, qbXML `ClassRef`, the helper's Journal report `Class` column, QBO `ClassRef`), created by full name on import with class tracking turned on; not locations or tags.

## Forecasting and accountant tools (L6, slice 4)

- `ForecastService.ForecastAsync(asOf, weeks ≤ 52, scenarioId)`: opening = Bank balances on `asOf`; open invoices (from the A/R aging) on due date + scenario collection delay, open bills on due date + payment delay, `LoanService.RemainingSchedule` payments, what open purchase orders still have to be billed for (with the bills, on `ExpectedDate` else the order date, plus the payment delay), pending channel payouts (with the collections), scenario items; anything on or before `asOf` falls in the first week. Weeks run `asOf+1 … asOf+7`. Catalog key `cash-forecast` (`asOf`, `weeks`, `scenarioId`; own page `/reports/cash-forecast` with scenario editing). `ForecastScenario` (audit `forecast_scenario`, owned `ForecastScenarioItems`: once/weekly/monthly, signed amount) posts nothing and can be deleted.
- `AdjustingEntry` (table `AdjustingEntries`, key = journal entry id): marks beside the ledger, only for journal-sourced entries other than auto-reversals; `AdjustingEntryService.SetAsync` audits an `Updated` record on the journal entry. Voided entries don't count. Worksheet (`trial-balance-worksheet`, accountant): adjustments = lines of marked posted entries in the fiscal year to date, unadjusted = balance − adjustments. `adjusting-entries` lists them. The journal form has an "Adjusting entry" box (`/journal/new?adjusting=true` ticks it); entry pages toggle it (`/journal/{id}/adjusting`).
- `AccountantPackageService.BuildAsync(from, to, basis?)`: ZIP of `Reports` (on the basis chosen, else the company's; `WhenUsed` reports (mileage log, sales tax, inventory valuation, channel sales and tax) only when they have a non-zero figure) (catalog keys run with `preset=Custom&from&to&asOf=to&year=to.Year&detail=true`) as xlsx, the 1099 filing CSV and a README; audited `Exported` on the company. `Filing1099CsvAsync(year, audit)`: vendors meeting the threshold (card payments excluded) with full TIN and TIN type, address, form/box (`FormAndBox`), amount, payer name/address; text fields CSV-quoted with formula prefixes neutralised. Page `/accountant` (accountant), downloads `/accountant/package`, `/accountant/1099`; API under `/api/accountant` (`/forecast`, `/scenarios`, `/adjusting-entries`, `/worksheet`, `/1099-filing`).
- Partners (`Domain/Accounts/Partner.cs`: `Partner` (name, `SharePercent`, equity `CapitalAccountId`, switched off) and `PartnerAllocation` (`Source = partners.allocation`); `PartnerService` behind `IPartnerStore`; audit `partner`, `partner_allocation`): `AllocateAsync(date)` posts the fiscal year's accrual net income (income and expense classes from `ReportLedger`) Dr "Retained Earnings" (`FinancialReports.RetainedEarningsAccount`) / Cr capital by `Shares.ByWeight` (reversed for a loss), dated the year end, one standing per year (`VoidAllocationAsync`); `CapitalAsync` is the roll-forward. Page `/accountant/partners` (posts there, `/{id}`, `/allocate`, `/allocations/{id}/void`); in the books check's other documents. No K-1 lines or special allocations.

## Books check and scale (2026-11-02)

- `BooksCheckService` (Application/Ledger/BooksCheck.cs; 17 checks, the last the audit chain (below), ties also for customer deposits, Received Not Billed (deliveries' `Value` less bills' `AccruedAmount`), pledges receivable, grants (`Receivable` less `Advance`, receivable and advance accounts together), accumulated depreciation and loans, each through `Compare` with the record's own sources) checks the books agree with themselves: entries balance and are sealed (`ILedgerStore.ListEntryHeadersAsync`, query filters ignored), documents and their entries agree (posted ↔ standing, voided ↔ voided, no standing entry for a document that doesn't use it), invoices' and bills' `AmountPaid` against their applications, A/R and A/P aging against their accounts and undeposited funds and stock value against theirs (`Compare`: lines from sources the subledger doesn't track explain a difference as a `Note`; anything left is a `Problem`), finished reconciliations' chain and cleared totals, stock below zero only where allowed. Reads only. A new document type that posts one entry goes in `Documents` or, with rows of a record that post their own, `OtherDocumentsAsync`; a new source posting to A/R or A/P in `ReceivableSources`/`PayableSources` (or to holding accounts in `UndepositedSources`). Page `/accountant/check` (accountant), daily step "Books check" in `RecurringPostingService`, the latest kept in memory (`BooksCheckStatus`) for the page and the home to-do list; `GET /api/accountant/check`, `openbook check` (exit 3 on problems). `BooksCheckTests` includes seeded random runs of everyday documents with the check after every ten steps.
- Pages that run often never load whole histories: open documents (`ListOpenInvoicesAsync`, `ListOpenBillsAsync`), counts (`CountDocumentsAsync`, `AnyBillsAsync`), undeposited documents (`ListUndepositedAsync`), bank totals (`IBankingStore.GetAccountTotalsAsync`). Lists of documents show the newest `RecentDocuments.PageSize` (100) with `<ShowMore>` (`?count=`), through the stores' `ListRecent…Async(skip, take)` (`RecentQuery.RecentAsync`: date then id in SQL, creation order in memory). API lists take optional `skip`/`take` (`ApiPaging`, at most 500, `X-Total-Count`); without them they return everything as before.
- Performance pass (2026-11-08, `artifacts/review/performance-2026-11-08.md`): `CustomerService.ListAsync` / `VendorService.ListAsync` run the A/R or A/P aging for balances, so pickers and name lookups use `ListRecordsAsync(includeInactive)` (customers: `CustomerEntry` with level and full name, tree order; vendors: `Vendor`s by name); only pages that show balances call `ListAsync`. A/P aging reads `IPurchasesStore.ListPayablesAsync(asOf)` (bills unpaid now or settled after the date, payments applied to them or to bills dated later, credits settling them or holding credit then, their refunds) through `PayablesService.Aging`, checked against every document in `BooksCheckTests`' random runs like A/R. Anything on the home page reads the ledger once, as totals where it can: `SalesTaxPaymentService.OwedAsync` uses `ReportLedger.TotalsAsync` (summed by the database on accrual) and `ReturnsDueAsync` reads each period end once; `GrantService.RemindersAsync` builds one context for all conditional grants, from the earliest start. Few accounts' balances: `ReportLedger.BalancesAsync` (`ILedgerStore.GetAccrualBalancesAsync`). Item 4 (2026-11-09): documents of a period come from `ISalesStore.List{Invoices,CreditMemos,Receipts,Estimates}DatedAsync` / `IPurchasesStore.ListPurchaseOrdersDatedAsync` (sales tax liability, sales by state, print), and cash-basis tax starts from `ListPostedPaymentsAsync` then `FindInvoicesAsync`; the nonprofit statements fold history with `LinesSinceAsync`, and `PurposesAsync` returns nothing without a donor-restricted account; close books uses `FirstEntryDateAsync`, reclassify `GetLinesByIdAsync`; approvals and ACH use `ListBillsAwaitingApprovalAsync`, `ListPaymentsForAchAsync`, `ListPaymentsInAchFilesAsync`. The item center reads `ItemDocumentRow`s (headings plus the item's lines, summed in memory since the amounts are converted columns) from `date` on (`CenterTransactions.Since`); `CenterTransactions`, the bank register and account registers draw `RecentDocuments.PageSize` rows with `<ShowMore>` (`?count=`). Items 5–6: records whose owned collections grow together (grants, loans, purchase orders) are loaded with `.AsSplitQuery()` in their stores (a busy order's lines × deliveries came back as one joined row each); everything else stays a single query on purpose (global splitting measured slower on invoice lists), and `MultipleCollectionIncludeWarning` is logged at Debug (`DependencyInjection.QueryWarnings`). A new entity with two owned collections that both grow loads with `AsSplitQuery()`. Gifts: `INonprofitStore.FindDonationsAsync(test)` (tracked, the database asked for matching rows only, tracked gifts tested as they stand), `MaxDonationNumberAsync` and `ListCampaignUsesAsync`; never load every donation per gift recorded (batches and imports were quadratic). Item 7: history the database can't add up (cash basis, or a segment filter) is folded once and kept in `ReportHistoryCache` (singleton) by basis, date and filter under `ILedgerStore.ChangeStampAsync` (company, newest audit record, count of the latest 10,000 ids; null inside a transaction or with unsaved changes, so previews that roll back never fill it); any saved change writes an audit record, so the next report works the history out again. `LinesSinceAsync` then reads only the period (cash lines of a range are the whole ledger's lines dated in it). So nothing that changes the books may skip its audit record, or reports could keep old history. Item 8: `PurchaseOrderService.ProgressAsync` reads the order's own bills (`ListBillsOfOrderAsync`), not every bill of the vendor; the dashboard's figures come from `ReportLedger.DailyTotalsAsync` (per account and day; summed by the database on accrual, `GetAccrualDailyTotalsAsync`); `ILedgerStore.GetEntriesAsync(ids)` and `InvoiceService.FindAsync(ids)` replace lookups one by one. Static files are already fingerprinted and precompressed (`@Assets[...]`, `MapStaticAssets`); pages are left uncompressed on purpose (BREACH), with proxy settings in `docs/admin/server.md`. A perf copy run from a build folder needs `--contentRoot` set to that folder, or its static files come back empty.
- Timings on the demo company (three years, 5,500 invoices; `make-demo`): home 0.66 → 0.14 s, all invoices 0.33 s / 2.4 MB → 0.05 s / 56 KB, dashboard 1.0 → 0.47 s, balance sheet 0.20 → 0.08 s, cash-basis balance sheet 0.92 → 0.49 s, A/R aging 0.67 → 0.07 s (on a past date 0.10 s), search 0.45 → 0.05 s, a statement 0.04 s. Still reading everything: cash-basis reports from the beginning (the balance sheet on cash basis derives every payment).

## Audit chain (2026-11-10)

- Tamper-evident audit trail: `AuditLink` rows (Domain/Auditing/AuditChain.cs, table `AuditChain`: `Position` key from 1, `AuditRecordId` unique with a restricting foreign key, `Hash`, `LinkedAt`), one per audit record, each `AuditChain.Hash(previous, position, record)`: SHA-256 hex of the UTF-8 of `openbook-audit-chain-v1`, the previous hash (`Genesis` = 64 zeros) and the record's fields, each as `{length}:{text}` or `-` for null, one per line, the time as UTC to the microsecond (`AuditChain.Time`, since Npgsql drops the ticks below it; a company moved to PostgreSQL checks the same, `PostgresMoveTests`). Never change the rule (a Domain test holds two hashes worked out apart from the code); a new rule would need a new version string and both kept.
- Links are added after the save, never in it (a lock on the chain's head in every PostgreSQL save would serialize them): `AuditChainService.ExtendAsync(late)` links records after the highest linked id in id order, stopping at a gap younger than `WebhookDispatcher.GapWait` (`Settled`, as webhooks do); with `late`, unlinked records behind it (a save longer than that) go on the end first, which reads every record, so `AuditChainLinkingService` (Web/Security, every 30 s, lease `audit-chain`, JobStatus "Audit chain") asks hourly. Links are a batch of 1,000 per save; a first run chains the whole history. The service logs the head (`Audit chain at position …: hash`) once a day, so log files hold fingerprints outside the database. Nothing else writes `AuditChain` rows; they're not audited themselves.
- Append-only like the audit log: `TR_AuditChain_NoUpdate` / `_NoDelete` (in `SqliteLedgerTriggers.Names` and `AddedBy`, migration `AuditChain`), PostgreSQL also `TR_AuditChain_NoTruncate` (function `ob_audit_chain_append_only`).
- Checking: `AuditChainVerifier` walks links in position order recomputing hashes; after a break it carries on from the stored hash (one changed record is one finding), names missing positions, records gone, and (not serious) a record linked after higher ids. `VerifyAsync()` (the company's, plus records unlinked after `WaitingAfter`, 15 minutes), static `VerifyAsync(source)` for any `IAuditChainSource`, `CompareAsync(backup)`: every backup link must be in the company's chain at its position with the same record and hash, which shows a rewrite that recomputed every hash after a change (or a restore from an older backup since). Backups are read by `IAuditChainFiles` (`SqliteAuditChainFiles`: read-only, the company file's key; `HasChain` false for files from before).
- Where it shows: the books check's 17th check `audit-trail` (Problem when broken; Note for late links; records waiting are said in the summary, not as a note, since tests and first starts have them), with position and fingerprint (`AuditChain.Fingerprint`, the first 16 characters); the accountant package's README (position and full hash); `verify-audit [--against <backup>] [--fingerprint <position>:<hash>]` (Web/Cli/VerifyAuditCommand.cs: reads only; exit 0 fine, 3 broken or different, 1 unreadable or not yet migrated, 2 a mistake in the command). On PostgreSQL there's no backup file to compare, so fingerprints noted from the log or the package are the outside copy.
- What it doesn't do: a record inserted with a new id and a believable time looks like any other; someone with the database and the log files and every backup could rewrite all of them. Tests: `AuditChainTests` (Integration, both providers; the backup comparison on SQLite) and Domain `AuditChainTests`.

# Sales channels and payouts

Developer notes moved out of `CLAUDE.md` (index there). Read this file before changing this area; keep it up to date in the same commit.

## Sales channels and payouts (L11 e-commerce, slice 1)

- `Domain/Channels`: `SalesChannel` (name unique ignoring case, `ChannelKind`, a deposit account (Bank or Other current asset) and an account per part of a payout; `ChannelService` turns `Guid.Empty` into the usual account, created on first use: Online Sales, Shipping Income, Refunds and Returns (income), Merchant and Marketplace Fees, Sales Tax Payable (other current liability), Marketplace Adjustments; deactivated, never deleted; audit `sales_channel`; optional `ClassId`/`LocationId` go on its payout, order and return entries through `SalesChannel.Classed` and the command's location, so P&L by class or location is profit by channel) and `ChannelPayout` (unique `ExternalId` per channel, so re-importing skips it; owned `ChannelPayoutLines` of `ChannelLineType` Sale/Shipping/Tax/MarketplaceTax/Refund/Fee/Adjustment with signed amounts, positive = money to you, optional reference and ship-to `Region`; `ReportedNet` when the report gives one; audit `channel_payout`). Pending → Posted (one entry, `Source = channels.payout`: Dr deposit for the net, each type's total to its account; Tax and MarketplaceTax share the tax account so marketplace-collected tax nets out) → void puts it back to Pending; Dismissed for duplicates. Posting is refused while the lines don't add up to `ReportedNet`. `SalesChannel.Rules` (owned `SalesChannelRules`, at most `MaxRules`; `ChannelService.SetRulesAsync`, audited on the channel; form `/sales/channels/{id}/rules` with `rtext:i/rtype:i/racct:i`, API `GET|PUT /api/channels/{id}/rules`): the first rule whose text is in a line's description or reference (and of its type, when set) gives its account at posting (`RuleAccountFor`); never tax or cleared lines, never A/R or A/P. Lines are never edited. Files with no payout ids get an id from their dates and total, so `AddAsync` also leaves out lines held already (same date, type, amount, reference; each held line answers for one incoming). Etsy tax rows emit Sale −x, Tax +x and MarketplaceTax −x, so sales are net and tax nets out. Shopify payout files are split by the order reports already held (`SplitCharges`, refunds too); PayPal reads Sales Tax and Shipping columns when the download has them.
- `ChannelReports.Read(kind, text)` (Application, no database): Amazon settlement flat file V2 (tab-separated, grouped by settlement id, totals row gives the deposit date and net), eBay transaction report (preamble skipped, grouped by Payout ID; order rows split into item subtotal, shipping, seller- and eBay-collected tax (the latter as Tax + MarketplaceTax), fee columns, and an adjustment for whatever's left of the net), Etsy monthly statement and PayPal activity download (one payout per file; deposits, withdrawals, transfers, memo and non-completed rows left out, with a warning), and a general reader for Shopify/Stripe payout exports and any CSV (date, type keywords, gross + fee or net, payout id groups). `CsvColumns.Find` returns the first matching column in the file, so call it once per preference when the order matters.
- Pages `/sales/channels`, `/sales/channels/{id}` (import a report: multipart, `IFormFile` binds the antiforgery check; settings), `/sales/channels/payouts/{id}` (parts by account, post, void, dismiss/restore, transactions); form posts in `Web/Endpoints/ChannelEndpoints.cs`. API `/api/channels` (import takes the raw file, `?dryRun=true`); scope area `channels`. Report `channel-sales` (posted payouts by channel).
- Live connections (slice 2): Stripe and Shopify channels (`SalesChannel.CanConnect`) store a key or Admin API token protected by `ISecretProtector` (`ProtectedCredential`: excluded from the data export, audit snapshots and `ChannelResponse`; `ShopDomain` normalized to `*.myshopify.com` by `ChannelSyncService.ShopDomain`). `IChannelClient` → `Infrastructure/Channels/ChannelClient` (Stripe: `/v1/payouts?status=paid`, then `/v1/balance_transactions?payout=…&expand[]=data.source`, cents, `starting_after` paging; Shopify Payments: `/admin/api/2025-01/shopify_payments/payouts.json` and `balance/transactions.json`, decimal strings, `Link` rel="next" paging to the same host only; payout rows skipped, charges split into sale + fee). `ChannelSyncService.SyncAsync` fetches from `SyncedThrough` − 7 days (first time 60 days back) and saves new payouts through `ChannelService.AddAsync`; failures are kept on the channel (`LastSyncFailed`, `LastError`). Stripe charges whose PaymentIntent is a recorded customer payment's reference become `ChannelLineType.Cleared`, at sync and again when the payout posts, so a payment recorded in between counts; posted to `ClearingAccountId` (default: the online payments deposit account), so invoices paid online aren't counted as sales twice. Posting sets `CustomerPayment.PayoutId` on those payments, which leave the deposit list and can't be voided until the payout is (void clears it). Shopify charges are gross (tax and shipping inside sales) until order details come in slice 3. `ChannelSyncHostedService` syncs every 6 hours as "system". Connect/disconnect/sync post to `/sales/channels/connections/{id}` (accountant); API `/api/channels/connections/{id}` (accountant). Tests use `FakeChannelApis` behind the real client.
- Orders (slice 3): `ChannelOrderBatch` (one per import or sync and date; owned `ChannelOrderLines`: order id, SKU, title, quantity, sales (after discounts, without shipping and tax), shipping, tax, ship-to `Region`; Pending/Posted/Dismissed; audit `channel_orders`). Orders already seen (by order id, any batch of the channel) are skipped. `ChannelOrderLine.MappingKey` is the SKU, or the title for a line with none, so those can be mapped too. `ChannelOrderReports.Read` reads Amazon All Orders (item-price is the line total), eBay, Etsy (order shipping and tax repeated per row count once), Shopify exports (blank order fields after the first row) and generic CSVs; cancelled orders are left out. `ChannelSku` maps a channel's SKU to an item, or to none ("not stocked"); unmapped SKUs fall back to an item whose barcode or name is the SKU. `MapSkusAsync` saves the page's one form (`sku:{i}`/`item:{i}` to `/sales/channels/{id}/skus/all`, only changes audited); `SkusCsvAsync`/`ImportSkusCsvAsync` (SKU and Item columns, item by name or barcode or "Not stocked", all or nothing) at `skus.csv` and `skus/import`. `POST /sales/channels/{id}/orders/post-waiting` posts every waiting batch, oldest first, each in its own scope (a refusal stays waiting with its reason); the to-do list counts waiting batches and payouts and Close the books warns about them. `ChannelOrderService.PostAsync` refuses while a SKU is unmapped, then plans a sale through `InventoryService.PlanSaleAsync` (the channel's `SalesChannel.WarehouseId`, stored form, null = default; returns go back there too; per-order fulfilment by the marketplace isn't split yet) and posts only stock and cost (`Source = channels.orders`, movements `InventorySources.ChannelOrders`; no entry when nothing is stocked); revenue stays with the payouts. Void reverses like an invoice void, and is refused while returns stand. Returns (`ChannelReturn`, `Source = channels.return`, audit `channel_return`, movements `InventorySources.ChannelReturn`): per order line of a posted batch, up to what was sold less what's back, stocked SKUs only and no lot/serial items; `ChannelOrderService.ReturnAsync` (lines in `notRestocked` count as returned but move no stock; form `nostock:{line}`, API `NotRestocked`) restocks through `InventoryService.PlanReturnAsync` (latest sale cost, default warehouse), `VoidReturnAsync` like a credit memo void. Batch page form posts `qty:{orderLine}` to `/sales/channels/orders/{id}/returns`; page `/sales/channels/returns/{id}`. Returns reports: `ChannelOrderReports.ReadReturns` (order id, quantity, return date; SKU, reason, condition: damaged/defective/unsellable/disposed = not restocked) and `ChannelOrderService.ImportReturnsAsync(channel, bytes, dryRun)` (rows matched to the posted batch holding the order, by SKU, up to what's left; memo "Returns report: order {id}, {sku}." marks a row recorded, so repeats are skipped; any problem row and nothing is recorded, else one `IUnitOfWork` transaction; unstocked SKUs come back off the shelf); form `POST /sales/channels/{id}/returns/import`, API `POST /api/channels/{id}/returns/import?dryRun=`. Search finds orders by id (`SearchKind.ChannelOrder`, `IChannelOrderStore.SearchOrdersAsync`, area channels). `SalesChannel.MarketplaceCollectsTax` (default on for Amazon, eBay, Etsy) splits the `channel-sales-tax` report (by ship-to state, "Taxes" group). Shopify syncs also fetch orders (`IChannelClient.FetchOrdersAsync`, needs the `read_orders` scope; failure keeps the payouts and records a note) and `ChannelSyncService.SplitCharges` splits each charge ("order {id}") into sales, shipping and tax in the order's proportions with its state. Pages `/sales/channels/orders/{id}`, `/sales/channels/{id}/skus`; form posts in `ChannelEndpoints`; API `/api/channels/{id}/orders`, `/{id}/skus`, `/orders/{id}/post|void`. The API takes `ChannelRequest` (nullable account ids): OpenAPI can't describe a record whose struct parameters default to `Guid.Empty`.
- Fuzzing (2026-11-12): `ChannelOrderReports` amounts beyond `Money.MaxAmount` are unreadable (a price of 79 octillion × 2 overflowed); payout reports go through `StatementValues`, which stops there too.

# Sign-in and security

Developer notes moved out of `CLAUDE.md` (index there). Read this file before changing this area; keep it up to date in the same commit.

## Sign-in (from the company section)

- Wrong passwords (2026-11-05): `SignInThrottle` (singleton, in memory) shuts one address out of one account after `User.MaxFailedLogins`, right password included, so nobody can keep someone locked out by knowing their username (each pause is audited `Updated` on the user with the address, actor "system"; `AuthService.StartSessionAsync` audits a sign-in from a device none of the user's earlier sessions had, not their first; `Login`/`LoginTwoFactor` log refusals at Warning with `SignInLog.Name`, never the password); the user's own count (`MaxFailedLoginsEverywhere`, 100, audited when reached) is for guessing from many addresses; two-factor codes still lock at 5. The login page answers the same either way, so it doesn't say which usernames exist.
- Cookie auth (`Web/Security/WebSecurity.cs`). The cookie carries the user's `SecurityStamp` and its `UserSession` id (`AuthService.SessionClaim`), both checked on every request (cookies without a session claim are refused, so people sign in again). Changing a password, "Sign out all other sessions" (`POST /account/sessions/end-others`) or restoring a backup ends other sessions; the first two re-issue the current browser's cookie, which keeps its session (`RenewSessionAsync`). A session counts while not ended, on the current stamp and used within `UserSession.IdleLimit` (8 h, also the cookie's sliding expiry); last use is written at most every 5 minutes. `/account/password` lists them (device from `UserAgents.Describe`, address, times) and signs one out (`POST /account/sessions/{id}/end`); signing out ends this browser's session. `UserSessions.SecurityStamp` is left out of the data export. Pages require auth via `Components/Pages/_Imports.razor`; mark public pages `[AllowAnonymous]`. The `/api` group requires auth and returns 401 instead of redirecting.

## Security (L7)

- Two-factor sign-in (slice 1): `Totp` (Domain/Companies/TwoFactor.cs; RFC 6238 SHA-1, 6 digits, 30 s, one step either side, tested against the RFC vectors; CA5350 suppressed there only), `Base32`, `TwoFactor` (recovery codes `xxxxx-xxxxx`, stored as SHA-256 of the code without dashes, lower case). `User` holds `ProtectedTwoFactorSecret` (base32 through `ISecretProtector`), `TwoFactorEnabledAt`, `LastTwoFactorStep` (a step is never accepted twice; the setup code's step counts as used) and `RecoveryCodeHashes` (comma-separated, crossed off when used); the secret and hashes are left out of the data export and audit snapshots. `TwoFactorService`: `NewSetupAsync` (nothing saved; the page carries the secret in the form, protected for 15 minutes by `TwoFactorCookies.ProtectSetup`), `EnableAsync` (a code confirms; returns the recovery codes once), `DisableAsync` / `NewRecoveryCodesAsync` (password and a code), `SignInAsync` (the second step; wrong codes call `RecordFailedLogin`, and `AuthService.SignInAsync` doesn't reset the count when it answers `TwoFactorRequired`, so codes can't be guessed between passwords), `SignInRememberedAsync`, `SettingsAsync`/`RequireAsync`. Audit `Updated` on the user ("two-factor sign-in turned on/off", "recovery codes replaced", "signed in with a recovery code"); `UserService.ResetTwoFactorAsync` (admins, not yourself; ends sessions) and `AuthService.ResetPasswordAsync(..., clearTwoFactor)` (the CLI flag).
- `SignInSettings` (one row, audit `sign_in_settings`; single sign-on fields below): `TwoFactorRequiredFrom` (null = nobody, else that role and above; `TwoFactor.Required`). A required user without two-factor gets `SignInResult.MustSetUpTwoFactor`; `WebSecurity.SignInAsync(..., mustSetUpTwoFactor)` puts `TwoFactorSetupClaim` on the cookie, and `AccessMiddleware` then allows only `AccessRules.AllowedBeforeTwoFactorSetup` (the setup page, `/logout`, static files) and answers others with a redirect to `/account/two-factor?required=true` (API: 403 `auth.two_factor_setup`). Turning the requirement on doesn't touch open sessions; they're asked at their next sign-in. API keys never need a code.
- Web: `TwoFactorCookies` (Data Protection, time-limited): `OpenBook.TwoFactor` carries the password step (user, stamp, return URL) to `/login/two-factor` for 5 minutes; `OpenBook.Remember` remembers a browser for 30 days by user, security stamp and `TwoFactorEnabledAt`, so a password change, "sign out all other sessions" or turning two-factor off and on forgets it. `WebSecurity.CompleteSignInAsync` ends the pending cookie, issues the session cookie and says where to go. QR codes are inline SVG from QRCoder 1.6.0 (MIT; `QrCodes.Svg`, white box in both themes). Pages `/login/two-factor` (anonymous), `/account/two-factor` (setup, recovery codes, turn off), `/settings/sign-in` (admin: who must use it, who hasn't set it up); the Users page has a Two-factor column with "Turn off". API: `UserResponse.TwoFactor`, `DELETE /api/users/{id}/two-factor`, `GET|PUT /api/settings/sign-in` (admin). Tests: `TwoFactorTests` (services), `TwoFactorWebTests` (the real pages, posting static forms with `_handler` and the antiforgery token).
- Invitations (slice 2): `UserInvite` (Domain/Companies/UserInvite.cs; audit `user_invite`, linked to `/settings/users#invites`): lower-case email, optional name, role (any), optional `AccessEndsOn`, token `obi_…` only in the link (SHA-256 `TokenHash`, excluded from the export), `ExpiresAt` (1–30 days, default 7), Pending → Accepted (`UserId`) / Revoked; expired = pending past `ExpiresAt`. `InviteService`: `InviteAsync(command, linkBase)` (refuses an email a user has or an open invitation for it; emails through `EmailService.SendMessageAsync` when email is set up, else says why; the `SentInvite.Link` is returned once either way, so pages show it in the response rather than redirecting), `ResendAsync` (new token and expiry), `RevokeAsync`, `OpenAsync(token)` (with a suggested username from the email), `AcceptAsync(token, username, password)` (creates the user with the role, email and access end; the caller signs them in through `WebSecurity.CompleteSignInAsync`, which sends them to two-factor setup when required). `User.Email` (optional, unique, lower-case) and `User.AccessEndsOn`: from that day sign-in, session checks, API keys and both two-factor sign-ins refuse them (`User.AccessEnded(today)`), and the hourly job's "Access end dates" step (`UserService.EndExpiredAccessAsync`) makes them inactive. `UserService.SetDetailsAsync` (email, access end; not your own access; an admin's access can only end while another active admin's doesn't). Pages `/invite/{token}` (anonymous; `AccessRules` lets any role post there), `/settings/users/{id}` (email, access end); the Users page has the invite card and the invitations list. API `PUT /api/users/{id}/details`, `/api/users/invites` (GET, POST returning the link, `/{id}/resend`, DELETE). Tests: `InviteTests`.
- Records and areas: `RecordAreas.Of(entityType)` gives a record type's area. A file is read with its record (`GET /attachments/{id}` is let through `Allows` for that and checked in the endpoint; `GET /api/attachments` lists by the same rule); adding and removing stay in `data`. `/print` and `/api/print` are in `sales` (purchase orders also need `purchases`); centers leave out rows of other areas. Capture crosses areas behind one path, so `AuthClaims.MayWrite` and `CaptureService.AreaOf(kind)` decide per draft and limited keys need that area's scope too; a refused draft waits for attention. `AccessRules.LocalPath` is the one test of a local return address (no backslash or control character); use it for any `back`/`returnUrl`.
- Linking single sign-on: `POST /account/sso/link` asks for the password (and code when on) through `TwoFactorService.CheckIdentityAsync`, and the request travels in the ticket's properties (`LinkItem`), not the address; a link is never replaced (`sso.already_linked`). A saved report on a schedule can only be changed or deleted by whoever saved it (`report.scheduled`). The last admin isn't made inactive by an end date; `EnsureAnotherAdminAsync` counts only admins with no end date.
- Permission sets (slice 3): `PermissionSet` (Domain/Companies/PermissionSet.cs; audit `permission_set`, page `/settings/permission-sets/{id}`): name (unique ignoring case), description, `Levels` text "area:Role,…" (areas = `ApiScopes.Areas` keys; levels ViewOnly/Standard/Accountant, never Admin; areas left out = none; `LevelMap`, `Highest`), switched off (only while no active user has it), never deleted. `User.PermissionSetId` (`AssignPermissionSet`: `Role` becomes the set's `Highest`, sessions end; `ChangeRole` takes the set away; `PermissionSetChanged` after an edit). `PermissionSetService` (CRUD; an edit that changes levels rotates its users' stamps, so cookies are refused and the next sign-in carries the new levels) and `UserService.AssignPermissionSetAsync`. `AuthenticatedUser.Areas` (built by `ICompanyStore.AuthenticatedAsync(user)`, used everywhere a cookie or API key principal is made) becomes `WebSecurity.PermissionSetClaim` + one `AreaClaim` per area ("sales:Standard"); the constants and `LevelIn` live in `AuthClaims` (Application) so the API can filter too: `GET /api/search` has no area for sets (like the page) and leaves out hits outside the set's areas (`SearchAreas.Of(kind)`); scoped API keys still need the data scope for it. Decisions stay in `AccessRules`: `Required(path, method)` gives the role a request needs as before; `AreaOf(path)` gives its area (API paths through `ApiScopes.AreaOf`, pages and form endpoints through `PageAreas`, first match wins); `Allows(user, path, method, out needed)` compares the role, or with a set the area's level (`LevelIn`), refusing admin things and allowing paths with no area only where view-only would do. `AccessMiddleware` uses `Allows` (redirects carry `area` for the access-denied page); `CanReach(href)` hides menu links, home shortcuts and search hits. A new page prefix needs an area in `PageAreas` or a place in `AccessRulesTests.Every_page_belongs_to_an_area_or_needs_none`'s list. Show or hide a link with `CanReach(href)` and a form or button with `CanPost(action)` (the form's own action path), never `User.Can(role)` in components, so permission sets are followed; `Can(role)` remains for code that really asks about the role. Invitations can give a set (`UserInvite.PermissionSetId`, `InviteCommand.PermissionSetId`; `InviteService.GiveSetAsync` on accepting, by password or single sign-on; refused with `invite.set_inactive` if the set was switched off since). API `/api/users/permission-sets` (GET, POST, PUT `/{id}`, PUT `/{id}/active`), `PUT /api/users/{id}/role` takes `PermissionSetId`, `UserResponse.PermissionSetId`. Tests: `PermissionSetTests`, `AccessRulesTests`, `ApiAccessTests.A_key_of_a_user_with_a_permission_set_reaches_only_its_areas`.
- Single sign-on (slice 4): one OpenID Connect provider, settings on `SignInSettings` (Domain/Companies/SignInSettings.cs, moved out of TwoFactor.cs): `SsoEnabled`, `SsoProvider` (Microsoft: authority from `SsoTenant`; Google; Other: `SsoAuthority`, https or loopback http), `SsoClientId`, `ProtectedSsoClientSecret` (`ISecretProtector`, excluded from the export and audit), `SsoButtonLabel`/`ButtonText`, `SsoOnly`; `IsSsoReady`. `SingleSignOnService`: `SaveAsync` (audit `sign_in_settings`, shared `Snapshot`; then `ISingleSignOnHost.SettingsChanged`), `ClientAsync`, `SignInAsync(ExternalIdentity)` (match `User.ExternalLogin` "issuer|subject" (unique), else a verified email equal to `User.Email` (then linked), else an open invitation for it (accepted: user created with a random password, linked); otherwise `SignInStatus.NotInvited`; inactive or ended access refused; never `MustSetUpTwoFactor`), `LinkAsync` (the signed-in user's own account; `sso.linked_elsewhere`), `UnlinkAsync`. `AuthService.SignInAsync` answers `SsoRequired` for a right password when `SsoOnly` and the user isn't an admin. Web (`Security/SingleSignOn.cs`): `AddOpenBookSingleSignOn` registers the `oidc` scheme (Microsoft.AspNetCore.Authentication.OpenIdConnect, MIT) signing in to a 5-minute `OpenBook.External` cookie; `SsoOptionsSetup` fills its options from the settings (code flow with PKCE, response mode query so the correlation cookies stay SameSite=Lax, `MapInboundClaims` off; placeholders while off, because the handler reads its options on every request); `SsoHost` drops the cached options when settings change, so no restart. `GET /login/sso[?link=true]` challenges; `/signin-oidc` is the callback; `GET /login/sso/done` reads the external cookie, drops it, and signs in (`WebSecurity.CompleteSignInAsync`) or links. `SingleSignOn.Identity` maps claims: subject = Microsoft `oid` else `sub`; email = `email` (Microsoft: else `preferred_username`), verified when `email_verified` is true or it's the company's own Microsoft tenant (not common/organizations/consumers). Pages: the login page's button and `?sso=` messages, `/settings/sign-in` SSO card (shows the redirect address), "link your account" on `/account/password`, Unlink on `/settings/users/{id}`, the invitation page offers the button (and hides the password form under SSO only, except for admin invitations). API `PUT /api/settings/sign-in/sso` (secret write-only; `GET` reports `HasClientSecret`). Tests: `SingleSignOnTests` (services and claim mapping); the handshake with a real provider isn't tested (the challenge to Google's authorize endpoint was checked by hand).

## Threat model fixes (2026-11-12)

- Desktop host names: `DesktopHost.RestrictHosts` (PostConfigure of `HostFilteringOptions`, after the host's own from `AllowedHosts`) answers only `localhost`, `127.0.0.1` and `[::1]`, so DNS rebinding can't reach the localhost port; other names get 400. Servers use `AllowedHosts` as configured (`docs/admin/server.md`). Tests: `DesktopHostTests`.
- Setup code (`Security/SetupCode`, singleton): on a server (not Desktop) `/setup` asks for it on both forms (read a file, create the company) until a company exists; `OpenBook:SetupCode` chooses it, else 8 characters from an unambiguous alphabet made at start and logged once started when there's no company (`AnnounceWhenStarted`; a chosen code isn't logged). Compared case-, space- and dash-insensitively in constant time. `/setup` posts count in the sign-in rate limit (`RateLimits.SignInPaths`). Web tests get `WebTestDatabase.SetupCode` through `Apply`. Tests: `SetupWebTests`, `DesktopHostTests`.
- `SamplePasswords.Refusal`: a server (not the commands, not Desktop) exits 1 at start when the connection string's password is the compose file's `change-me`. Tests: `SamplePasswordTests`.

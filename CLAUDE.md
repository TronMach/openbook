# OpenBook

Open-source QuickBooks alternative in .NET 10. Plan and milestones: `ROADMAP.md`.

Licence: AGPL-3.0-or-later (`LICENSE`; decided 2026-11-01, when the repository went public). Dependencies must be compatible: MIT, BSD, Apache-2.0 or similar permissive licences (bundled fonts are OFL); never add a proprietary or GPL-incompatible package.

## Commands

- Build: `dotnet build`
- Test: `dotnet test` (Domain.Tests = pure unit; Integration.Tests = migrated in-memory SQLite incl. triggers) Each run migrates once into template databases (with and without a company) that every test copies (`LedgerDatabase`), so the full SQLite suite takes about 5 minutes through `tools/run-tests.ps1` (PostgreSQL takes about 24 at 12 at once, more than that at 6, hence its default of 12: each test copies a template database and drops it afterwards, and on Windows a drop waits for a checkpoint); `MigrationTests` still migrate for real. On PostgreSQL the first template of a run drops leftover `openbook_test_*` databases this login owns (a run's own templates usually outlive it); `PostgresTests` use `openbook_pgtest_*` so they're never caught.
- Run suites with `powershell -File tools/run-tests.ps1 [-Postgres] [-Filter …] [-Threads n]` (decided 2026-11-01): it caps the tests running at once (`xUnit.MaxParallelThreads`, default a quarter of the cores for SQLite, 12 for PostgreSQL; decided 2026-11-01) and runs at below-normal priority, because uncapped runs (xUnit's default is one test per core) froze the user's computer. It saves a trx file and exits 1 when a test failed (going by the trx counters as well as dotnet's exit code) or none ran, so the release workflow stops; `-Postgres` loads `.env` (`-EnvFile` from a worktree).
- Testing schedule (decided 2026-10-29): per milestone, build, run the tests for the area touched (`--filter`), check new pages in the browser and commit on its own. Run the full SQLite and PostgreSQL suites once per batch of 2–3 milestones and always before pushing, both at the same time (two processes), then drop the PostgreSQL leftovers (`openbook_test_*` / `openbook_pgtest_*` databases owned by `openbook_test`); if a batch run fails, rerun the failing tests at each commit to find the cause.
- Run: `dotnet run --project src/OpenBook.Web` (migrates `openbook.db` on startup; API under `/api`)
- Reset a forgotten password: `dotnet run --project src/OpenBook.Web -- reset-password [username] [--clear-two-factor] [--restore-admin]` (same config as the web app; prompts twice, reads lines when stdin is piped; refuses if the company file is missing rather than creating one; the first flag also turns the user's two-factor sign-in off, the second makes them an active admin with no end date, for a company left with none; both are stripped from the args before configuration)
- Restore a backup too large to upload (OpenBook stopped; same checks and safety copy as the page, SQLite only): `dotnet run --project src/OpenBook.Web -- restore-backup <file>`
- Move a SQLite company file into an empty PostgreSQL database (OpenBook stopped; the file is left unchanged): `dotnet run --project src/OpenBook.Web -- move-to-postgres --to "Host=…;Database=…;Username=…;Password=…" [--from <file>] [--source-keys <folder>] [--target-keys <folder>]` (file defaults to this install's; key folders to this install's Data Protection keys)
- Demo company for trying OpenBook or timing pages on books with history: `dotnet run --project src/OpenBook.Web -- make-demo --ConnectionStrings:OpenBook="Data Source=artifacts/perf/demo.db" [--years 3] [--invoices 150] [--password …]` (a new file only; everything entered through the services, same data for the same options; three years at 150 invoices a month take about four minutes).
- Encrypt / decrypt the SQLite company file in place (OpenBook stopped, key from `OpenBook:EncryptionKey`): `dotnet run --project src/OpenBook.Web -- encrypt-database` / `decrypt-database`
- New migration (SQLite): `dotnet ef migrations add <Name> -p src/OpenBook.Infrastructure -s src/OpenBook.Infrastructure -o Persistence/Migrations`
- New migration (PostgreSQL), every time a SQLite one is added: `dotnet ef migrations add <Name> -p src/OpenBook.Infrastructure.Postgres -s src/OpenBook.Infrastructure.Postgres -o Migrations`
- PostgreSQL tests run only with `OPENBOOK_TEST_POSTGRES` set (a server connection string allowed to create databases, e.g. `Host=localhost;Username=postgres;Password=…`); otherwise they're skipped. Add `OPENBOOK_TEST_ALL_ON_POSTGRES=1` to run the whole integration suite on PostgreSQL (each test gets its own database, dropped afterwards; `[SqliteFact]` tests such as file backups skip). Run it after schema or SQL changes. Web-hosted tests take their database from `WebTestDatabase`, so they run on PostgreSQL too (`openbook_pgtest_*`, migrated by the app): page behaviour differs between the providers because only PostgreSQL really waits, so a page fix counts only once both pass. `OrderedComponentTests` wait for real on either. Locally, `.env` (gitignored) holds `OPENBOOK_TEST_POSTGRES` for the `openbook_test` login (CREATEDB, not a superuser; its string names `Database=postgres`, since without one PostgreSQL looks for a database named after the user) and `OPENBOOK_PG_APP` for running the app as `openbook` (owns only the `openbook` database); load it with `set -a; . ./.env; set +a` (values are quoted because of the `;`). Test connections use 120 s timeouts (a full run creates hundreds of databases at once), and `LedgerDatabase.DropPostgresDatabaseAsync` retries a drop refused with 42501: a login that isn't a superuser can't end an autovacuum worker on PostgreSQL 17.
- CLI client: `dotnet run --project src/OpenBook.Cli -- help` (or pack it as the `openbook` dotnet tool). It only talks to a running server's API with an API key (`openbook config --url … --key obk_…`, saved in `%APPDATA%/OpenBook/cli.json`; `OPENBOOK_URL` / `OPENBOOK_API_KEY` override).
- Docker: `docker build -t openbook .` (SQLite in `/data`), or `docker compose up -d` (with PostgreSQL). `/healthz` for probes; the image's `HEALTHCHECK` runs `OpenBook.Web healthcheck` (exit 0/1, handled before the host is built; address from `ASPNETCORE_URLS`/`ASPNETCORE_HTTP_PORTS`, or `--url`). Admin guide: `docs/admin/server.md`.
- QuickBooks Desktop export helper (Windows): `powershell -File tools/package-qb-export.ps1 -Version x.y.z` → `artifacts/quickbooks-export/OpenBook.QuickBooksExport.exe` (the desktop package builds it too). Build into `artifacts/`, never a temp folder: the checkout is excluded from the user's antivirus (VIPRE), temp folders aren't.
- Desktop installer (Windows, Inno Setup 6 installed): `powershell -File tools/package-desktop.ps1 -Version x.y.z` → `artifacts/desktop/OpenBook-Setup-x.y.z.exe`. Run as Desktop from source: `dotnet run --project src/OpenBook.Web -- --OpenBook:Install=Desktop` (add `--OpenBook:Desktop:DataFolder=…`, `AppFolder=…`, `OpenBrowser=false` to keep it away from your Documents).

## Layout

Domain (no EF/ASP.NET) → Application (use cases, `ILedgerStore`) → Infrastructure (EF Core; SQLite migrations) → Infrastructure.Postgres (PostgreSQL migrations only) → Api (minimal API endpoints, class library) → Web (Blazor host, maps the API).

## Ledger rules (do not bypass)

- Everything that affects balances posts through `PostingEngine` as a `JournalEntry`. No other code writes `JournalLines`.
- Money is `decimal` (or `Money`) in code and integer minor units (`AmountMinor`) in the DB. Never `double`/`float` in Domain (`ArchitectureTests` enforces).
- Posted entries are immutable. Corrections = `VoidAsync`, which posts a same-date reversal. Never delete.
- Every change writes an `AuditRecord` in the same save.
- DB triggers enforce balance-on-seal, immutability and append-only audit (overview in `SqliteLedgerTriggers`). New entries are inserted unsealed and sealed in the same transaction by `OpenBookDbContext.SaveChangesAsync`.

## Migrations (SQLite)

- Trigger SQL lives frozen inside the migration that creates it (`*_InitialLedger.Triggers.cs`, `*_ChartAndSettings.cs`). Never edit an applied migration; to change a trigger, add a migration that drops and recreates it. Add new trigger names to `SqliteLedgerTriggers.Names`.
- A new column on `JournalEntries` must be added to the `TR_JournalEntries_Immutable` condition (via a new migration). The latest copies are in `*_LedgerGaps` (2026-11-06): entries start unsealed, only 1 seals on SQLite, a line needs an unsealed entry, void details change only with the void; PostgreSQL also refuses TRUNCATE on the journal tables.
- A trigger added after the first goes in `SqliteLedgerTriggers.Names` and `AddedBy` (its migration), or older backups are refused before they can be migrated. Restore checks trigger names, not their text.
- `IX_Accounts_SiblingName` (raw SQL in both projects, on the parent and lower-case name, not in the EF model) stops two first uses making one account twice: an EF rebuild of `Accounts` would lose it.
- Never let EF rebuild `JournalEntries`, `JournalLines` or `AuditRecords` (its SQLite `DropColumn`/`AlterColumn`): the rebuild loses triggers and its table swap runs after all `Sql()` steps. Drop the triggers, use native `ALTER TABLE … DROP COLUMN` via `Sql()`, recreate the triggers. Check generated migrations for `ef_temp_`.
- Backfill non-null columns explicitly in the migration (`defaultValue`), not with model `HasDefaultValue` (EF's sentinel rule would turn `false`/`0` into the DB default).
- `MigrationTests` cover a fresh database, upgrading an M0-era file, and downgrading.
- Keep SQL provider-neutral (quoted identifiers, no SQLite-only functions) for the V1.8 PostgreSQL provider.
- Domain errors throw `DomainException` with a stable `code`; the API maps them to 400 (404 for `EntityNotFoundException`).

## Company, sign-in, backup

- One company per database, created by `/setup` (`CompanySetupService`), then `/accounts` for a starter chart. Setting up from an export: "Read the file" (multipart, handler `read`) gets the company's details with `MigrationReaders.ReadCompany` (qbXML CompanyRet, QBO CompanyInfo/Preferences, GnuCash book options; IIF and CSV have none) to fill the form, and `SetupState.Hold` keeps the file (one, an hour, before setup only; the form carries its token); "Create company and import" runs `MigrationSetupService.SetUpAsync`: setup and import in one transaction (`EfUnitOfWork` joins an open one), nothing kept if a row has an error, audited as the new owner (the page sets `HttpContext.User` to the username first). Home currency comes from the `Company` row; ledger services throw `company.not_set_up` before setup. `SetupGateMiddleware` routes pages to `/setup` until then.
- Wrong passwords (2026-11-05): `SignInThrottle` (singleton, in memory) shuts one address out of one account after `User.MaxFailedLogins`, right password included, so nobody can keep someone locked out by knowing their username; the user's own count (`MaxFailedLoginsEverywhere`, 100, audited when reached) is for guessing from many addresses; two-factor codes still lock at 5. The login page answers the same either way, so it doesn't say which usernames exist.
- Cookie auth (`Web/Security/WebSecurity.cs`). The cookie carries the user's `SecurityStamp` and its `UserSession` id (`AuthService.SessionClaim`), both checked on every request (cookies without a session claim are refused, so people sign in again). Changing a password, "Sign out all other sessions" (`POST /account/sessions/end-others`) or restoring a backup ends other sessions; the first two re-issue the current browser's cookie, which keeps its session (`RenewSessionAsync`). A session counts while not ended, on the current stamp and used within `UserSession.IdleLimit` (8 h, also the cookie's sliding expiry); last use is written at most every 5 minutes. `/account/password` lists them (device from `UserAgents.Describe`, address, times) and signs one out (`POST /account/sessions/{id}/end`); signing out ends this browser's session. `UserSessions.SecurityStamp` is left out of the data export. Pages require auth via `Components/Pages/_Imports.razor`; mark public pages `[AllowAnonymous]`. The `/api` group requires auth and returns 401 instead of redirecting.
- "Today" is `CompanyTime.Today` (Application), never `DateTime.Today`: the company's `TimeZoneId` (IANA, Windows ids converted; null = the server's, which is UTC in containers), set in Settings. `CompanyTime` is static (one company per process), refreshed at startup, on a settings save and at the start of each hourly job run. Schedules (backups, report subscriptions, bank sync, "Send later") use `CompanyTime.Zone`. Timestamps shown on pages (audit, sessions, "Changed … by", emails sent) go through `InCompanyTime()`, never `ToLocalTime()`; services take "today" from their `IClock` with `CompanyTime.TodayAt(clock.UtcNow, CompanyTime.Zone)`.
- Region (2026-11-06): `Company.Region` (null until chosen; chosen at `/setup` and in Settings, `Company.Regions` is the list `AppCulture` offers) decides how printed documents, emails and the jobs write dates, whoever opens them; screens keep each person's region. Text goes out in `CurrentCulture` down to the PDF renderer, so a service producing either holds `using var region = CompanyRegion.Use(company);` around the whole of the work (it follows awaits). A new thing that prints or sends text for someone outside needs that.
- Audit actor comes from `ICurrentUser`, which the host registers (`WebCurrentUser` covers both HTTP requests and interactive circuits).
- Backup = SQLite online backup API → plain `.openbook.db` file. Restore validates (integrity, known migrations, triggers present, company present, ledger balanced), migrates and validates a temporary copy, writes a safety copy to `backups/` next to the company file, then copies over the live DB in place, so a failed migration leaves the books as they were. At start on SQLite, `SqliteBackupService.PrepareToMigrateAsync` clears a stale `__EFMigrationsLock` row and, when migrations are waiting on an existing company, takes a `pre-upgrade-…` copy (last three kept). A new trigger must be added to `SqliteLedgerTriggers.Names` or restore won't check for it.
- Pages are static server-rendered by default; use plain HTML forms with `<AntiforgeryToken />` for posts to minimal API endpoints (`Web/Endpoints`). Wrap a page's content in `<div class="wide">` for the wide layout.
- A second submit: `shortcuts.js` drops a repeat of a `method="post"` form within 5 seconds (not print forms, nor those opening a tab) and the second click of a double click on a submit button or one in `.actions` (so a save button goes in `.actions`; "Add line" buttons don't). Every interactive handler starts `if (_busy) return;`, for a click while the first is running: the render that disables the button may not have reached the browser. A handler that sets `_busy` must not be called from another that has.
- Interactive pages (`@rendermode InteractiveServer`: journal entry form, CSV import) must not inject application services directly: use `Operations.RunAsync` so each action gets a fresh scope and the right audit actor. A circuit outlives the request whose cookie was checked, so `RunAsync` checks the session each time on a circuit (`CircuitUser.InCircuit`) and refuses with `auth.session_ended` once it's over; what's already on the page stays until the person reloads. `/_blazor` is open to every role: the page's own rule was checked when it was opened.
- `FormDraft<T>` (Components; `Snapshot`, `OnRestore`, `ClearAsync` once saved) keeps a new document's typing in the tab's sessionStorage every 2 seconds, keyed by user and form, and offers it back after a lost circuit, since a circuit doesn't outlive a long sleep or a restart. On the new invoice, receipt, estimate and bill forms.
- Every component inherits `OrderedComponent` (`@inherits` in `Components/_Imports.razor`; layouts `OrderedLayout`; `Every_component_of_the_app_is_ordered` checks it). `ComponentBase` renders as soon as `OnInitializedAsync` first waits, which SQLite never does because its calls finish without waiting, so on PostgreSQL a static page's components would share the request's DbContext at once and draw null data. Here a component renders once it has loaded, and in a static render the components of a request load, and handle their forms, one at a time (`RenderTurn`, per scope), so static pages can inject services and load in `OnInitializedAsync`. A status page re-executed by `UseStatusCodePagesWithReExecute` isn't waited for by the framework (its scope is disposed under a running query), so it must draw without waiting: `MainLayout` skips its query there, and "not found" shows the default menu.

## Chart of accounts and reporting

- `AccountType` is QuickBooks' list (Bank, AccountsReceivable, …); `AccountClass` groups them for statements. Pick the narrowest type; M2–M4 key off Bank/CreditCard/AR/AP.
- Rules spanning accounts live in `ChartOfAccounts` (subaccount = parent's type, max 5 levels, unique sibling names and numbers, no cycles, class change blocked once posted). `AccountService` also refuses a type change to or from A/R or A/P once posted (`account.type_receivable`). Full names use `Parent:Child`. Accounts are deactivated, never deleted.
- CSV import (`ChartImportService`, parser in `Application/Import/Csv.cs`) matches headers loosely and is all-or-nothing. The starter chart at `Web/wwwroot/samples/chart-of-accounts.csv` is covered by a test.
- `ReportBasis` (Accrual/Cash) per report, default from company settings. `EntryBasis` on each entry (Both / AccrualOnly / CashOnly) decides inclusion. Cash basis for invoices and bills is payment-driven; see Reporting below.
- Dev preview: `.claude/launch.json` → `openbook-web` on port 5188, data in `src/OpenBook.Web/openbook.dev.db`.

## Banking (M2)

- Bank and credit card accounts are accounts of type `Bank` / `CreditCard`. Amounts in banking code are in the account's natural sign (`BankingRules.Natural`): positive = money in the bank, or owed on a card.
- `BankTransaction` is a document (Spend / Receive / Transfer, with payee and check number) that posts one journal entry with `Source = bank.*` and `SourceId` = the document id. Categories are the entry's lines. Documents are voided, never edited (except corrections in place, below); the journal page refuses to void entries posted by documents. `BankingService.ChangeAsync` corrects a spend or receive in place (entry voided and reposted; account and kind fixed; not a cash count's over/short; transfers go through `ChangeTransferAsync` instead (accounts, amount, date, memo; feed-backed ones keep amount and accounts; page `/banking/transfers/{id}/edit`, API `PUT /api/banking/transfers/{id}`); reconciled refused by `StageVoidAsync`). Feed lines added as it or matched to its entry (`BankFeedService.TiedToAsync`) keep its amount, and matched ones follow the new entry (`BankFeedItem.FollowEntry`; sales receipt corrections do the same); an issued check (printed, or sent by positive pay) keeps amount, payee and number; billable marks point at entry line numbers (bank line 1, splits from 2), so marked splits stay in place. `SplitsAsync` reads the current splits with classes. Page `/banking/transactions/{id}/edit`, API `PUT /api/banking/transactions/{id}`.
- Corrections keep what the document already has, though it's been deactivated since: `StageVoidAsync` remembers the voided entry's accounts, classes, location and tags for the scope (so void before staging the replacement), `SalesLineBuilder.BuildCorrectionAsync` the items, and Change pages offer them (`ItemService.ListForDocumentAsync`, `SegmentOptions.LoadAsync(sp, onDocument)`).
- Services that create several entries in one save use `PostingEngine.StageAsync` / `StageVoidAsync` (internal) and save once; `NextEntryNumberAsync` counts staged entries. Mutate documents only after the staged call succeeds, so a refusal leaves nothing changed in memory.
- Reconciliation state lives in `Reconciliations` / `ReconciliationLines` referencing ledger lines; the ledger itself is never touched. One in progress per account, ticks saved as made. Voiding is blocked for any entry with a ticked or reconciled line. Voided entries and their reversals are left out of worksheets and reports.
- Statement CSV import: `BankImportService` (headers matched loosely, starting at the first of the first 20 records that has a date and an amount header (`Csv.FromHeader`), so a bank's lines above it are skipped; the delimiter is the one found most, outside quotes, on any of the first 20 lines; one signed amount column or money-out/money-in columns) with `StatementValues` for dates and amounts. It refuses to guess on ambiguous amounts ("1.005") and flags ambiguous date orders. Possible duplicates = same date, signed amount and payee as an existing posted transaction.

## Sales (M3)

- `Customer` and `Item` (products and services; `Service` or `NonInventory`, each with a default price and income account) are deactivated, never deleted. Names are unique ignoring case. Customers with unpaid invoices can't be deactivated.
- `Invoice`, `CustomerPayment` and `SalesReceipt` are documents posting one journal entry each (`Source = sales.*`), voided never edited, except invoices: `InvoiceService.ChangeAsync` corrects one in place (same id and number) by voiding its entry (reversal on the original date) and posting a new one, with its stock reversed and planned again, in one save; so an invoice has one standing entry (`JournalEntryId`) and may have voided ones with the same `SourceId`. The customer can't change, the total can't go below `AmountPaid`, lines from a sales order or estimate (`SourceLines`) and billable expense/time/mileage lines (by `PriceSource`) must be passed back unchanged, and when the income per account and class changes, the dates payments and retainers were applied must be open too (cash basis allocates over current lines). Lines are renumbered in their new order; `ChangeInvoiceCommand.FromLines` says which old line each continues, and `CustomFieldStamper.MoveLinesAsync` moves their custom field values. The `Updated` audit record's after-snapshot carries `ChangeReason` (`ChangesAsync` reads them for the invoice page). Page `/sales/invoices/{id}/edit`, API `PUT /api/sales/invoices/{id}`. `SalesReceiptService.ChangeAsync` does the same for a receipt (customer can change, or be none; deposit account too; while in a bank deposit the total and deposit account must stay, `receipt.deposited`; reconciled ones are refused by `StageVoidAsync`). Page `/sales/receipts/{id}/edit`, API `PUT /api/sales/receipts/{id}`. Lines (`SalesLine`) need an item when they have an amount; item-less lines are notes. Rates and quantities allow 4 decimals (stored as ten-thousandths); line amounts round half away from zero to the cent. `SalesLine.Postings` credits each income account with its lines' sum (debits it if a discount makes it negative).
- Invoices post to the first active A/R account; one is created and saved on first use if none exists. Payments deposit to a Bank or Other current asset account (Undeposited Funds by default when the chart has it). Invoice `AmountPaid` is everything settled (payments, early payment discounts, applied credit) and is kept in step by payment create/void/change and credit application. `PaymentService.ChangeAsync` corrects a payment in place (entry voided and reposted; applications replaced, each invoice's old settlement removed and the new one applied, invoices audited; customer and receivable account fixed; credit applied later keeps its `AppliedOn` unless before the new date; unapplied ≥ refunded). The amount and deposit account stay while it's deposited, matched to a feed line (the match follows) or taken online (a `PaymentLink.CustomerPaymentId` points at it; the reference stays too, since Stripe payouts clear by it). Page `/sales/payments/{id}/edit`, API `PUT /api/sales/payments/{id}`. An invoice with anything applied can't be voided.
- Returned payments (bounced checks, 2026-11-07): `PaymentService.ReturnAsync(id, date, fee, feeAccountId, reason)` posts `CustomerPayment.ReturnSource` (`sales.payment_return`, `SourceId` = the payment): Dr A/R amount + discount, Cr the bank (the deposit's, or the payment's own bank account; refused while in Undeposited Funds, `payment.not_in_bank`), discount lines reversed, an optional fee Dr "Bank Service Charges" (`SalesAccounts.GetOrCreateBankChargesAsync`) / Cr bank. The payment stays posted with `ReturnedOn`, `ReturnEntryId`, `ReturnAccountId`, `ReturnFee`, `ReturnReason`; its applications stay, `StandsOn(date)` says whether they settle anything then (aging, statements: a return line), `Unapplied` is 0, and invoices' `AmountPaid` drops. Change, void, refund, apply credit and the deposit's change or void are refused (`payment.returned`, `deposit.payment_returned`); `UndoReturnAsync` voids the return entry unless an invoice was paid another way since. Cash basis: `ReturnSource` is an accrual document; each return in range keeps its non-A/R lines, takes the invoices' income back through a negative `SettlementPlan` turn (source = the return entry) and puts the unapplied part back in A/R. The books check counts it in `ReceivableSources` and as the payment's second document. Page: the payment's "The payment came back"; API `POST /api/sales/payments/{id}/return[/undo]`. Not done: returned gifts, chargebacks on channel payouts.
- Document services check everything before `StageAsync` and mutate documents/invoices only after staging succeeds.
- Customer and item CSV imports (`SalesImports.cs`) follow the chart import pattern (preview, all-or-nothing, existing names skipped). `CsvColumns` is the shared header matcher.
- SQLite can't `ORDER BY` a `DateTimeOffset`; order such results in memory.
- `Web/Components/Links.cs` maps a journal entry's source to its document page; use it wherever a ledger line links somewhere.

## Purchases (M4)

- `Vendor` mirrors `Customer` (plus your account number with them and a default expense category that pre-fills bills and expenses). Vendors with unpaid bills can't be deactivated.
- `Bill` lines are category lines (account, description, amount; negative = credit), not items; any active account except A/R and A/P. Bills post Dr categories / Cr the first A/P account (created and saved on first use). Bill numbers are the vendor's, unique per vendor. A bill with payments can't be voided. `BillService.ChangeAsync` corrects a bill in place like `InvoiceService.ChangeAsync` (entry voided and reposted, stock reversed and received again, which `PlanReversalAsync` refuses once a layer is used; vendor fixed; total ≥ `AmountPaid`; bill payment dates must be open when the postings per account and class change); bills from a purchase order go through `PurchaseOrderService.ChangeBillAsync` instead (the public `ChangeAsync` refuses them, `bill.from_order`). Lines marked billable (`BillableExpense.LineNumber`) must stay unchanged on the same line; other lines renumber and their custom field values move. Approval runs again (`Bill.Rehold`: held again, even if approved, with the changer as `EnteredBy`). History through the shared `DocumentChanges` (audit `ChangeReason`) and `<DocumentChangeList>`. Page `/purchases/bills/{id}/edit`, API `PUT /api/purchases/bills/{id}`.
- Possible duplicate bills (2026-11-03): `BillService.PossibleDuplicatesAsync(vendor, date, total, except)` (posted, same total, within `DuplicateDays` = 14); the new bill form shows them and turns its button into "Save anyway" until the vendor, total or date changes. API `GET /api/purchases/bills/duplicates`. Nothing is refused.
- `BillPaymentService.PayAsync` takes any open bills across vendors and writes one `BillPayment` per vendor (and per A/P account) in one save, vendors in name order; numeric check numbers count up from the first. Paid from a Bank or Credit card account. The vendor's account number is the default memo. `BillPaymentService.ChangeAsync` corrects one in place like a customer payment (applications replaced among the same vendor's bills on the same A/P account, bills audited; an issued payment (printed, `AchBatchId`, or sent by positive pay) keeps amount, account and reference; a feed-matched one keeps amount and account, and the match follows). Page `/purchases/payments/{id}/edit`, API `PUT /api/purchases/payments/{id}`.
- `BankingService.CheckNumberUsedAsync` (the spend form's "Save anyway"; nothing is refused). Expenses (paid immediately) are `BankTransaction` spends with an optional `VendorId`; the payee defaults to the vendor's name. Check-number suggestions count both expense and bill-payment references.
- `DocumentStatus` (Posted/Voided) is shared by sales and purchase documents; `Text.Optional` lives in Domain.Common.

## Reporting (M5)

- Every report reads lines from `ReportLedger.LinesAsync(basis, from, to)`, never from the store directly, so all reports agree. Accrual = ledger as posted (entry basis permitting). Cash = entries whose basis allows cash, minus everything sourced from invoices, bills, customer payments and bill payments; plus, for each posted payment in range, derived lines on the payment date: the deposit/payment account for the full amount, and the paid documents' accounts allocated in proportion to their lines. `SettlementPlan` splits all of a document's settlements in turn (date, then id), each taking the difference between the cumulative shares, so the last lands every line on its figure, whatever the report's range; credit applied comes off the lines first (`Less`), since it brings no money. A new accrual document type must be added to `AccrualDocuments` and given a derivation.
- `FinancialReports`: P&L sections by account type; balance sheet with "Retained earnings" (net income before the fiscal year containing the as-of date; merged into a top-level, childless Equity account named "Retained Earnings" if there is one, else a computed row) and computed "Net income" (since its start); general ledger with opening and running balances in each account's natural sign. Rows link to the general ledger for drill-down.
- Reports that need totals rather than lines (balance sheet, trial balance, opening balances, the dashboard) use `ReportLedger.TotalsAsync(basis, splitAt, to)` (each account folded into "before" and "since" lines) or `LinesSinceAsync(basis, detailFrom, to)` (history folded, detail after): on the accrual basis without a segment filter the database adds history up (`ILedgerStore.GetAccrualTotalsAsync`); otherwise it's folded in memory. Sums are exactly those of `LinesAsync` (`LedgerFoldingTests`). Folded lines have `Source = ReportLedger.BroughtForwardSource` and no entry. Cash basis loads only the payments and refunds dated in the range, the documents they pay and everything else settling those (all of them when the range starts at the beginning).
- `TrialBalanceQuery` also runs on `ReportLedger`. Income and expense accounts show this fiscal year on the trial balance and worksheet, and open at the fiscal year in the general ledger and registers; earlier years are in retained earnings, by the balance sheet's rule (`FinancialReports.PriorYears`, `RetainedEarningsAccount`; a computed row has `Guid.Empty` as its account). `DateRanges` has the period presets (calendar month/quarter, fiscal year).
- `SearchService` searches names, numbers, references, memos and amounts (`StatementValues.TryParseAmount`), ignoring case, max 20 hits per kind, newest first. Customers, vendors, items, accounts and custom field values are matched in memory; documents and journal-made entries (manual, import, opening balance, recurring) are narrowed by the stores' `SearchAsync`/`SearchMoreAsync`/`SearchManualEntriesAsync` (estimates, sales orders, credit memos and deposits in `ISalesStore.SearchMoreAsync`, purchase orders and vendor credits in `IPurchasesStore.SearchMoreAsync`; a new kind needs a heading and link in `Search.razor` and an area in `SearchAreas`) with a `DocumentSearch` (lower-case text, amount, the matched parties' and records' ids, take 21), so a search doesn't read every document. On SQLite only ASCII letters' case is ignored there. The EF queries use `ToLower()` under a local `#pragma` (CA1304/CA1311/CA1862): the culture overloads don't translate.
- Report pages share `Components/Reports` (`ReportFilter`, `ReportQuery`, `ReportSectionRows`); they're static GET forms so every report has a shareable, printable URL.

- Journal-sourced entries (`JournalEntry.IsJournalSource`: manual, auto-reversal, recurring, opening balance) are voided from the journal page; anything else from its document.
- Schedules: a template's place in its schedule is `OccurrencesPosted + IndexOffset`, and any maximum counts `OccurrencesPosted` alone. - `ReverseOn` posts a mirror entry (`AutoReversalSource`, `SourceId` = original). `PostingEngine.VoidAsync` voids a standing mirror with the entry, in one save (`StandingAutoReversalAsync`; a mirror's void shares its source, so look at `Kind`). Recurring templates (`RecurringEntry`) compute each date from `StartDate` and the occurrence index, so month ends don't drift; `RecurringEntryService.PostDueAsync` saves each occurrence separately and stops a template at its first error. `RecurringPostingService` (Web) runs it hourly for auto-post templates as actor "system".
- `JournalEntryFilter` can filter by `Source`/`SourceId`; use it rather than scanning entries.
- Opening balances post against "Opening Balance Equity" (created on first use); A/R and A/P are excluded (enter open invoices/bills instead). `OpeningBalanceService.PostYearToDateAsync(through, amounts)` posts income and expense accounts' year so far (natural sign) against the same account, source `ledger.opening_balance`, memo "Year to date before OpenBook" (page section "Year to date so far", API `POST /api/opening-balances/year-to-date`).
- Starter charts are embedded CSVs in `Application/Accounts/Templates`, imported through `ChartImportService`; each has a top-level "Retained Earnings" equity account. Their last column is the tax line, every income and expense row filled in (`ChartTemplateTaxTests`); the corporation chart is written for Form 1120-S and `ApplyAsync` turns it to Form 1120 for a C corporation by line name (`TaxLines.Equivalent`).
- `AuditLogQuery` filters in memory and diffs top-level JSON fields (null = absent). `Links.ForAuditEntity` maps an entity type to its page; add new entity types there.
- `JournalLinesEditor` (Components/Journal) is the shared debit/credit grid; the parent owns the `JournalLineModel` list and checks it with `JournalLines`.

## Receivables (V1.3)

- Sales lines have a `SalesLineKind`: Item, Note, DiscountPercent (percent of the item lines above it) or DiscountAmount. Discount lines post to the income account "Discounts Given" (`SalesAccounts.GetOrCreateDiscountsAsync`). Build lines with `SalesLineBuilder`, never `SalesLine.FromDrafts` directly in services.
- Terms are `PaymentTerms` (due days plus optional early payment discount) from the customer, copied onto each invoice (`EarlyPaymentDiscountPercent`/`Date`). A payment application has `Amount` (money) and `Discount` (posted Dr Discounts Given); `Settled` is both.
- A `CustomerPayment` has an explicit `Amount`; what isn't applied is customer credit (`Unapplied`). Credit (credit memo balance or unapplied payment) is applied to invoices by `CreditService.ApplyAsync`, which posts nothing; applications carry `AppliedOn` dates so aging and statements work as of a past date. Applying more of the same source to the same invoice adds to the existing application (keeps the first date). `ApplyAsync` needs the date open (`EnsureOpen`), and on a company whose default basis is cash the payment's date too, since cash basis counts it there; not on accrual, or a prepayment could never be used once its year is closed. `CreditService.UnapplyAsync` and `VendorCreditService.UnapplyAsync` take a credit memo or vendor credit back off an invoice or bill (the date applied must be open; audited on both; `POST /sales/credit-memos/{id}/applications/{invoiceId}/remove`, `/purchases/vendor-credits/{id}/applications/{billId}/remove`, API `DELETE` on `/applications/{id}`). Payment credit comes off through `PaymentService.ChangeAsync`.
- `CreditMemo` posts the mirror of an invoice (Dr income, Cr A/R) and shares the invoice number sequence (each refuses a number the other uses; `SalesAccounts.NextNumber` increments the trailing digits of the highest, keeping prefix and padding). `CreditService.ChangeCreditMemoAsync` corrects one in place like an invoice (customer fixed; total ≥ applied + refunded; date no later than the first application; when the income per account and class changes, refund dates must be open, since cash basis allocates refunds over the current lines; returned stock reversed and planned again). Page `/sales/credit-memos/{id}/edit`, API `PUT /api/sales/credit-memos/{id}`. `CustomerRefund` pays credit back (Dr A/R, Cr bank/card) from one credit memo or one payment.
- `Estimate` posts nothing; changing the customer, lines or total of one answered online clears the answer and puts it back to Pending; `InvoiceService` closes it when invoiced (`CreateInvoiceCommand.EstimateId`) and reopens it when that invoice is voided.
- Payment methods (2026-11-03): `PaymentMethod` (Cash, Check, Card, BankTransfer, Other; `PaymentMethods.Label`) on `CustomerPayment`, `SalesReceipt`, `Donation` and `Retainer` (`SetMethod`, nullable, set after `Create`/`Change`; commands take `Method`, change commands keep it when null; online payments are Card). `UndepositedItem.Method` feeds the deposit form's "Tick only" buttons and `ListReports.DepositSlipAsync` (cash/check/other totals; `GET /banking/deposits/{id}/slip` and `/api/sales/deposits/{id}/slip` as PDF through `IReportExporter`). `PaymentMethodField` (Components/Sales) on the interactive forms.
- Undeposited funds: payments, receipts, retainers and gifts in an Other current asset account are grouped by `DepositService` into a `BankDeposit` (`Source = bank.deposit`: Dr bank, Cr holding account). Deposited items can't be voided until the deposit is. `BankDeposit.Extras` (owned `BankDepositExtras`, `DepositExtraDraft`, at most `MaxExtras`; `MakeDepositCommand.Extras`): signed lines besides the items, negative = a fee or cash back (Dr its account), positive = other money (Cr its account), in `Total` and the bank debit; not A/R, A/P or the deposit's own bank; the total must stay above zero (`deposit.total_not_positive`); on the slip, the detail page and the API. Kinds outside Sales register an `IUndepositedSource` (marked and cleared in the deposit's save; `DescribeAsync` gives deposited ones' dates and labels for changing a deposit); `Links.ForDeposited` gives each kind's page.
- Cash basis (`ReportLedger`): credit memos and refunds are accrual documents. Payments recognize applied amounts plus discounts against the invoice lines (credit applied later counts on the payment's date), keep the unapplied part in A/R, and include the discount lines as posted. A credit memo refund reverses income on the refund date; a payment refund counts as posted.
- Money ahead of its document: an application to an invoice or bill dated after the as-of date isn't a settlement of anything then, so the agings count it as credit (`ReceivableDocuments.InvoicesDatedLater`, `VendorAging.PaidAhead`), and they keep tying to A/R and A/P. Refunds can't be dated before their source, nor a source moved past its refund (`refund.before_source`). `CustomerSummary`/`VendorSummary.Balance` is open documents less unused credit, as on the aging; `CustomerService.StatementListAsync` rolls billed sub-customers into their parent, once each. A sub-customer settled by another customer's money stays billed with it (`customer.settled_by_parent`).
- `ReceivablesService` computes aging and statements from the documents, not the ledger. `ReceivablesService.Aging(customers, documents, asOf)` is the calculation; `AgingAsync` feeds it `ISalesStore.ListReceivablesAsync(asOf)`: invoices dated by then that are unpaid now or settled by something dated after it, whatever settled them, and payments and credit memos holding credit now or used or refunded after the date, with their refunds (exactly the documents that can matter; `BooksCheckTests`' random runs compare it with every document). Statements and one customer's aging use `ListReceivablesForAsync(customerIds)` (those customers' documents plus anything others applied to their invoices). Settlements are found from the applications (indexed by invoice) to their documents, selecting the owned rows' foreign keys (`EF.Property<Guid>(a, "CustomerPaymentId")`): selecting the owner's id inside the collection needs an APPLY, which SQLite can't do. Forms: `FormService` builds `SalesForm`/`StatementForm`, `IFormRenderer` (MigraDoc) renders them. PDFsharp-MigraDoc is pinned to `[6.2.4]`, the last MIT release (6.5+ is AGPL or commercial): never let it be upgraded. Its Core build needs `SystemFontResolver`, which maps the one family forms use ("OpenBook Sans") to a system sans-serif, or to OpenBookSans-Regular/Bold.ttf in a `fonts` folder beside the app. PDFs are served inline at `/api/sales/{kind}/{id}/pdf`.
- Email: `EmailService` with `IEmailSender` (MailKit; "folder" delivery writes .eml files to `mail/` beside the company file). The SMTP password is encrypted by the host's `ISecretProtector` (Data Protection; tests use a marker). Every send writes an `AuditAction.Emailed` record. `RecurringPostingService` also creates (and emails) automatic recurring invoices. Recurring templates (invoice, bill, expense, gift) make each occurrence and advance in one `IUnitOfWork` transaction, so a failure between can't repeat it; a refusal discards the scope's tracked changes, so each template is loaded afresh.
- Scheduled invoice emails: `ScheduledEmail` (Domain/Sales; audit `scheduled_email`, linked to `/sales/scheduled-emails`): the message fixed when scheduled, `SendAt` in UTC (later than now, within a year), Scheduled → Sent / Failed (reason kept; `RetryAsync` puts it back to go on the next run) / Cancelled; never deleted. `ScheduledEmailService.SendDueAsync` sends each due one through `EmailService.SendFormAsync` (so the PDF shows the invoice as it is then) and saves each on its own; an invoice voided, paid or written off since is cancelled, not sent (decided when due, so a payment taken back leaves it to go; one already settled can't be scheduled, `scheduled_email.invoice_settled`). `ScheduledEmailHostedService` runs it every minute as "system". The invoice email form (`/sales/email/invoices/{id}`) has "Send later" with a `datetime-local` in the company's time zone; the invoice page and `/sales/scheduled-emails` list them with cancel / try again (posts in `CollectionEndpoints`). API `/api/sales/invoices/{id}/scheduled-emails` (GET, POST with `SendAt` and optional to/subject/body, defaulting to the usual draft), `/api/sales/scheduled-emails` and `/{id}/cancel|retry`.
- New audit entity types: estimate, credit_memo, refund, deposit, recurring_invoice, email_settings, form_style (a form design; all in `Links.ForAuditEntity`).

## Banking pro (V1.2)

- Statement files: `Ofx.Parse` (Application/Import) reads OFX/QFX/QBO, SGML or XML, with a regex tag scan (no XML parser); a file with more than one account is refused (`ofx.several_accounts`). The preview carries each line's occurrence (`BankImportRow.Occurrence`, `FeedLine.Occurrence`), so the second of two identical lines comes in alone. `BankFeedService.PreviewAsync` takes OFX or CSV; nothing posts at import.
- `BankFeedItem` is the review queue (Pending / Added / Matched / Excluded). `PostingEngine.StageVoidAsync` puts lines tied to the voided entry back to Pending (`ListFeedItemsTiedToEntryAsync`), audited; a correction that posts a replacement passes `keepFeedLines: true` and follows the match. `DedupeKey` is unique per account: `fit:<FITID>`, else a text key of date, amount, payee and reference with `#n` for the nth identical line in one file. Re-importing skips known keys. An id arriving with another amount, or a date more than `MatchWindowDays` away, is another line the bank numbered the same (`BankFeedItem.ReusedKey`: the id plus its date and amount); a date moved less is the same line. The preview also flags `PossibleDuplicate` for a line with the date and amount of one already in the feed, whatever its status.
- Add stages a `BankTransaction` through `BankingService`; Match links an existing ledger line of the same holder-view amount within 7 days; Reopen (undo) voids the transaction for an added line. The audit log links feed lines and imports through `GET /banking/feed-lines/{id}` (`BankFeedService.LocateAsync`: line id or import batch id), which opens the account's feed on the line's tab (`?show=`).
- A spend or receive can't be categorized to A/R or A/P (`bank.category_receivable`; an older line stays on a correction). A line a rule can't add waits for review and `FeedImportResult.NotAdded` says why; a rule never fits a line on its own category account. Connections move a quiet account on to a month behind today, and report an account the service no longer lists.
- A feed line added takes `AddFeedItemCommand.Splits` (adding up to the line), `ClassId`, `LocationId`; rules carry a class and location too (splits aren't on rules). `MatchAsync(itemId, entryIds)` ties one line to several entries that add up to it: `MatchedJournalEntryId` is the first, the rest are owned `MoreEntries` (`BankFeedItemEntries`); read them through `MatchedEntryIds`. `FollowEntry(from, to)`; voiding any of them sends the whole line back. `FeedReviewItem.PartMatches` are the smaller entries near it. `FeedDocumentService` (bank accounts only): `CandidatesAsync` offers open invoices (money in) or approved open bills (money out) whose balance is the line's amount, dated by it; `ApplyAsync(item, kind, id)` records `PaymentService.ReceiveAsync` / `BillPaymentService.PayAsync` on the line's date and reference and matches the line, in one `IUnitOfWork` transaction. API `GET /api/banking/accounts/{id}/feed/documents`, `POST /api/banking/feed/{id}/pay-document`.
- `BankRule`: first active rule in `Priority` order whose text is in payee or memo (plus direction, amount range, account) wins. AutoAdd rules post at import, except a line with a possible match (same amount within `MatchWindowDays`), which waits for review so it can't double; others only suggest. A vendor only goes on money-out rules.
- `ReconciliationService.StartAsync` ticks the lines feed items stand for (added from or matched to, dated by the statement, not reconciled before). `ReconciliationService.UndoAsync` reopens only the latest completed reconciliation of an account, and only when none is in progress; ticks are kept.
- Checks: `CheckService` lists bank (not card) spends, bill payments, customer refunds and retainer refunds (`CheckKind.CustomerRefund`/`RetainerRefund`; both carry `PrintedAt`, `PositivePaySentAt`, `PositivePayVoidSentAt` like bill payments; `PrintableCheck.OwnerId` is the retainer; positive pay lists and marks them, and `ListSpendReferencesAsync` counts their references for the next check number), not payments in an ACH batch nor spends from statement or feed lines (their money has left; printing an ACH one is refused, `check.sent_by_ach`, and the page ticks only those with a check number); printing (`PrintAsync(checks, firstNumber)`) numbers checks that have none from `firstNumber` in the order given (digits, keeping zeros; `AssignCheckNumber` on spends, bill payments and both refunds) and renders `CheckForm`s (voucher layout, absolutely positioned MigraDoc frames, `AmountInWords.ForCheck`) and sets `PrintedAt` with an audit record. Printing goes through the web form endpoint `/checks/print` (antiforgery), which binds `IFormCollection`: minimal APIs on .NET 10 can't bind a `string[]` form parameter.
- Blazor `[SupplyParameterFromQuery]` can't bind enums: take a string and `Enum.TryParse`.
- Audit entity types: bank_rule, bank_feed_item, bank_feed_import.

## Sales tax (V1.5)

- Domain in `Domain/SalesTax`: `TaxAgency` (owns a liability account: a subaccount of "Sales Tax Payable", created by `SalesTaxService` on agency creation), `TaxRate` (one agency, percent to 4 decimals, stored as ten-thousandths), `TaxCode` (1–10 rates in print order; "combined" when more than one), `SalesTaxPayment` (`Source = salestax.payment`).
- Tax lines are `SalesLine`s of kind `Tax`, appended after the other lines by `SalesLineBuilder.BuildAsync(drafts, customer, taxCodeId, date)`: one per rate of the code, even when zero, with `TaxRateId`, `Rate` = the percent charged and `IncomeAccountId` = the agency's liability account, so `SalesLine.Postings` credits it and cash-basis allocation covers it. They're never drafted: use `SalesLine.Drafts(lines)` to copy a document's lines (`ToDraft()` throws on a tax line).
- `TaxCalculator` is the one place for the math (the web preview calls it too): taxable amount = taxable item lines less each discount's taxable share; tax = taxable × combined percent rounded once, split by rate through `Shares.ByWeight` (the running total, so a 0% rate gets nothing and none goes negative).
- Corrections keep what was sold: `BuildCorrectionAsync` keeps each continuing line's income account (unless it's inactive), list rate and price source (`SalesLine.KeepFrom`, by `FromLines`, else by position). A sub-customer billed with its parent is covered by the parent's exemption (`CustomerTree.ExemptionOn`).
- Corrections keep the tax charged: `SalesLineBuilder.BuildCorrectionAsync` with `TaxAsCharged`, used by the three `Change…` services: under the same customer and code the tax is recomputed on the new lines at the stored rates (`TaxCalculator.Charged`) and stored exemption, even if the code can't be charged now; the Change pages list the document's code at those rates (`ListChoicesForDocumentAsync`). A code with active customers can't be made inactive (`tax.code_in_use`); `SalesTaxField.CustomerCodeOff` warns on forms for a customer already on one.
- Command `TaxCodeId`: null takes the customer's code, `Guid.Empty` charges no tax. Documents store `TaxCodeId` and `TaxExemption` (the customer's exemption text when valid on the document date; tax lines are then zero). Recurring invoices use the customer's code; estimates pass theirs to the invoice.
- Line `Taxable` defaults from the item (`Item.Taxable`; existing items were backfilled taxable); `SalesLineDraft.Taxable` null means "the item's setting".
- Inactive codes, rates and agencies can't be charged (`tax.code_inactive`, …); a rate in an active code and an agency with active rates can't be deactivated.
- `TaxAgency.Region` (one agency per state): `ChannelPayout.Postings(channel, taxAccounts)` sends a Tax or MarketplaceTax line with that ship-to `Region` to the agency's account, and `LiabilityAsync` adds an "Online sales" row (`TaxRateId` empty) from posted payouts. Lines with no region stay on the channel's tax account. Already posted payouts aren't moved.
- `SalesTaxReports.LiabilityAsync` works from the documents (accrual): invoices and receipts plus credit memos negated, each counted on every rate of its code, one row per rate and percent charged; `SalesTaxPaymentService.OwedForPeriodAsync` is the balance at a period's end less payments dated after it for that period; owed figures are the liability accounts' ledger balances. `FilingPeriods.LastCompleted` gives the period to file.
- `FormService.TaxTotals` gives the subtotal/tax rows for screens and PDFs; tax lines never show as ordinary lines.
- Audit entity types: tax_agency, tax_rate, tax_code, sales_tax_payment (attachments allowed on sales_tax_payment and now shown on customers, for certificates).

- Comparisons: `Comparisons.Columns` (previous period, previous year, months, quarters; max 24 columns). Multi-column statements build each column with `FinancialReports.BuildProfitAndLoss/BuildBalanceSheet` and a shared `show` set so every column has the same rows; `StatementTables` zips them and adds `DerivedColumn`s ($ change, %, total).
- Cash flow (indirect): cash = Bank accounts; operating = net income + current assets/liabilities (incl. A/R, A/P, cards); investing = fixed/other assets; financing = long-term liabilities and equity. Net change always equals the bank balance change.
- Sales by customer and expenses by vendor read `ReportLedger` (so they tie to the P&L on either basis) and attribute lines by `Source`/`SourceId` to the document's customer/vendor. Sales by item is document-based (accrual).
- `Budget` (Domain/Reporting): monthly amounts (natural sign, P&L accounts only) for one fiscal year; owned `BudgetLines`; deletable (audit `Deleted`). `SavedReport` stores report key + query string (presets stay relative); saving under an existing name updates it. Audit types `budget`, `saved_report`.
- Tax summary table: net profit row (Schedule C "line 31"), half of 24b meals taken off, and on Schedule C the mileage log's standard mileage value under "Not in the books" (`StatementReports` reads `IProjectStore`). Schedule C has line 30 (`c.30`).
- Tax lines: `TaxLines` catalog per `TaxForm` (from `BusinessType`), keys stored in `Account.TaxLineKey` (P&L accounts only; cleared on a change to a balance sheet type). Unmapped subaccounts use the nearest parent's line in `StatementReports.TaxSummaryAsync`. Keys are stable; relabel lines for new form years, never rekey.
- Grid forms (budget amounts, tax line mapping) and save/delete of saved reports post to `Web/Endpoints/ReportEndpoints.cs` binding `IFormCollection`.
- Reports added 2026-11-06: `budget-by-class` (`StatementReports.BudgetByClassAsync`: every budget for a class in the fiscal year of the date, side by side), `grant-budget-vs-actual` (`ReportInputs.Grant`), `inventory-rollforward` (`InventoryReports`), `profit-by-product` (`ActivityReports`; sales from `SoldByItemAsync` plus `ChannelOrderService.SoldAsync`, cost from movements). The three nonprofit statements take `Compare`, activities `Segments`, and a nonprofit's accountant package adds `NonprofitReports`. Budgets go in and out as CSV (`BudgetService.ToCsvAsync`, `ImportCsvAsync`; `/reports/budgets/{id}/csv|upload`).
- ClosedXML is MIT (0.105.x); text cells are written as text so nothing exports as a formula, and CSV prefixes `=`, `+`, `@` and non-numeric `-` with `'`.

## Inventory (V1.6)

- `ItemType.Inventory` items carry `InventoryAssetAccountId` (other current asset), `CostAccountId` (expense class, usually COGS), `ReorderPoint` and `PurchaseCost`. `ItemService` fills missing accounts with "Inventory Asset" / "Cost of Goods Sold" (`InventoryAccounts`, created on first use; "Inventory Shrinkage" is the default adjustment account). Once an item has movements its type and asset account are locked.
- Stock is an append-only ledger of `InventoryMovement`s (Domain/Inventory). A receipt is its own FIFO layer (`LayerId == Id`); issues and reversals point at a layer. `Fifo.Layers` derives remaining quantity/cost; `Fifo.Take` uses the oldest layers received on or before the date, proportional cost rounded to the cent with the last of a layer taking exactly what's left. Stock can't go negative (`inventory.insufficient`) unless the item may be sold short (below).
- Documents move stock through `InventoryService` in three steps: plan (checks everything: `PlanSaleAsync`, `PlanReturnAsync`, `PlanPurchaseAsync`, `PlanReversalAsync`), stage the entry with the plan's postings appended, then `Apply`. Sales post Dr COGS / Cr inventory asset in their own entry; credit memos restock at the latest sale's average unit cost (else average on hand, else purchase cost). Voids add opposite movements on the document date and are refused once a layer the document opened has been used (`inventory.layer_used`). `InventorySources` names the document types (audit entity types).
- Bills take item lines (`BillLineDraft.ItemId`/`Quantity`): the line posts to the item's asset account and opens a layer at the line amount. Vendor credits and recurring bills refuse item lines. `BillLinesEditor` shows item columns when given `Items` (bills only).
- `InventoryAdjustment` (`Source = inventory.adjustment`, audit `inventory_adjustment`, attachments allowed): increases at a unit cost, decreases at FIFO cost; value change against the adjustment account (Opening Balance Equity for starting stock; `AdjustmentAccountId = Guid.Empty` creates it, since a new company doesn't have it).
- Cash basis keeps the inventory cost lines of invoices and credit memos as posted (`ReportLedger`): COGS is recognized when stock is sold.
- A sale short on its date first takes stock dated later (`Costing.Take`, only for items that may be sold short), at its real cost; so a past date's movements can hold an issue whose receipt comes later, and `Fifo.Layers`/`Slices` keep such a layer, at what's been taken, so past stock adds up. Only what's beyond all the stock is a shortfall.
- Selling short: `Company.AllowSellingShort` (Settings → Stock, audited in the company snapshot) and `Item.SellShort` (`ShortStock.Company/Allow/Never`; `Allow` refused for lot/serial items, `item.short_stock_tracked`); `Item.CanSellShort(companyAllows)` decides. `InventoryService.ShortfallCostAsync` gives the estimate (`Costing.EstimatedUnitCost`: purchase cost, else latest receipt's unit cost, else average, else 0) or null; sales (the automatic take) and build components pass it to `TakeAndSimulate`/`Costing.Take`, which takes what `Fifo.Available` allows and makes the rest one `FifoTake` with `Shortfall` → `InventoryMovement.Issue` writes it as a shortfall layer (a receipt of −q at −cost, `IsShortfall`). Transfers and adjustment decreases never sell short. Every receipt goes through `InventoryService.Receive` (receipts made with `PlannedReceipt`, then `ForSource`): it fills open shortfalls oldest first, same warehouse first (`InventoryMovement.Cover` +q at the estimate on the shortfall, an issue −q at actual cost from the receipt) and posts the difference Dr/Cr cost of goods sold vs the asset in the receiving document's entry, line memo starting `InventoryService.ShortfallMemo` (cash basis keeps those bill lines as posted). Bills and PO receipts now stage the stock plan's postings; adjustments add them as `corrections`; auto-builds inside a sale plan with `fill: false`. A sale whose shortfall was filled can't be voided (`inventory.shortfall_filled`); voiding the filling document reopens it.
- `EfInventoryStore.ListMovementsAsync` includes unsaved added movements, so several documents in one save see each other's stock.
- Reports: `inventory-valuation` (as of a date, summary or layers, with a tie-out row to the asset accounts), `inventory-stock` (reorder status) and `inventory-aging` (value on hand by layer age: 90/180/365 days and older, last sold date from invoice, receipt and channel issues; longest unsold first) in `ReportCatalog`, built by `InventoryReports`.

- Physical counts (2026-11-03): `InventoryAdjustmentService.CountAsync(InventoryCountCommand)` compares counts with the warehouse's stock on the date and makes one adjustment for the differences (reference "Physical count"; increases at purchase cost into no bin, decreases from any bin); null when all matched; lot/serial items refused (`count.tracked`). Report `physical-inventory-worksheet` (`InventoryReports.CountSheetAsync`, lots listed). Page `/inventory/count` posts `count:{itemId}` to `/inventory/count` (`InventoryEndpoints`); API `POST /api/inventory/count`.

## Multi-user and server (V1.8)

- `UserRole` (ViewOnly < Standard < Accountant < Admin) on `User`, plus `IsActive`; users are deactivated, never deleted. Changing a role or deactivating rotates the security stamp, so sessions end. `UserService` keeps at least one active admin and refuses changes to yourself. Inactive users sign in like a wrong password.
- Access is decided in one place: `Web/Security/AccessRules.Required(path, method)` (first matching prefix rule; reads need ViewOnly, changes and "write pages" — `new`, `edit`, `import`, `apply`, `pay`, `reconcile`, `feed`, recurring editors, … — need Standard), enforced by `AccessMiddleware` for pages, form endpoints and the API (403 JSON for `/api`, `/access-denied` redirect otherwise). A new page or endpoint that changes the books or settings needs a rule; add a case to `AccessRulesTests.Access_rules_map_paths_to_roles` (in `ApiAccessTests.cs`; a class of its own because `ApiAccessTests` starts a web app per case). Hide nav links with `User.CanReach(href)`.
- The role is a claim in the cookie; cookies without one (from before V1.8) are rejected so people sign in again.
- API keys (`ApiKey`, `ApiKeyService`): `Authorization: Bearer obk_…`, SHA-256 hash stored, shown once, act as their user with the user's role, revoked not deleted, last use recorded at most once a minute. The default auth scheme is a policy scheme picking the bearer handler (`ApiKeyAuthenticationHandler`) or the cookie.
- OpenAPI at `/api/openapi/v1.json` (anonymous; Microsoft.AspNetCore.OpenApi). `/api/me`, `/api/users`, `/api/api-keys`, `/api/webhooks`, `/api/backup` cover what the new pages do.
- Webhooks are fed by the audit log: `WebhookDispatcher` (run every 5 s by `WebhookDispatchService`) turns audit records after each subscription's `Cursor` into `WebhookDelivery` rows, stopping at a gap in the ids until it's `GapWait` (5 minutes) old, since on PostgreSQL a long transaction's ids show only at commit (event type `{entity_type}.{action_snake}`, payload with before/after snapshots, fixed at creation), then posts due ones via `IWebhookSender` (`HttpWebhookSender`: 10 s timeout, no redirects) with `OpenBook-Signature: t=…,v1=HMAC-SHA256(secret, "t.body")` (`WebhookSignature`). Retries back off 1 m → 12 h, 6 attempts, then Failed (redeliver by hand). Secrets are stored with `ISecretProtector`. Anything audited is an event, so keep audit snapshots free of secrets. Outbound calls to addresses people type in (webhooks, SimpleFIN claim/access URLs) use `Net.PublicNetwork.Handler(OutboundPolicy)`: its connect callback resolves the host and refuses (`PrivateNetworkException`) when any address is loopback, private, link-local, shared, multicast or reserved (IPv4-mapped and NAT64 judged as IPv4), connecting to the checked address so DNS can't switch in between. `OpenBook:Outbound:AllowPrivateNetworks=true` turns it off (the host registers `OutboundPolicy`). S3 backup and SMTP hosts are admin settings and may be local; fixed hosts (Stripe, Shopify, Google Fonts, Claude) don't need it.
- Concurrency: records two people (or a person and a background job) may change at once carry a shadow `Version` concurrency token (`OpenBookDbContext.Versioned`: documents with balances or status, bill payments, recurring templates, feed lines, payment links, payouts, items), bumped by every save that modifies the row, or adds, changes or removes one of its owned rows (`TouchOwners`: what's used of a credit is summed from its applications). A stale save, or a unique number (entry or document number) taken in between, throws `ConcurrencyConflictException` (`save.conflict`, API 409) and saves nothing. `Operations.RunAsync` (new scope) and the `/api` filter (`DiscardPending`, raw bodies rewound) run the operation again, up to `ConflictRetry.Attempts`, only while the scope hasn't saved anything (`IUnitOfWork.HasSaved`); static form endpoints show the message. A new entity people may change concurrently goes in `Versioned` (migration in both projects). Stock: every save adding `InventoryMovement`s bumps those items' versions (`SaveChangesAsync` touches them), so two documents planned from the same stock can't both save; this relies on plans loading the item (tracked) before reading its movements, as `InventoryService` does.
- Stale forms: the token only catches overlapping saves, so edit pages note the version when they open and check it first (`IRecordVersions`, `EnsureUnchangedAsync`, `save.stale`; read it before loading the record). Interactive: `Ops.VersionAsync<TRecord>(id)` and `Ops.ChangeAsync<TRecord, TService, T>(id, _version, …)`; static: a hidden `Input.Version` and `Versions.EnsureUnchangedAsync`. Not on settings pages, nor the API (which sends no version). A new edit page of a `Versioned` record does the same.
- Encryption at rest: SQLite runs on SQLCipher (`SQLitePCLRaw.bundle_e_sqlcipher` 2.1.11 with `Microsoft.EntityFrameworkCore.Sqlite.Core`). `OpenBook:EncryptionKey` becomes the connection's `Password`; backups and safety copies use the same key, and restore only accepts backups with that key. `SqliteEncryption` converts files with `sqlcipher_export` (triggers included).
- PostgreSQL: `OpenBook:Database=Postgres` (or a connection string starting `Host=`). Migrations live in `OpenBook.Infrastructure.Postgres` (`InitialPostgres` creates the whole current schema; ledger triggers as PL/pgSQL functions in `InitialPostgres.Triggers.cs`, same names and messages, plus a TRUNCATE guard on AuditRecords). Every schema change needs a migration in both projects, and trigger changes in both dialects. In-app backup/restore is SQLite-only (`UnsupportedBackupService` says to use pg_dump). Store `DateTimeOffset`s in UTC (Npgsql rejects other offsets). The whole integration suite passes on PostgreSQL 17. Tests that touch the database directly catch `System.Data.Common.DbException` and use SQL both providers accept (TRUE/FALSE, explicit `"Basis"`).
- Containers: Data Protection keys go to `OpenBook:DataProtectionKeys` (Docker: `/data/keys`) so cookies and stored secrets survive restarts. The image installs DejaVu fonts for PDFs and `libgssapi-krb5-2` (Npgsql loads it on connect) and runs as the non-root `app` user. The build copies `.editorconfig`, which marks migrations as generated code; without it the analyzers fail the Release build. Image and compose stack verified with Docker Desktop (Linux containers); on a fresh PostgreSQL database EF logs one failed `__EFMigrationsHistory` query before creating the schema, which is expected.
- Audit entity types: api_key, webhook (users were already `user`).
- Diagnostics (`Web/Diagnostics`): `FileLoggerProvider` (made by the container so it's disposed; one file per UTC day `openbook-yyyyMMdd.log`, kept 14 days, written by one background writer from a bounded queue; Microsoft/System categories at Warning and up) also keeps the last 100 warnings and errors in memory. `LogFolder.For`: `OpenBook:LogDirectory`, else `logs` beside the backups folder (Docker: /data/logs), else beside a SQLite file, else the content root. `JobStatus` (singleton, in memory) holds each background job's last run, duration and last failure: every hosted service records its run (failures reported per item count too), and `RecurringPostingService` records each step. Page `/settings/system` (admin).

## Segments (L1)

- Domain in `Domain/Segments/Segment.cs`: one `Segment` entity for classes (per line), locations (per transaction; `Company.LocationLabel` renames them, e.g. "Department") and tags (per entry, flat). Classes and locations nest (full names "Parent:Child", max 5 levels, unique among siblings, rules in `SegmentRules`); deactivated, never deleted. `Company.TrackClasses` / `TrackLocations` only show or hide the form fields.
- Segments live beside the ledger, never in it: `LineSegments` (one row per journal line with a class or location) and `EntryTags`. Posted lines stay immutable and their triggers untouched, while segments can be reclassified. `JournalLineDraft.ClassId` and `PostJournalEntryCommand.LocationId` / `TagIds` are written by `PostingEngine.StageAsync` (validated: right kind, active); voids and auto-reversals copy them, so reports by segment net to zero.
- Documents record them too: `SalesLine.ClassId`, `BillLine.ClassId`, `BankSplit.ClassId`, and `LocationId` on invoices, receipts, credit memos, estimates, bills, vendor credits and bank transactions (set with `SetLocation`; every line of the entry carries it). Sales postings are one line per income account and class. Inventory cost lines take the class the item's lines share, else none. Cash basis (`ReportLedger`) allocates payments with `AllocateByClass` and the paid document's location, so cash-basis segments come from the documents.
- `SegmentService`: lists (tree order), tracking, `SetTagsAsync` (tags are editable after posting; the reversal follows; not on reversals) and `ReclassifyAsync` (class and/or location of posted lines; closed periods need the closing password; a document's location applies to its whole entry; documents follow: sales lines by income account and old class, bill lines by position). Each change is an `Updated` audit record on the journal entry.
- `JournalLineDraft.LocationId` is a line's own location (else the entry's). An early payment discount and a bad debt go in the invoice's classes (`Invoice.ByClass`, in proportion to its income) and location, on those lines only; `PostingEngine.Carry` lets them use segments deactivated since, and `SegmentsOfAsync` gives an entry's location only when every line has it.
- Reports: `SegmentFilter` (class and location include subsegments; `Guid.Empty` = "Not specified", query value `none`) via `ReportLedger.LinesAsync(basis, from, to, filter)`; `ReportInputs.Segments` (`classId/locationId/tagId`) on P&L, GL, sales by customer and expenses by vendor. `profit-and-loss-by-class` / `-by-location` give a column per segment plus "Not specified" and Total. Budgets can be for a class and/or location (budget vs. actual and prior-year seeding filter by it). Tag filters on cash basis use the payment's entry tags.
- Web: `SegmentOptions.LoadAsync` (interactive forms, through `Operations`), `ClassSelect` and `LocationField`; the line editors take `Classes` (null hides the column). `<EntryTags EntryId=…/>` on detail pages, `<SegmentFilterFields>` on report filters. Pages `/segments`, `/segments/{id}`, `/segments/reclassify` (accountant); form posts in `Web/Endpoints/SegmentEndpoints.cs`. API under `/api/segments` (tags at `/api/segments/tags/{entryId}`). Audit entity type `segment`.
- Recurring templates (journal, invoice, bill) store a class per line, a `LocationId` and tags (`Tags`: comma-separated ids as text, at most `Recurrence.MaxTags`; `TagIds` parses them), checked when saved (`PostingEngine.EnsureSegmentsAsync`) and passed to every entry or document they make. Forms use `LocationField` and `TagChecks` (`SegmentOptions.Tags`). Journal entry CSV imports take optional class (per line), location (per entry; lines must agree) and tags (`;`-separated) columns by full name; the migration importers don't.

## Migration and scheduled backups (L8)

- `ImportedBefore` keeps imports from repeating: a transaction or journal CSV entry with the date, memo, accounts and amounts of a standing `ledger.import` entry is `Exists` (each standing entry answers for one incoming, so identical ones in a file both come in once; undoing an import frees them).
- The planner runs the same rules as the import (`Vendor.Create`, `Account.Create`, `Item.Create`, inactive accounts), so a clean preview imports. An all-zero transaction is Skipped. An account whose number is taken comes in without one (`#1234` references still reach it).
- Moving in from another program goes through one pipeline (`Application/Import/Migration`): a reader turns the export into `MigrationData` (accounts, customers, vendors, items, transactions in OpenBook's terms), and `MigrationImportService` previews it against the books and imports it all-or-nothing in one `IUnitOfWork` transaction (the old IIF importer's rules: existing names are left alone, transactions become `ledger.import` journal entries, one batch per file). `MigrationReaders.Read(source, bytes, homeCurrency)` picks the reader. Readers never touch the database; accounts named "#1234" are resolved by account number in the planner.
- Jobs come in as sub-customers billed with their customer (`SourceCustomer.Parent`, the source's full name; the customer CSV takes a Parent column or "Customer:Job" names, parents anywhere in the file). Inventory parts come in tracked (`ItemType.Inventory`, `SourceItem.Quantity`/`UnitCost`) and `OpeningStockService.RecordAsync` brings their stock in: an adjustment against Opening Balance Equity and, with `alreadyInBooks`, a journal entry taking that value back out, since the history already holds it. CSV imports, each preview then all or nothing: `OpeningStockImportService` (`/inventory/opening-stock`), `OpenDocumentImportService` (`/import/open-documents`: real invoices on an "Opening balance" item, and bills, warning when the A/R or A/P accounts hold money no document explains), `ProjectImportService` (`/time/people/import`: people, rate card, unbilled time). API under `/api/import` (`/open-documents/{kind}`, `/opening-stock`, `/projects/{kind}`).
- Readers: `IifImportService.Read` (QuickBooks Desktop IIF; the service is now a thin wrapper), `QbxmlReader` (QuickBooks Desktop SDK responses: accounts, customers, vendors, items, journal entries; jobs and other transactions are reported, not imported), `QuickBooksOnlineReader` (QBO API query JSON; journal lines resolve accounts by id), `GnuCashReader` (XML book, gzip or not; split values are fractions; an account whose type differs from its parent's starts a new top-level branch because OpenBook subaccounts share their parent's type; other currencies are refused), `XeroReader` (chart, contacts or manual journal CSV, recognized by columns), `WaveReader` (accounting transactions CSV) and `FreshBooksReader` (clients CSV). XML is loaded with DTDs prohibited and no resolver; elements are matched by local name with `Named`/`Child`/`Text` (don't call `XDocument.Descendants(string)`, which needs the namespace).
- Page `/import/migrate` (also `/import/quickbooks`, accountant) and `POST /api/import/migrate/{source}` with the raw file as the body (`?dryRun=true` previews). No live QuickBooks Online OAuth connection: the API JSON is saved and uploaded.
- Scheduled backups: `BackupSchedule` (singleton row: daily or weekly at an hour in the company's time zone, folder or S3-compatible destination, keep N; the secret key protected by `ISecretProtector` and left out of the data export and audit) and `ScheduledBackupService` (settings, `RunDueAsync`, `RunNowAsync`; outcome kept on the schedule). A run is due when nothing has run since the latest slot, so the first one runs right away, or when the last failed an hour ago and fewer than `BackupSchedule.Retries` (5) tries followed the slot. Each copy is checked first (`IBackupService.CheckAsync`: the restore checks) so a damaged file never rotates good ones out; `BackupSchedule.IsFailing` (last run failed, or the last success older than two periods plus a day) shows on Settings and the home to-do list. Targets are `IBackupTarget`s in `Infrastructure/Backups`: `FolderBackupTarget` (write then rename) and `S3BackupTarget` (path-style requests signed by `AwsSignatureV4`, tested against the AWS example). Only files named `openbook-scheduled-{company}-*` of this company are ever deleted (the first 8 of its id; names from before that are left alone). `ScheduledBackupHostedService` checks every 15 minutes. SQLite only, like manual backups. UI on `/backup` (admin), API `/api/backup/schedule`. Audit entity type `backup_schedule`.

## Banking advanced (L4, slice 1)

- Live bank feeds: `BankConnection` (Domain/Banking; owned `BankConnectionAccount`s keyed by the service's account id) holds the access credential protected by `ISecretProtector` (excluded from the data export and audit snapshots). `IBankConnectionClient` per provider; only SimpleFIN so far (`SimpleFin` parser in Application, `SimpleFinClient` HTTP in Infrastructure: setup token = Base64 claim URL, POST once for the access URL, GET `/accounts` with Basic auth, fetched in 60-day pieces, https only). `BankConnectionService.SyncAsync` fetches posted lines from `Start` (last fetched date − 10 days, else `ImportFrom`, else 30 days back) into `BankFeedService.QueueAsync` with `FitId` = the service's transaction id, so overlaps dedupe; pending lines wait. Failures are kept on the connection (`LastSyncFailed`, `LastError`), not thrown. `BankSyncHostedService` syncs due connections (every 6 h) as "system". Pages `/banking/connections` (accountant). Tests use `FakeSimpleFinBridge` behind the real client.
- Positive pay: `PositivePayService` lists numbered checks (digits-only references) on a Bank account, spends (not those from statement or feed lines, `ImportBatchId`: their money has left, and the reference is the bank's; check number suggestions skip them too) and bill payments, voids marked `V`; the first file for an account goes back `FirstFileDays` (90); the CSV is ASCII (account number, check number, date, amount, payee, void). Each check records what the bank knows (`PositivePaySentAt`, `PositivePayVoidSentAt`, on spends and bill payments): with no dates the file is `UnsentAsync`, new checks and voids of sent ones whatever their date; dates send a range again. A sent check keeps its amount, payee and number. `PositivePaySettings` per account remembers the bank account number, date format, header and how far exports went. Page `/banking/positive-pay`; audit type `positive_pay_export`.
- Petty cash: `PettyCashFund` (a Bank account with a `FloatAmount`) and `CashCount`s. `PettyCashService.CountAsync` stages an over/short spend or receive against "Cash Over and Short" (created on first use) in the same save; `ReplenishAsync` transfers float − balance. Spending from the box is an ordinary spend. Pages `/banking/petty-cash`, `/banking/petty-cash/{id}`; audit type `petty_cash_fund`. Form posts for all three live in `Web/Endpoints/BankingEndpoints.cs`; API under `/api/banking/connections`, `/positive-pay`, `/petty-cash`.

- Recurring expenses (2026-11-03): `RecurringExpense` (Domain/Banking; audit `recurring_expense`, Versioned; owned `RecurringExpenseLines` as `BankSplit`s; paid from a Bank or CreditCard account, optional vendor and payee, `Recurrence` schedule, location and tags). `RecurringExpenseService.CreateDueAsync` records each occurrence through `BankingService.RecordAsync` (a spend), saving each on its own and stopping a template at its first error; the hourly job's "Recurring expenses" step runs automatic ones. Pages `/banking/recurring`, `/banking/recurring/new|{id}`; API `/api/banking/recurring-expenses` (+ `/{id}/active`, `/record-due`).

## Inventory costing (L4, slice 2)

- `Item.CostMethod` (`InventoryCostMethod.Fifo` / `Average`, tracked items only, locked once stock has moved). Every stock issue goes through `Costing.Take(item, movements, quantity, date)`: quantity still comes out of FIFO layers (so availability and void checks are unchanged), but average items cost the take at the average on hand on the date (rounded once, spread over the layers; taking everything takes its whole value). Layer costs of average items aren't meaningful one by one; the valuation detail shows one "Weighted average" row for them.
- `ItemType.Bundle` (kit) and `ItemType.Assembly`; `Item.IsInventory` (= `Item.IsTracked(type)`) is true for inventory products and assemblies. Both have `Components` (`ItemComponent`, owned table `ItemComponents`), set with `ItemService.SetComponentsAsync`: bundles take any non-bundle item; assemblies take tracked items only, no cycles. A component's type can't change in a way its parent forbids.
- Bundles sell as one sales line (their own price and income account); `InventoryService.ItemQuantitiesAsync` expands them into tracked components (line quantity × component quantity) for sales, returns and voids, costing to each component's accounts.
- `AssemblyBuild` (`Source = inventory.build`, audit `assembly_build`): `AssemblyBuildService` issues the bill of materials × quantity at each component's cost and receives one layer of the assembly at the total (Dr assembly asset, Cr component assets). Void = unbuild, refused once the built layer has been used. `PreviewAsync` gives needs, on hand and the most buildable.
- `LandedCost` (`Source = inventory.landed_cost`, audit `landed_cost`): spreads an amount from an account (default "Landed Cost Clearing", other current asset, created on first use; never bank, card, A/R or A/P) over the receipts of chosen posted bills, by value or quantity (`LandedCost.Allocate`, by `Shares.ByWeight`; receipts ordered by item then id). Each share splits by the layer's remaining quantity: that part becomes an `InventoryMovement.CostAdjustment` (quantity 0) on the layer and Dr the item's asset; the rest Dr its cost of goods sold (stock built into assemblies counts as gone, too). A bill under a landed cost can't be voided; a landed cost can't be voided once its layers have moved since.
- Pending builds (`PendingBuild`, audit `pending_build`): a build saved to finish later posts nothing and holds no stock. `AssemblyBuildService`: `SavePendingAsync`, `BuildWhatYouCanAsync` (builds the most whole units the warehouse allows, the rest pending, one save; output lots are for the built part), `FinishPendingAsync` (an ordinary build on the finish date), `CancelPendingAsync`, `ListPendingAsync` (with today's preview). The build page posts `Input.Mode` = build / partial / pending / finish; `?pending={id}` finishes one. Builds are planned by `InventoryService.PlanBuildAsync`, which also serves auto-builds.
- `Item.AutoBuild` (assemblies without lot or serial tracking): `PlanSaleAsync` builds a sale's shortfall in the warehouse from components inside the sale's own entry (Dr assembly asset, Cr components) before taking the sale; the build's movements belong to the sale, so voiding it undoes both. Receipts planned before a document exists are made with a placeholder source and re-sourced with `InventoryMovement.ForSource` (same id). `PlanReversalAsync` counts a layer as used only when movements from other documents (not voided again) touch it.
- Pages `/inventory/builds/new` (preview by query string, then an `EditForm`), `/inventory/builds/{id}`, `/inventory/landed-costs/new`, `/inventory/landed-costs/{id}`; components grid on the item page posts to `/items/{id}/components` (`Web/Endpoints/InventoryEndpoints.cs`). API under `/api/inventory` (`/items/{id}/components`, `/builds`, `/landed-costs`).

## Stock tracking (L4, slice 3)

- A warehouse or bin with stock stays active (`warehouse.has_stock`, `bin.has_stock`). An invoice or receipt whose shortfall has been filled can still be corrected while its items, quantities, lots, date and warehouse stay: its movements are kept and the new entry repeats the old cost lines (`InventoryService.KeptStockAsync`). Found stock on a count uses `Costing.EstimatedUnitCost`. `form[data-keep-typed]` (`shortcuts.js`) brings a form's values back after a refusal (the gift, pledge, grant and count forms; nothing of type password).
- Places: `Warehouse` (one `IsDefault`, "Main", created on first use by `WarehouseService.DefaultAsync`) and `Bin` (in a warehouse). Documents and movements store the default warehouse as **null** (`Warehouse.Key`), so pre-warehouse data needs no backfill; `StockPlace(WarehouseId, BinId)` is a place. `WarehouseService.CheckAsync` turns a chosen id or place into the stored form (active, bin in that warehouse). Deactivated, never deleted; the default can't be.
- `InventoryMovement` carries `WarehouseId`, `BinId` and `Lot` (set on the receipt, copied onto everything that moves it). Costing is still per item across places: `Fifo.Slices` splits each layer by place, and `Fifo.Take(movements, quantity, date, name, StockFilter)` takes from slices the filter allows (`StockFilter.In(warehouse)` = any bin; `At(place)` = exactly that bin or no bin; `.WithLot`). `Costing.Take` passes the filter. Plans that take an item more than once use `InventoryService.TakeAndSimulate` so later takes see earlier ones.
- Invoices, sales receipts, credit memos and bills have `WarehouseId` (commands take `WarehouseId`; `WarehouseField` on the forms, shown once there are two warehouses). Sales take from any bin of the warehouse; receipts arrive outside bins. Adjustment lines take a place (`StockPlaces` lists warehouses and bins for static forms) and lots; builds take a warehouse (components and output) and output lots.
- `StockTransfer` (audit `stock_transfer`, `InventorySources.Transfer`) moves stock between places on the same layers (`InventoryMovement.Transfer`: −q at the source, +q at the destination, cost 0); posts nothing, but its date must be open (`EnsureOpen`), as for a void. Void refused once the moved stock has left the destination. A bill/receipt void is refused once its layer has moved anywhere (`PlanReversalAsync` checks the receipt's place too).
- Lots and serials: `Item.Tracking` (`ItemTracking.None/Lot/Serial`, tracked items only, locked once stock has moved). `LotText` parses "A-1 x 3; B-2 x 2" (one lot alone = the whole line) and serials "S1, S2" (whole units, one each) and formats them back. Each lot or serial is its own receipt layer (cost split by quantity, `InventoryService.Split`). Receipts must name them (`lot.required`); a serial can't be received while in stock. Sales take the lots named on the line, else the oldest; the lots actually used are saved on `SalesLine.Lots` / `BillLine.Lots` (`RecordLots`) and shown on screens and PDFs. Bundle components always take the oldest. `InventoryService.LotHistoryAsync` and the inventory page's lookup trace a lot or serial.
- Lot expiry: `LotDetail` (item + lot, `ExpiresOn`), set on the item page or `InventoryService.SetLotExpiryAsync` (lot-tracked items, existing lots). Automatic picks go through `InventoryService.ForPickingAsync`, which adds the expiries to the `StockFilter`: soonest expiry first, expired lots skipped (a named lot is still taken). `ExpiringAsync` lists lots on hand expiring by a date (inventory page: next 30 days).
- Landed costs follow stock into assemblies: the share for a layer's quantity issued to (unvoided) builds goes to the build's assembly layers by quantity, split again into on hand (cost adjustment) and sold (the assembly's cost of goods sold); only what was sold or adjusted goes to the component's cost of goods sold. One level deep.
- Labels: a barcode whose narrowest bar would be under `LabelService.NarrowestBarPoints` (0.54 pt) across `PrintableWidthPoints` is refused (`label.barcode_too_long`). `Code128` (Application/Inventory/Labels.cs: set C for even digit runs of 4+, else set B; `Modules` gives bar/space widths) and `LabelService` → `ILabelRenderer` (`LabelRenderer`, PDFsharp, Letter 3 × 10 of 2⅝" × 1"). Page `/inventory/labels` posts to `/inventory/labels` (PDF). Don't name a page `Labels.razor`: its class hides the `Labels` helper.
- Reports: `ReportInputs.Warehouse` (`warehouseId`, a warehouse's id) limits `inventory-valuation` (detail by bin and lot; no tie-out row) and `inventory-stock` to one warehouse.
- Barcodes: `Item.Barcode` (unique ignoring case, plain printable, ≤ 50) is a picker keyword, so scanning into an item `SearchSelect` and pressing Enter picks it; `ItemService.FindByBarcodeAsync`, API `/api/inventory/items/barcode/{code}`.
- Pages `/inventory/warehouses` (form posts in `InventoryEndpoints`), `/inventory/transfers/new`, `/inventory/transfers/{id}`; stock by place and lot on item pages. API under `/api/inventory` (`/warehouses`, `/bins`, `/stock/places`, `/lots/{lot}`, `/transfers`). Audit types `warehouse`, `stock_transfer`.

## Collections (L3, slice 1)

- Sub-customers: `Customer.ParentId` (rules in `CustomerTree`: max 5 levels, no cycles, full names "Parent:Child", `Ordered` for tree order; names stay unique across all customers). `CustomerService.CheckParentAsync` refuses inactive new parents, cycles and too-deep moves (counting the levels below the customer); a parent with active sub-customers can't be deactivated, nor a sub-customer reactivated under an inactive parent. `BillWithParent`: `CustomerTree.BillTo` walks up to who's billed, and invoice, estimate and credit memo forms and emails are addressed there, with a "For" fact naming the project or job; the parent's payments and credits can settle billed sub-customers' invoices (`PaymentService.BilledAsync`, used by payments and `CreditService.ApplyAsync`), its statement includes them (a billed sub-customer's statement is the parent's), and reminders go to the parent. A/R aging still lists each customer's own invoices, in tree order; settlements count from any payer.
- Bad debt: `BadDebtWriteOff` (`Source = sales.write_off`, audit `write_off`, attachments allowed) per invoice: Dr "Bad Debts" (expense, created on first use) or a chosen expense/other expense account, Cr the invoice's A/R; settles the invoice through `AmountPaid`, so the invoice can't be voided while it stands. `WriteOffService.WriteOffAsync` takes several invoices in one save (one entry each); void puts the balance back. Aging and statements count write-offs by date. Cash basis drops them entirely (in `AccrualDocuments` with no derivation: the unpaid income was never recognized). Sales tax on written-off invoices stays owed.
- `CollectionSettings` (one row, everything off until saved; audit `collection_settings` on the company): late fees (percent of the overdue balance to 4 decimals + flat amount, grace days, repeat every N days or once, automatic or not) and reminders (schedule of days from the due date, -90..365, at most 6; subject/body templates with `{customer} {invoice} {balance} {due} {days} {when} {company}`, filled by `CollectionSettings.Fill`).
- Overlapping runs: a fee records `Invoice.LateFeeOn`, unique with `LateFeeForInvoiceId` (null on older fees), and a clash counts as already charged; a reminder's row is saved before the email goes (removed if it fails), so the second run stops on the unique index.
- An invoice with a standing late fee can't be voided (`invoice.has_late_fees`). Automatic recurring invoices that fail to email wait as failed `ScheduledEmail`s, on the to-do list; a recurring template that stops fails its job step, so the System page shows it.
- Late fees: `LateFeeService.DueAsync(today)` lists open invoices (not fees themselves) past `due + grace` whose last fee (voided ones count, since voiding waives it) is older than the repeat period; customers with `NoLateFees` or inactive are skipped. `ChargeAsync` makes one invoice per fee through `InvoiceService` (internal `lateFeeFor` sets `Invoice.LateFeeForInvoiceId`), due on receipt, untaxed, for the "Late Fee" service item (income "Late Fee Income", other income; both created on the first charge and remembered on the settings).
- Reminders: `InvoiceReminder` rows (unique per invoice and step). `ReminderService.DueAsync` picks, per open invoice, the latest step reached that's on or after the invoice date and later than any sent, so a missed step is skipped rather than sent late; `SendAsync` emails the invoice PDF through `EmailService.SendFormAsync`, records each send on its own and keeps going after a failure (stops on email not configured).
- `RecurringPostingService` also charges late fees and sends reminders hourly when they're set to be automatic. Pages `/sales/collections` (what's due today, with ticked rows), `/sales/collections/settings` (accountant), `/sales/write-offs/new` (overdue by N days, or `?invoice=`), `/sales/write-offs/{id}`; customer pages add the parent picker, "bill with parent", no reminders, no late fees and a sub-customer list. Form posts in `Web/Endpoints/CollectionEndpoints.cs`; API under `/api/sales` (`/write-offs`, `/collections/settings`, `/late-fees`, `/reminders`).

## Sales flow (L3, slice 2)

- The invoice that clears a line charges what's left of its amount (`PartialInvoicing.Billed`, worked out from quantities and the line's rate), so progress invoices add up to the source.
- Partial invoicing (`Domain/Sales/SalesOrder.cs`, `PartialInvoicing`): an invoice made from a sales order or estimate records `Invoice.SourceLines` (owned `InvoiceSourceLines`: source line number + quantity) and `SalesOrderId` (estimates use the existing `EstimateId`). What's invoiced is summed from the source's posted invoices, so voiding an invoice frees its quantities with nothing to undo. Item lines bill by quantity (`ByPercent` scales every item line, 4 decimals, capped at what's left); an amount discount goes whole on the first invoice that bills an item (tracked as quantity 1); percent discounts and notes go on every invoice; tax is recalculated each time. Lines keep the source's price (`ToDraft`, no repricing); lots are kept only when the whole line is billed. `InvoiceService.CreateAsync(..., source: InvoiceSource)` closes the order/estimate when `Completes`; voiding reopens a closed one.
- `SalesOrder` (audit `sales_order`, attachments allowed): posts nothing, holds no stock, own number sequence, customer PO number (copied into the invoice memo as "Your PO …"), warehouse. Open → Closed (all invoiced) or Cancelled (`CancelAsync` stops the rest). Editable only until the first invoice. `SalesOrderService.InvoiceAsync(id, InvoiceFromSourceCommand)`: chosen `Lines`, a `Percent`, or (neither) everything left.
- Progress invoicing: `EstimateService.ProgressInvoiceAsync` (same command); `ConvertToInvoiceAsync` now invoices what's left. An estimate can't be edited after its first progress invoice (`estimate.invoiced`) and closes when fully invoiced. Old estimates invoiced whole have invoices without source lines; they're already closed.
- Retainers (`Retainer`, audit `retainer`, attachments allowed): received into a Bank account or Undeposited Funds (then Make deposit), Dr bank / Cr "Customer Deposits" (other current liability, created on first use), `Source = sales.retainer`. Applications (`sales.retainer_application`, owned `RetainerApplications`, own entry Dr deposits / Cr A/R, settle the invoice via `AmountPaid`; the retainer's customer or a sub-customer billed with it) and refunds (`sales.retainer_refund`, owned `RetainerRefunds`, Dr deposits / Cr bank or card) can each be voided (reversal entry, `IsVoided`); `SourceId` is the retainer for all three. Aging and statements count applications by `AppliedOn`. Cash basis: receipts and refunds as posted; applications are in `AccrualDocuments` and derived as Dr deposits / Cr the invoice's income lines (like a payment).
- Billable expenses (`BillableExpense`, audit `billable_expense`): a category line of a posted bill (`BillLine.LineNumber`, no item, cost > 0) or expense (a debit line of the spend's journal entry other than the bank), marked after posting with a customer and markup (`BillableExpenseService.MarkAsync`; unique per document and line; removable until invoiced, audited `Deleted`). `CreateInvoiceCommand.BillableExpenseIds` adds them as "Billable Expenses" lines (service item, income "Billable Expense Income", untaxed, price source "Billable expense"; created on first use) and sets `InvoiceId`; voiding the invoice clears it. `BillService.VoidAsync` / `BankingService.VoidAsync` call `BillableExpenseService.ReleaseAsync` first: refused if a cost is invoiced, else the marks are removed.
- Pages: `/sales/orders`, `/sales/orders/new`, `/sales/orders/{id}/edit`, `/sales/orders/{id}`; estimates' "Turn into an invoice" is the shared `PartialInvoiceForm` (Components/Sales; posts `mode` rest/percent/lines, `percent`, `qty:{line}`); `/sales/retainers`, `/sales/retainers/new`, `/sales/retainers/{id}`; `/sales/billable`; `BillableLinesPanel` on bill and expense pages; `RetainerOffer` (Components/Sales) on open invoices lists `RetainerService.AvailableForInvoiceAsync` with an apply button (the apply post takes `back` to an invoice page); the new invoice form lists the customer's open billable expenses to tick. Form posts in `Web/Endpoints/SalesFlowEndpoints.cs`; API under `/api/sales` (`/orders`, `/estimates/{id}/progress(-invoice)`, `/retainers`, `/billable-expenses`). `PriceNote` hides the list price when the item has none (0).

## Purchasing controls (L3, slice 3)

- Bills from an order: `Bill.LinesFromOrder` says how many of its lines came from the order (null on older bills, which plan it again); a zero-cost item line goes on a bill and into stock at no value (no posting); hold reasons are cut to fit (`HoldText`). An order with priced goods received and not billed can't be cancelled (`purchaseorder.received_not_billed`). Inbox documents: lines for one order item add up to one order line at the printed amounts (`Amount / Quantity` to 4 decimals). `ReceiptService.RecordAsync` is one transaction, and `ReceiptCapture` is `Versioned`.
- `PurchaseOrder` (Domain/Purchases/PurchaseOrder.cs; audit `purchase_order`, attachments allowed; own number sequence): owned `PurchaseOrderLines` (an inventory item, not an assembly, with quantity and unit cost to 4 decimals; or a category line with an amount) and `PurchaseOrderReceipts` (rows per line grouped by `ReceiptNumber`, voidable). Posts nothing; receiving posts nothing either (stock enters the books with the bill). Open → Closed (everything billed) / Cancelled; editable until anything is received or billed.
- Bills from a PO: `PurchaseOrderService.CreateBillAsync(id, BillFromOrderCommand)`; lines given (quantity + the vendor's unit cost, or a category amount) or, by default, what's received and not billed (everything left when nothing is received). The bill records `PurchaseOrderId` and owned `BillSourceLines` (line, quantity, amount); billed totals come from posted bills, so voiding frees them and reopens a closed PO. 3-way match differences (billed more than ordered; more than received when `RequireReceipt`; unit cost, or a category line's running total, over the order beyond `PriceTolerancePercent`) go to `BillService.CreateAsync(..., BillSource)` as hold reasons. The lines are worked out by `PlanBillAsync`; `ChangeBillAsync(billId, ChangeBillFromOrderCommand)` plans a posted bill again against `ProgressAsync(order, except: bill)` (so accruals and the match see only the order's other bills) and changes it through `BillService.ChangeFromSourceAsync` (new source lines, holds rerun, the order closed or reopened); cancelled orders are refused. `BillPartsAsync` takes a bill apart into order picks (unit cost = amount / quantity) and extra lines (the bill's lines after those the picks plan to). The bill's Change page shows `BillFromOrderEdit` for these; API `GET|PUT /api/purchases/bills/{id}/from-order`.
- Receiving into stock (`PurchasingSettings.ReceiveIntoStock`, off by default; `PurchasingSettingsCommand.ReceiveIntoStock` null keeps it): `PurchaseOrderService.ReceiveAsync` also plans the delivery like bill item lines (`InventoryService.PlanPurchaseAsync`, the order's unit costs and warehouse; lot/serial items refused because they need numbers) and posts `Source = purchases.receipt` (`SourceId` = the delivery's `StockSourceId`, movements `InventorySources.PurchaseReceipt`): Dr each item's asset / Cr "Received Not Billed" (other current liability, created on first use). Receipt rows keep `StockSourceId`, `JournalEntryId`, `Value`; `PurchaseOrder.InStock(line)`. A bill from the order bills units already in stock as category lines: Dr "Received Not Billed" at their received value (the remainder of the line's value when it clears the line) plus the cost difference to "Purchase Price Variance" (cost of goods sold); units beyond go in as item lines. `BillSourceLine.AccruedQuantity/AccruedAmount` record this, so voiding the bill frees them. Taking a delivery back reverses its stock and entry, refused once its units are billed or its layer used. Landed costs only reach layers opened by bills. Bills ahead of deliveries (`StockedRowsAsync`): a line needs in stock from deliveries what's received less `BilledIntoStock`, so a delivery leaves out units a bill brought in, on rows of their own (`PurchaseOrder.SplitReceipt`; `InStock` false, `Value` 0), and needs no schema of its own. `PlanBillAsync` keeps such units as item lines, a bill that would drop them is refused (`EnsureDeliveriesCovered`, `purchaseorder.delivery_counted_on`, only with receiving into stock on), and so is taking back a delivery a later one counted on (`purchaseorder.receipt_counted_on`). A closed order still receives goods, and takes deliveries back; only a cancelled one refuses.
- Approvals: `PurchasingSettings` (one row; audit `purchasing_settings`): `ApprovalThreshold` (bills with total ≥ it are held), tolerance, `RequireReceipt` (default on), `AllowSelfApproval` (default off). Every bill records `EnteredBy` (the actor); `Bill.Approval` NotRequired / Pending / Approved / Rejected with `HoldReason` (one reason per line), `ApprovedBy/At`, `ApprovalNote`. Existing bills were backfilled NotRequired. `BillPaymentService.PayAsync` refuses bills that aren't `CanBePaid` (`bill.not_approved`). `BillApprovalService` approves (from Pending or Rejected) or rejects (note required); the person who entered a bill can't decide on it unless self-approval is on. Rejected bills are voided the usual way.
- ACH: `VendorBankAccount` (one per vendor; routing number checked with the ABA check digit; account number stored through `ISecretProtector`, shown as last four, excluded from the data export; changes audited on the vendor without the number). `AchSettings` per Bank account (bank routing = immediate destination and ODFI, origin, company ID/name, entry description). `AchService.CreateFileAsync` takes posted bill payments from that account to vendors with bank details, not printed as checks, not sent before and not matched or reconciled (the page leaves them unticked and shows the reference: Pay Bills fills in a check number by default, so a number can't rule one out), builds a NACHA file with `Ach.Build` (one CCD batch of credits, service class 220, codes 22/32, trace numbers ODFI + sequence, entry hash, padded with 9s to blocks of ten, CRLF), stores it encrypted on an `AchBatch` (`ProtectedContent`, read with `AchService.FileText`; older or restored files in clear are in `UnprotectedContent`, column `Content`, until the hourly job's "ACH files" step encrypts them and wipes what they left in the database; audit `ach_batch`; file ID modifier A–Z then 0–9 per account per day) and sets `BillPayment.AchBatchId`.
- Pages: `/purchases/orders`, `/purchases/orders/new`, `/purchases/orders/{id}/edit`, `/purchases/orders/{id}` (receive goods, take a receipt back, enter the bill, cancel); `/purchases/approvals` and `/purchases/approvals/settings` (accountant); `/purchases/ach` (accountant: bank details per account, payments to send, files, download at `/purchases/ach/files/{id}`); `VendorBankDetails` on vendor pages (form posts to `/purchases/ach/vendors/{id}`, accountant). `PurchaseOrderForms` renders a PO as a `SalesForm` (`PartyLabel` "VENDOR") at `/purchases/orders/{id}/pdf` and emails it (`/purchases/orders/{id}/email`, audit `Emailed` on the order; API `/api/purchases/orders/{id}/pdf|email`). Bill pages show the PO, approval and hold reasons; pay bills shows held bills unticked. Form posts in `Web/Endpoints/PurchasingEndpoints.cs`; API under `/api/purchases` (`/orders`, `/approvals`, `/ach`).

- Reordering (2026-11-03): `Item.PreferredVendorId` (any item; an inactive vendor only if it was already chosen) and `Item.ReorderQuantity` (inventory only, > 0). `ReorderService.OutlookAsync(warehouse?)` gives each active tracked item's `StockOutlook`: on hand, on open purchase orders (ordered less what came into stock: received into stock plus billed item units), on open sales orders (not invoiced yet; bundles as components), `Available`, `Projected`, `NeedsReorder` (projected ≤ reorder point) and `Suggested` (the reorder quantity, else whole units to get back above the point). `CreateOrdersAsync` makes one PO per vendor (name order, memo "Reorder") in one `IUnitOfWork` transaction. The stock status report shows these columns. Page `/purchases/reorder` (posts `pick`, `vendor:/qty:/cost:{itemId}` to the same path in `PurchasingEndpoints`); API `GET|POST /api/purchases/reorder`.

## Getting paid online (L3, slice 4)

- Online payments (`Domain/Sales/OnlinePayments.cs`): `OnlinePaymentSettings` (one row; Stripe only; secret key and webhook signing secret through `ISecretProtector`, never shown, excluded from the export and audit; deposit account (bank or other current asset, usually Undeposited Funds); `PublicUrl` for return pages; `IsReady` = enabled with all three; admin page `/settings/online-payments`, audit `online_payment_settings`). `IPaymentGateway` (Application) with `StripeGateway` (Infrastructure/Payments: Checkout Sessions over REST, form-encoded, Bearer key, amounts in cents; tests use `FakeStripe` behind it, like `FakeSimpleFinBridge`).
- `PaymentLink` per checkout (unique `SessionId`): `OnlinePaymentService.LinkForInvoiceAsync` reuses an open, unexpired link for the same balance, else creates one (success/cancel URLs `/pay/done|cancelled?invoice=`). Paid links record an ordinary `CustomerPayment` (invoice's customer, applied up to the balance, the rest as credit; reference = PaymentIntent id) with the link marked paid in the payment's own save, so repeats are ignored. Three ways in: the webhook `POST /hooks/stripe` (anonymous, `StripeSignature` HMAC check, 5-minute tolerance; `checkout.session.completed`/`async_payment_succeeded` with `payment_status=paid`, and `expired`), `CheckAsync` (button on the invoice's `OnlinePaymentPanel`), and the `/pay/done` page asking about the invoice's open links. Requests without a user act as "online payment" (`OnlinePaymentActor` sets the circuit principal). The emailed "Pay now" button goes through OpenBook when customers can reach it (`/view/{token}/pay`, a `DocumentLink`, made even for an email attaching the PDF): a Stripe session lasts a day, so a fresh one is made at the click, and paid or voided invoices say so. Without a link address it's the session's own URL. ## Fixed assets and loans (L5, slice 2)

- Domain in `Domain/Assets`. `FixedAsset` (audit `fixed_asset`): asset, accumulated depreciation and expense accounts (`Guid.Empty` in the details = "Accumulated Depreciation" / "Depreciation Expense", created by `AssetAccounts` on first use), cost, salvage, in-service date, `DepreciationMethod` (StraightLine, DecliningBalance with `DecliningPercent`, Macrs with `MacrsClass`, None), and `PriorDepreciation` through `PriorThrough` for assets bought before OpenBook. Creating one posts nothing (the purchase is a bill/expense/journal entry); one entered by mistake goes to `FixedAssetStatus.Removed` (`RemoveAsync`, refused once depreciation is posted; `PutBackAsync`), left out of runs and reports. Once depreciation is posted only name, number and description can change.
- `Depreciation.Schedule` gives one amount per calendar month from the in-service month, adding up exactly to `Base` (cost − salvage; MACRS ignores salvage) by cumulative rounding. MACRS: Pub 946 half-year tables (3–20 year), Table A-7a held for 39-year (its figures differ slightly from the fraction), mid-month formula for 27.5-year (equal to Table A-6 to three places); each tax year (calendar years) spread evenly over its months. `ScheduledThrough(asset, date)` = prior depreciation + schedule months ending after `PriorThrough` and on or before the date.
- `FixedAsset.ClassId` and `Loan.ClassId` (optional, changeable after posting; `FixedAsset.SetClass`, `LoanService.DescribeAsync(..., classId)`) go on depreciation, disposal catch-up and interest lines.
- `DepreciationRun` (`Source = assets.depreciation`, audit `depreciation_run`, owned `DepreciationRunLines`): `DepreciationService.RunAsync(through)` posts each active asset's due amount (scheduled − prior − posted) in one entry, Dr expense / Cr accumulated per asset. Only the latest posted run can be voided, and not once one of its assets is disposed.
- Disposal (`FixedAsset.DisposalSource = assets.disposal`, `SourceId` = asset): posts depreciation due through the date (kept as `DisposalDepreciation`), Dr accumulated, Dr proceeds (Bank or Other current asset), Cr asset cost, gain/loss to "Gain or Loss on Disposal of Assets" (other income). `UndoDisposalAsync` voids it.
- `Loan` (audit `loan`, owned `LoanPayments`): `LoanService.VoidAsync` takes back a loan entered by mistake with its proceeds entry, refused while payments stand (`VoidedAt`; it leaves lists, reports and the forecast); `DescribeAsync` changes name and notes at any time. Monthly, `Amortization.Payment` rounds up to the cent so the term repays it; optional proceeds entry (`Source = assets.loan`: Dr bank/asset, Cr the liability). Payments (`assets.loan_payment`, `SourceId` = loan) split interest = one month on the current balance, the rest principal; in date order; only the latest can be voided. Terms are locked once a payment exists. Interest defaults to "Interest Expense".
- Reports `fixed-assets` (as of), `depreciation-schedule` (year, by quarter), `loans`. Pages `/assets` (register, run depreciation, runs), `/assets/new`, `/assets/{id}`, `/assets/{id}/edit`, `/assets/runs/{id}`, `/loans`, `/loans/{id}` (accountant to change). Form posts in `Web/Endpoints/AssetEndpoints.cs`; API under `/api/assets` (`/depreciation`, `/loans`).

## Offline capture (L9, slice 4)

- Device side: `wwwroot/capture.html` + `capture.js`, a static page (no data in the HTML, so the service worker may cache it and serve it offline; it's in `SHELL` with `capture.js` and `/app.css`). Drafts (time, mileage, expense with optional photo, receipt photo, invoice or estimate) and the cached lists live in IndexedDB `openbook-capture`, sealed with an AES-GCM key generated non-extractable and kept in the same database. Encrypt before opening an IndexedDB transaction (a transaction closes if it awaits anything else). Each draft gets `crypto.randomUUID()`. Sync on load, on `online`, every minute and on "Send now", one tab at a time (Web Locks), in requests of at most 200 drafts and 20 MB (Kestrel stops a body at 30 MB; photos are limited to 5.5 MB, under `CaptureDraft.MaxPayload` once base64); 401 keeps drafts and asks to sign in; 410 wipes the database. The JS checks mirror the server's main rules; the server decides.
- Server side: `CaptureDevice` (per user, revoked never deleted; audit `capture_device`) and `CaptureDraft` (key = the device's id, so a resend returns the stored outcome; audit `capture_draft` naming the device). Each draft's row and what it became are one `IUnitOfWork` transaction, row first, so a send cut off, or made from two tabs, can't enter a draft twice (`RetryAsync` likewise, through `TryTakeWaitingAsync`); a refusal rolls back, then records the draft as needing attention. A draft over `MaxPayload` is kept without its photo, needing attention, and stops nothing else. An expense entered without its photo (`Error` holds the note) keeps the photo in `Payload`, since the device deletes its copy: `/capture` lists it under "Entered, with a note" with `GET /capture/drafts/{id}/photo`, and `AcknowledgeAsync` drops both. `CaptureService.SyncAsync(userId, deviceId, drafts)` enters each draft in its own DI scope through `TimeService`, `MileageService`, `BankingService` (+ `AttachmentService` for a photo), `ReceiptService`, `InvoiceService` or `EstimateService` (kinds `Invoice`/`Estimate`: customer, date, memo and item lines; a line without a rate is `AutoPrice`d, and the server numbers and taxes it, so an invoice posts on sync); a `DomainException` leaves it `NeedsAttention` with the message. Entered drafts drop their photo from the stored payload (`Compact`); `CaptureDrafts.Payload` is left out of the data export. A revoked device gets `capture.device_revoked` (410 from the API). A device records the sign-in session that registered it (`CaptureDevice.SessionId`; null through an API key), and revoking it ends that session unless it's the caller's own. The revoke form's "also sign out my other sessions" box, like the "Sign out all other sessions" button on `/account/password`, calls `AuthService.EndOtherSessionsAsync` (new security stamp, so every other cookie is refused on its next request) and re-issues the current browser's cookie. A signed-out device asks the anonymous `GET /capture/device-status/{id}` (`IsRevokedAsync`; unknown ids answer false) when it gets 401, and wipes itself if revoked. API keys aren't affected by ending sessions. `ListsAsync` gives what the forms need (workers, customers, services, active items, pay-from and expense accounts, vendors, this year's mileage rate), never balances or secrets.
- API `/api/capture` (`/devices`, `/lists`, `/sync`, `/drafts`, retry/dismiss); scope area `capture`. Page `/capture` (drafts needing attention: retry, dismiss; the user's devices: remove access); form posts are mapped in `Program.cs`.

## Desktop and Server (L13)

- One build, two installs: `OpenBook:Install` = `Desktop` or `Server` (default), else `openbook.install.json` (`{"Install": "Desktop"}`) beside the app, which the desktop package ships so its commands (`reset-password`, …) act on the desktop company too. `Web/Hosting/Installation` (singleton, read once in `Program.cs`) is the one place that knows; code says "install", never "edition" (L11's industry editions). It decides files, defaults and page wording only, never data or rules.

## Hardening (2026-11-02)

- Rate limits (`Web/Security/RateLimits.cs`, `AddOpenBookRateLimits`, `app.UseRateLimiter()` early): one global partitioned limiter, sliding one-minute windows per remote address; sign-in posts (`/login*`, `/invite/*` POST) and `/login/sso` at `OpenBook:RateLimits:SignInPerMinute` (20), anonymous links (`/portal/`, `/pay/`, `/invite/`, `/capture/device-status/`, `/hooks/`) at `LinksPerMinute` (120); 0 turns one off; everything else unlimited. 429 with Retry-After, JSON for `/api` and `/hooks`, a short page otherwise. - `SearchSelect` with `CustomerAdded`, `VendorAdded` or `ItemAdded` (the callback puts the record in the page's list) adds a "+ Add" row for people who can reach that `/…/new` page; `QuickAdd` asks only the basics and the picker chooses the result. `SalesLinesEditor` takes `OnItemAdded`. So the new-document forms draw with empty lists, and a first invoice can be finished on the form. Items made there are services or products not counted in stock (`ItemService.CreateQuickAsync`); the simple setup adds a "Services" item (`CreateStarterServiceAsync`) unless they only sell products.
- Static (server-rendered) forms get the same picker by adding `data-search` to a `<select>`/`InputSelect` (`searchselect.js`): a search box goes in front and the hidden select still carries the value, so the form works without script. An empty-value option is the "none" choice, optgroups become headings, `data-keywords` on an option is searched too. It's re-added after every enhanced load; never use it on interactive pages (use `SearchSelect`) or on multi-selects. A grid with one long list on every row gives each select only its current choice and `data-options="#id"` naming one `<datalist>`, so the page isn't rows × options long (reorder, document review); picking another then needs the script.

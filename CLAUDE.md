# OpenBook

Open-source QuickBooks alternative in .NET 10. Plan and milestones: `ROADMAP.md`.

Licence: AGPL-3.0-or-later (`LICENSE`; decided 2026-11-01, when the repository went public). Dependencies must be compatible: MIT, BSD, Apache-2.0 or similar permissive licences (bundled fonts are OFL); never add a proprietary or GPL-incompatible package. The one exception is for the tests only: axe-core's MPL-2.0 (`Deque.AxeCore.Commons`, decided 2026-11-13), listed in `$TestsOnly` in `tools/check-licences.ps1`. It never ships, and the check fails if anything under `src/` uses it.

## Commands

- Build: `dotnet build`
- Test: `dotnet test` (Domain.Tests = pure unit; Integration.Tests = migrated in-memory SQLite incl. triggers) Each run migrates once into template databases (with and without a company) that every test copies (`LedgerDatabase`), so the full SQLite suite takes about 15 minutes (measured 2026-11-13) through `tools/run-tests.ps1` (PostgreSQL about 13 at 10 at once on the test server below, 45 on an ordinary one, which flushes every write: each test copies a template database and drops it afterwards, and every drop forces a checkpoint); `MigrationTests` still migrate for real. On PostgreSQL the first template of a run drops leftover `openbook_test_*` databases this login owns (a run's own templates usually outlive it); `PostgresTests` use `openbook_pgtest_*` so they're never caught.
- Run suites with `powershell -File tools/run-tests.ps1 [-Postgres [-Server Fast|Env]] [-Filter …] [-Threads n] [-CpuPercent n]` (decided 2026-11-01): it caps the tests running at once (`xUnit.MaxParallelThreads`), because uncapped runs (xUnit's default is one test per core) froze the user's computer. Since 2026-11-13, after a blue screen at the end of a full run, it also keeps the whole run to `-CpuPercent` of the processors (default 85: 20 of the 24 threads). That covers the build (no build servers), the test host and the headless browser, and two runs at once share the same 20. The test caps are 85% of the old defaults: 5 for SQLite (a quarter of the cores) and 10 for PostgreSQL (12). Every process the run starts is kept at below-normal priority; the build's workers and the test host reset their own, so the script lowers them again every 3 s. An ordinary PostgreSQL server isn't limited; the test server is. It saves a trx file and exits 1 when a test failed (going by the trx counters as well as dotnet's exit code) or none ran, so the release workflow stops; `-Postgres` loads `.env` (`-EnvFile` from a worktree). After each run each class's time goes in `artifacts/test-times/<suite>.json`, and the integration tests start the slowest classes first (`SlowestFirst`, reading `OPENBOOK_TEST_TIMES`; `tools/test-times.json` when there's no local file, as on CI), so a run doesn't end on one long class.
- Test PostgreSQL server (2026-11-13): `-Postgres` runs on `tools/pgtest.ps1 [start|stop|status]` by default (`-Server Fast`): a server of its own in `artifacts/pgtest` on port 5433, localhost only, set up with `initdb` from the installed PostgreSQL (`PGBIN`, or the newest under `C:\Program Files\PostgreSQL`), with `fsync`, `synchronous_commit`, `full_page_writes` and autovacuum off. It holds only test databases, so it's set up afresh (new random passwords, connection string in `artifacts/pgtest/connection.txt`, never printed) whenever it isn't running, and left running for the next run. It starts within the run's processors at below-normal priority. On it the template is copied with `STRATEGY FILE_COPY` (`OPENBOOK_TEST_PG_COPY`, `LedgerDatabase.CopyStrategy`): 0.46 s against WAL_LOG's 1.23 s, while on an ordinary server FILE_COPY took 15.7 s against 4.5. `-Server Env` uses `OPENBOOK_TEST_POSTGRES` from `.env` or the environment as before. CI uses the test server too, on the runner's PostgreSQL programs.- CI (2026-11-10): `.github/workflows/tests.yml` runs on every push to master and every pull request, on Windows runners like the release: a Release build and the SQLite suite, and the integration suite on the runner's own PostgreSQL as a CREATEDB login (`run-tests.ps1 -Postgres` takes `OPENBOOK_TEST_POSTGRES` from the environment when there's no `.env`). Failed tests are listed on the run's summary page and their trx files kept 14 days. Changes only to CLAUDE.md, README, ROADMAP, `docs/dev` or `docs/admin` don't start it. It doesn't replace running both suites before pushing.
- Package licences (2026-11-11): `powershell -File tools/check-licences.ps1` (after a restore) reads every package's .nuspec, direct and transitive, and fails on a licence expression outside its permissive list, on one given only as a file or link unless listed in its `$Reviewed` (read by hand), and on PDFsharp-MigraDoc other than 6.2.4; CI and the release workflow run it. Dependabot (`.github/dependabot.yml`) opens weekly update PRs (NuGet grouped, no .NET majors, MigraDoc ignored; Actions; Docker). Contributor files: `CONTRIBUTING.md`, `SECURITY.md`, `CODE_OF_CONDUCT.md`, issue forms and the PR template in `.github`.
- Browser tests (2026-11-11): `tests/OpenBook.Integration.Tests/Browser` (Playwright 1.64.1, MIT) drive the installed Edge or Chrome headless and never download a browser (`OPENBOOK_TEST_BROWSER=0` skips them, `=chrome`/`msedge` picks one); `[BrowserFact]` tests share one collection: one app on a real port (`WebApplicationFactory.UseKestrel(0)`, a company and its owner) and one browser, a context per test, signed in through the real form. Each test fails on any script or console error and any failed request (`BrowserPage.AssertCleanAsync`). They run in the ordinary suites, on PostgreSQL too, and in CI (Windows runners have Edge). ## Layout

Domain (no EF/ASP.NET) → Application (use cases, `ILedgerStore`) → Infrastructure (EF Core; SQLite migrations) → Infrastructure.Postgres (PostgreSQL migrations only) → Api (minimal API endpoints, class library) → Web (Blazor host, maps the API).

## Ledger rules (do not bypass)

- Everything that affects balances posts through `PostingEngine` as a `JournalEntry`. No other code writes `JournalLines`.
- Money is `decimal` (or `Money`) in code and integer minor units (`AmountMinor`) in the DB. Never `double`/`float` in Domain (`ArchitectureTests` enforces).
- Posted entries are immutable. Corrections = `VoidAsync`, which posts a same-date reversal. Never delete.
- Every change writes an `AuditRecord` in the same save. A background job then chains each record to the one before by a SHA-256 hash (`AuditChain`, append-only by trigger; only `AuditChainService` writes it), which the books check works out again.
- DB triggers enforce balance-on-seal, immutability and append-only audit (overview in `SqliteLedgerTriggers`). New entries are inserted unsealed and sealed in the same transaction by `OpenBookDbContext.SaveChangesAsync`.

## Migrations (SQLite)

- Trigger SQL lives frozen inside the migration that creates it (`*_InitialLedger.Triggers.cs`, `*_ChartAndSettings.cs`). Never edit an applied migration; to change a trigger, add a migration that drops and recreates it. Add new trigger names to `SqliteLedgerTriggers.Names`.
- A new column on `JournalEntries` must be added to the `TR_JournalEntries_Immutable` condition (via a new migration). The latest copies are in `*_LedgerGaps` (2026-11-06): entries start unsealed, only 1 seals on SQLite, a line needs an unsealed entry, void details change only with the void; PostgreSQL also refuses TRUNCATE on the journal tables.
- A trigger added after the first goes in `SqliteLedgerTriggers.Names` and `AddedBy` (its migration), or older backups are refused before they can be migrated. Restore checks trigger names, not their text.
- `IX_Accounts_SiblingName` (raw SQL in both projects, on the parent and lower-case name, not in the EF model) stops two first uses making one account twice: an EF rebuild of `Accounts` would lose it.
- Never let EF rebuild `JournalEntries`, `JournalLines` or `AuditRecords` (its SQLite `DropColumn`/`AlterColumn`): the rebuild loses triggers and its table swap runs after all `Sql()` steps. Drop the triggers, use native `ALTER TABLE … DROP COLUMN` via `Sql()`, recreate the triggers. Check generated migrations for `ef_temp_`.
- Backfill non-null columns explicitly in the migration (`defaultValue`), not with model `HasDefaultValue` (EF's sentinel rule would turn `false`/`0` into the DB default).
- `MigrationTests` cover a fresh database, upgrading an M0-era file, downgrading, and upgrading files from three later milestones holding a row in every table (parents first, the ledger sealed and balanced; every row must survive, foreign keys and integrity hold, triggers present); `PostgresMigrationTests` do the last on PostgreSQL. A new starting point is one more `InlineData`. EF's own `__EF…` tables are never filled (a row in `__EFMigrationsLock` makes the next migration wait forever).
- Keep SQL provider-neutral (quoted identifiers, no SQLite-only functions) for the V1.8 PostgreSQL provider.
- Domain errors throw `DomainException` with a stable `code`; the API maps them to 400 (404 for `EntityNotFoundException`).

## Pages and services

- "Today" is `CompanyTime.Today` (Application), never `DateTime.Today`: the company's `TimeZoneId` (IANA, Windows ids converted; null = the server's, which is UTC in containers), set in Settings. `CompanyTime` is static (one company per process), refreshed at startup, on a settings save and at the start of each hourly job run. Schedules (backups, report subscriptions, bank sync, "Send later") use `CompanyTime.Zone`. Timestamps shown on pages (audit, sessions, "Changed … by", emails sent) go through `InCompanyTime()`, never `ToLocalTime()`; services take "today" from their `IClock` with `CompanyTime.TodayAt(clock.UtcNow, CompanyTime.Zone)`.
- Region (2026-11-06): `Company.Region` (null until chosen; chosen at `/setup` and in Settings, `Company.Regions` is the list `AppCulture` offers) decides how printed documents, emails and the jobs write dates, whoever opens them; screens keep each person's region. Text goes out in `CurrentCulture` down to the PDF renderer, so a service producing either holds `using var region = CompanyRegion.Use(company);` around the whole of the work (it follows awaits). A new thing that prints or sends text for someone outside needs that.
- Audit actor comes from `ICurrentUser`, which the host registers (`WebCurrentUser` covers both HTTP requests and interactive circuits).
- Pages are static server-rendered by default; use plain HTML forms with `<AntiforgeryToken />` for posts to minimal API endpoints (`Web/Endpoints`). Wrap a page's content in `<div class="wide">` for the wide layout.
- A second submit: `shortcuts.js` drops a repeat of a `method="post"` form within 5 seconds (not print forms, nor those opening a tab) and the second click of a double click on a submit button or one in `.actions` (so a save button goes in `.actions`; "Add line" buttons don't). Every interactive handler starts `if (_busy) return;`, for a click while the first is running: the render that disables the button may not have reached the browser. A handler that sets `_busy` must not be called from another that has.
- Interactive pages (`@rendermode InteractiveServer`: journal entry form, CSV import) must not inject application services directly: use `Operations.RunAsync` so each action gets a fresh scope and the right audit actor. A circuit outlives the request whose cookie was checked, so `RunAsync` checks the session each time on a circuit (`CircuitUser.InCircuit`) and refuses with `auth.session_ended` once it's over; what's already on the page stays until the person reloads. `/_blazor` is open to every role: the page's own rule was checked when it was opened.
- `FormDraft<T>` (Components; `Snapshot`, `OnRestore`, `ClearAsync` once saved) keeps a new document's typing in the tab's sessionStorage every 2 seconds, keyed by user and form, and offers it back after a lost circuit, since a circuit doesn't outlive a long sleep or a restart. On the new invoice, receipt, estimate, bill, credit memo and vendor credit forms.
- Every component inherits `OrderedComponent` (`@inherits` in `Components/_Imports.razor`; layouts `OrderedLayout`; `Every_component_of_the_app_is_ordered` checks it). `ComponentBase` renders as soon as `OnInitializedAsync` first waits, which SQLite never does because its calls finish without waiting, so on PostgreSQL a static page's components would share the request's DbContext at once and draw null data. Here a component renders once it has loaded, and in a static render the components of a request load, and handle their forms, one at a time (`RenderTurn`, per scope), so static pages can inject services and load in `OnInitializedAsync`. A status page re-executed by `UseStatusCodePagesWithReExecute` isn't waited for by the framework (its scope is disposed under a running query), so it must draw without waiting: `MainLayout` skips its query there, and "not found" shows the default menu.

## Rules for new work

The details live in the area notes below; these are the ones every area has to follow.

Pages and forms:

- Pages need sign-in by default (`Components/Pages/_Imports.razor`); mark public pages `[AllowAnonymous]`. The `/api` group answers 401 instead of redirecting (`security.md`).
- A new page or endpoint that changes the books or settings needs a rule in `AccessRules` and a case in `AccessRulesTests`; a new page prefix needs an area in `PageAreas`; a new API area's prefixes go in `ApiScopes.Areas` (`platform.md`, `security.md`).
- Link and post with `<ActionLink>` / `<PostForm>` for anything that may need more access: greyed out, never hidden on pages; menus hide links with `CanReach(href)`, forms and buttons use `CanPost(action)`; never `User.Can(role)` in components (`ui.md`, `security.md`).
- Every signed-in form post binds a form (`IFormCollection _` when it reads nothing), so the antiforgery check runs (`platform.md`).
- A button that asks first takes `data-confirm="…"`, never an inline `onclick` (`purchases.md`). Return addresses (`back`, `returnUrl`) go through `AccessRules.LocalPath` (`security.md`).
- Static forms: a multi-select with nothing chosen binds as null (`set => field = value ?? []`); numbers go through `FormNumbers` (`sales.md`). `[SupplyParameterFromQuery]` can't bind enums: take a string (`banking.md`). Never `return;` inside page markup while an element is open (`platform.md`).
- An interactive input whose text the server keeps as people type is bound (`@bind:get`/`@bind:set` with `@bind:event="oninput"`), never `value=` with `@oninput`: only a binding stops each keystroke's render writing stale text back over what was typed since (`ui.md`, Pickers).
- Pick customers, vendors, items and accounts with `SearchSelect` on interactive forms, `data-search` on static ones (`ui.md`). Interactive forms that post show `ClosedPeriodPassword` once `ClosedPeriod.NeedsPassword(ex)` (`ledger.md`).
- Edit pages of `Versioned` records check the version when they save (`IRecordVersions`), and their API route goes in `ApiVersions.Routes` (`platform.md`).
- Text goes through `@L["English text"]` with arguments in the call; regenerate the catalog with `python tools/extract-strings.py` (`platform.md`). Dark colors: keep `:root[data-theme="dark"]` and the `prefers-color-scheme` block in step (`install-and-moving-in.md`).
- Check new pages at 375px. Every control needs a name (a `<label for>`, or `aria-label` when there's no room). A column without a heading gets a `visually-hidden` one, and a second `role="search"` or `<nav>` on a page gets its own `aria-label`. `AccessibilityTests` checks all of this (`ui.md`, Accessibility). A new area gets a prefix in `HelpTopics`; a new settings page an entry on `/settings` (`ui.md`).
- Editions, the simple view and the install (desktop/server) only change what's shown: never data, rules or access (`projects-and-assets.md`, `ui.md`, `install-and-moving-in.md`).

Services and data:

- Check everything, stage (`PostingEngine.StageAsync` / `StageVoidAsync`), then change documents, and save once (`banking.md`, `sales.md`).
- Nothing that changes the books may skip its audit record (the report history cache depends on it); new audit entity types go in `Links.ForAuditEntity`; ledger lines link to documents through `Web/Components/Links.cs`; keep audit snapshots free of secrets, since webhooks send them (`ledger.md`, `platform.md`, `sales.md`).
- A new accrual document type goes in `AccrualDocuments` with a derivation (`reports.md`); a new document source in the books check (`Documents`, `ReceivableSources`, `PayableSources`, `UndepositedSources`; `ledger.md`) and a label in `ReportCatalog.DocumentType` (`reports.md`). A new search kind needs a heading in `Search.razor` and an area in `SearchAreas` (`reports.md`).
- Secrets: protect with `ISecretProtector`, name the column `Protected…` (the PostgreSQL move re-protects those), add it to `DataExporter.Excluded`; an endpoint that returns a secret goes in the idempotency `SecretPaths` (`install-and-moving-in.md`, `platform.md`).
- Records two people may change at once go in `OpenBookDbContext.Versioned` (migration in both projects). An entity with two owned collections that both grow loads with `AsSplitQuery()` (`platform.md`, `ledger.md`).
- SQLite can't `ORDER BY` a `DateTimeOffset`: order in memory; store `DateTimeOffset`s in UTC for Npgsql (`sales.md`, `platform.md`).
- Outbound calls to addresses people type in go through `Net.PublicNetwork.Handler` (`platform.md`). A new background job takes a job lease and records its runs in `JobStatus`; a new anonymous path that takes tokens or passwords goes in the rate-limit lists (`platform.md`).
- A new reader of uploaded files or of a service's answers gets a target and a sample in `Fuzz/FuzzTests.cs` and `Fuzz/Seeds.cs`; values read from them stop at `Money.MaxAmount`, so their sums and products can't overflow.
- A new record type that takes files or notes goes in `AttachmentService.EntityTypes` / `NoteService.EntityTypes`, `EfAttachmentStore.ExistsAsync` and `RecordAreas.Of` (`purchases.md`, `install-and-moving-in.md`). A new item field needs a column in the items spreadsheet (`inventory.md`). A column referring to a customer, vendor or item without a foreign key needs a name the merger knows (`lists-and-fields.md`).

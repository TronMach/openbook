# OpenBook

Open-source QuickBooks alternative in .NET 10. Plan and milestones: `ROADMAP.md`.

## Commands

- Build: `dotnet build`
- Test: `dotnet test` (Domain.Tests = pure unit; Integration.Tests = migrated in-memory SQLite incl. triggers) Each run migrates once into template databases (with and without a company) that every test copies (`LedgerDatabase`), so the full SQLite suite takes about 2½ minutes (PostgreSQL about 7: copying a template there costs about as much as migrating did); `MigrationTests` still migrate for real. On PostgreSQL the first template of a run drops leftover `openbook_test_*` databases this login owns (a run's own templates usually outlive it); `PostgresTests` use `openbook_pgtest_*` so they're never caught.
- Testing schedule (decided 2026-10-29): per milestone, build, run the tests for the area touched (`--filter`), check new pages in the browser and commit on its own. Run the full SQLite and PostgreSQL suites once per batch of 2–3 milestones and always before pushing, both at the same time (two processes), then drop the PostgreSQL leftovers (`openbook_test_*` / `openbook_pgtest_*` databases owned by `openbook_test`); if a batch run fails, rerun the failing tests at each commit to find the cause.
- Run: `dotnet run --project src/OpenBook.Web` (migrates `openbook.db` on startup; API under `/api`)
- Reset a forgotten password: `dotnet run --project src/OpenBook.Web -- reset-password [username]` (same config as the web app; prompts twice, reads lines when stdin is piped; refuses if the company file is missing rather than creating one)
- Encrypt / decrypt the SQLite company file in place (OpenBook stopped, key from `OpenBook:EncryptionKey`): `dotnet run --project src/OpenBook.Web -- encrypt-database` / `decrypt-database`
- New migration (SQLite): `dotnet ef migrations add <Name> -p src/OpenBook.Infrastructure -s src/OpenBook.Infrastructure -o Persistence/Migrations`
- New migration (PostgreSQL), every time a SQLite one is added: `dotnet ef migrations add <Name> -p src/OpenBook.Infrastructure.Postgres -s src/OpenBook.Infrastructure.Postgres -o Migrations`
- PostgreSQL tests run only with `OPENBOOK_TEST_POSTGRES` set (a server connection string allowed to create databases, e.g. `Host=localhost;Username=postgres;Password=…`); otherwise they're skipped. Add `OPENBOOK_TEST_ALL_ON_POSTGRES=1` to run the whole integration suite on PostgreSQL (each test gets its own database, dropped afterwards; `[SqliteFact]` tests such as file backups skip). Run it after schema or SQL changes. Locally, `.env` (gitignored) holds `OPENBOOK_TEST_POSTGRES` for the `openbook_test` login (CREATEDB, not a superuser; its string names `Database=postgres`, since without one PostgreSQL looks for a database named after the user) and `OPENBOOK_PG_APP` for running the app as `openbook` (owns only the `openbook` database); load it with `set -a; . ./.env; set +a` (values are quoted because of the `;`). Test connections use 120 s timeouts (a full run creates hundreds of databases at once), and `LedgerDatabase.DropPostgresDatabaseAsync` retries a drop refused with 42501: a login that isn't a superuser can't end an autovacuum worker on PostgreSQL 17.
- CLI client: `dotnet run --project src/OpenBook.Cli -- help` (or pack it as the `openbook` dotnet tool). It only talks to a running server's API with an API key (`openbook config --url … --key obk_…`, saved in `%APPDATA%/OpenBook/cli.json`; `OPENBOOK_URL` / `OPENBOOK_API_KEY` override).
- Docker: `docker build -t openbook .` (SQLite in `/data`), or `docker compose up -d` (with PostgreSQL). `/healthz` for probes.

## User guide

- `docs/user-guide/` (Markdown, 26 numbered chapters, one per area, indexed in its `README.md`; a new area gets a chapter and an index line). Written for bookkeepers, not developers: menu paths and on-screen labels exactly as the pages show them, roles where an action needs more than standard. When a change renames a label, moves a page or changes a rule a chapter describes, update the chapter in the same commit.

## Layout

Domain (no EF/ASP.NET) → Application (use cases, `ILedgerStore`) → Infrastructure (EF Core; SQLite migrations) → Infrastructure.Postgres (PostgreSQL migrations only) → Api (minimal API endpoints, class library) → Web (Blazor host, maps the API).

## Ledger rules (do not bypass)

- Everything that affects balances posts through `PostingEngine` as a `JournalEntry`. No other code writes `JournalLines`.
- Money is `decimal` (or `Money`) in code and integer minor units (`AmountMinor`) in the DB. Never `double`/`float` in Domain (`ArchitectureTests` enforces).
- Posted entries are immutable. Corrections = `VoidAsync`, which posts a same-date reversal. Never delete.
- Every change writes an `AuditRecord` in the same save.
- DB triggers enforce balance-on-seal, immutability and append-only audit (overview in `SqliteLedgerTriggers`). New entries are inserted unsealed and sealed in the same transaction by `OpenBookDbContext.SaveChangesAsync`.

## Migrations (SQLite)

- Trigger SQL lives frozen inside the migration that creates it (`*_InitialLedger.Triggers.cs`, `*_ChartAndSettings.cs`). Never edit an applied migration; to change a trigger, add a migration that drops and recreates it. Add new trigger names to `SqliteLedgerTriggers.Names`.
- A new column on `JournalEntries` must be added to the `TR_JournalEntries_Immutable` condition (via a new migration).
- Never let EF rebuild `JournalEntries`, `JournalLines` or `AuditRecords` (its SQLite `DropColumn`/`AlterColumn`): the rebuild loses triggers and its table swap runs after all `Sql()` steps. Drop the triggers, use native `ALTER TABLE … DROP COLUMN` via `Sql()`, recreate the triggers. Check generated migrations for `ef_temp_`.
- Backfill non-null columns explicitly in the migration (`defaultValue`), not with model `HasDefaultValue` (EF's sentinel rule would turn `false`/`0` into the DB default).
- `MigrationTests` cover a fresh database, upgrading an M0-era file, and downgrading.
- Keep SQL provider-neutral (quoted identifiers, no SQLite-only functions) for the V1.8 PostgreSQL provider.
- Domain errors throw `DomainException` with a stable `code`; the API maps them to 400 (404 for `EntityNotFoundException`).

## Company, sign-in, backup

- One company per database, created by `/setup` (`CompanySetupService`). Home currency comes from the `Company` row; ledger services throw `company.not_set_up` before setup. `SetupGateMiddleware` routes pages to `/setup` until then.
- Cookie auth (`Web/Security/WebSecurity.cs`). The cookie carries the user's `SecurityStamp` and its `UserSession` id (`AuthService.SessionClaim`), both checked on every request (cookies without a session claim are refused, so people sign in again). Changing a password, "Sign out all other sessions" (`POST /account/sessions/end-others`) or restoring a backup ends other sessions; the first two re-issue the current browser's cookie, which keeps its session (`RenewSessionAsync`). A session counts while not ended, on the current stamp and used within `UserSession.IdleLimit` (8 h, also the cookie's sliding expiry); last use is written at most every 5 minutes. `/account/password` lists them (device from `UserAgents.Describe`, address, times) and signs one out (`POST /account/sessions/{id}/end`); signing out ends this browser's session. `UserSessions.SecurityStamp` is left out of the data export. Pages require auth via `Components/Pages/_Imports.razor`; mark public pages `[AllowAnonymous]`. The `/api` group requires auth and returns 401 instead of redirecting.
- Audit actor comes from `ICurrentUser`, which the host registers (`WebCurrentUser` covers both HTTP requests and interactive circuits).
- Backup = SQLite online backup API → plain `.openbook.db` file. Restore validates (integrity, known migrations, triggers present, company present, ledger balanced), writes a safety copy to `backups/` next to the company file, then copies over the live DB in place. A new trigger must be added to `SqliteLedgerTriggers.Names` or restore won't check for it.
- Pages are static server-rendered by default; use plain HTML forms with `<AntiforgeryToken />` for posts to minimal API endpoints (`Web/Endpoints`). Wrap a page's content in `<div class="wide">` for the wide layout.
- Interactive pages (`@rendermode InteractiveServer`: journal entry form, CSV import) must not inject application services directly: use `Operations.RunAsync` so each action gets a fresh scope and the right audit actor.

## Chart of accounts and reporting

- `AccountType` is QuickBooks' list (Bank, AccountsReceivable, …); `AccountClass` groups them for statements. Pick the narrowest type; M2–M4 key off Bank/CreditCard/AR/AP.
- Rules spanning accounts live in `ChartOfAccounts` (subaccount = parent's type, max 5 levels, unique sibling names and numbers, no cycles, class change blocked once posted). Full names use `Parent:Child`. Accounts are deactivated, never deleted.
- CSV import (`ChartImportService`, parser in `Application/Import/Csv.cs`) matches headers loosely and is all-or-nothing. The starter chart at `Web/wwwroot/samples/chart-of-accounts.csv` is covered by a test.
- `ReportBasis` (Accrual/Cash) per report, default from company settings. `EntryBasis` on each entry (Both / AccrualOnly / CashOnly) decides inclusion. Cash basis for invoices and bills is payment-driven; see Reporting below.
- Dev preview: `.claude/launch.json` → `openbook-web` on port 5188, data in `src/OpenBook.Web/openbook.dev.db`.

## Banking (M2)

- Bank and credit card accounts are accounts of type `Bank` / `CreditCard`. Amounts in banking code are in the account's natural sign (`BankingRules.Natural`): positive = money in the bank, or owed on a card.
- `BankTransaction` is a document (Spend / Receive / Transfer, with payee and check number) that posts one journal entry with `Source = bank.*` and `SourceId` = the document id. Categories are the entry's lines. Documents are voided, never edited; the journal page refuses to void entries posted by documents.
- Services that create several entries in one save use `PostingEngine.StageAsync` / `StageVoidAsync` (internal) and save once; `NextEntryNumberAsync` counts staged entries. Mutate documents only after the staged call succeeds, so a refusal leaves nothing changed in memory.
- Reconciliation state lives in `Reconciliations` / `ReconciliationLines` referencing ledger lines; the ledger itself is never touched. One in progress per account, ticks saved as made. Voiding is blocked for any entry with a ticked or reconciled line. Voided entries and their reversals are left out of worksheets and reports.
- Statement CSV import: `BankImportService` (headers matched loosely; one signed amount column or money-out/money-in columns) with `StatementValues` for dates and amounts. It refuses to guess on ambiguous amounts ("1.005") and flags ambiguous date orders. Possible duplicates = same date, signed amount and payee as an existing posted transaction.

## Sales (M3)

- `Customer` and `Item` (products and services; `Service` or `NonInventory`, each with a default price and income account) are deactivated, never deleted. Names are unique ignoring case. Customers with unpaid invoices can't be deactivated.
- `Invoice`, `CustomerPayment` and `SalesReceipt` are documents posting one journal entry each (`Source = sales.*`), voided never edited. Lines (`SalesLine`) need an item when they have an amount; item-less lines are notes. Rates and quantities allow 4 decimals (stored as ten-thousandths); line amounts round half away from zero to the cent. `SalesLine.Postings` credits each income account with its lines' sum (debits it if a discount makes it negative).
- Invoices post to the first active A/R account; one is created and saved on first use if none exists. Payments deposit to a Bank or Other current asset account (Undeposited Funds by default when the chart has it). Invoice `AmountPaid` is everything settled (payments, early payment discounts, applied credit) and is kept in step by payment create/void and credit application. An invoice with anything applied can't be voided.
- Document services check everything before `StageAsync` and mutate documents/invoices only after staging succeeds.
- Customer and item CSV imports (`SalesImports.cs`) follow the chart import pattern (preview, all-or-nothing, existing names skipped). `CsvColumns` is the shared header matcher.
- SQLite can't `ORDER BY` a `DateTimeOffset`; order such results in memory.
- `Web/Components/Links.cs` maps a journal entry's source to its document page; use it wherever a ledger line links somewhere.

## Purchases (M4)

- `Vendor` mirrors `Customer` (plus your account number with them and a default expense category that pre-fills bills and expenses). Vendors with unpaid bills can't be deactivated.
- `Bill` lines are category lines (account, description, amount; negative = credit), not items; any active account except A/R and A/P. Bills post Dr categories / Cr the first A/P account (created and saved on first use). Bill numbers are the vendor's, unique per vendor. A bill with payments can't be voided.
- `BillPaymentService.PayAsync` takes any open bills across vendors and writes one `BillPayment` per vendor (and per A/P account) in one save, vendors in name order; numeric check numbers count up from the first. Paid from a Bank or Credit card account. The vendor's account number is the default memo.
- Expenses (paid immediately) are `BankTransaction` spends with an optional `VendorId`; the payee defaults to the vendor's name. Check-number suggestions count both expense and bill-payment references.
- `DocumentStatus` (Posted/Voided) is shared by sales and purchase documents; `Text.Optional` lives in Domain.Common.

## Reporting (M5)

- Every report reads lines from `ReportLedger.LinesAsync(basis, from, to)`, never from the store directly, so all reports agree. Accrual = ledger as posted (entry basis permitting). Cash = entries whose basis allows cash, minus everything sourced from invoices, bills, customer payments and bill payments; plus, for each posted payment in range, derived lines on the payment date: the deposit/payment account for the full amount, and the paid documents' accounts allocated in proportion to their lines (`ReportLedger.Allocate`, rounding cent on the last line). A new accrual document type must be added to `AccrualDocuments` and given a derivation.
- `FinancialReports`: P&L sections by account type; balance sheet with "Retained earnings" (net income before the fiscal year containing the as-of date; merged into a top-level, childless Equity account named "Retained Earnings" if there is one, else a computed row) and computed "Net income" (since its start); general ledger with opening and running balances in each account's natural sign. Rows link to the general ledger for drill-down.
- `TrialBalanceQuery` also runs on `ReportLedger`. `DateRanges` has the period presets (calendar month/quarter, fiscal year).
- `SearchService` searches in memory across names, numbers, references, memos and amounts (`StatementValues.TryParseAmount`), max 20 hits per kind.
- Report pages share `Components/Reports` (`ReportFilter`, `ReportQuery`, `ReportSectionRows`); they're static GET forms so every report has a shareable, printable URL.

## Ledger hardening (V1.1)

- Closing date and password live on `Company`. `PostingEngine` checks every staged entry and void against it (`EnsureOpen`): `period.closed` without a password, `period.password_required` / `period.wrong_password` with one. The password comes from the scoped `ClosedPeriodOverride` (API: `X-Closing-Password` header; interactive pages: `Operations.RunAsync(..., closingPassword)`; static forms: set it before calling the service). Each override writes an `AuditAction.ClosedPeriodOverride` record on the company. Show `ClosedPeriodPassword` on any form that posts, once `ClosedPeriod.NeedsPassword(ex)`.
- `CloseBooksService`: moving the closing date earlier, clearing it, or changing/removing the password needs the current closing password; closing more doesn't. Year-end close only moves the closing date; nothing is posted.
- Journal-sourced entries (`JournalEntry.IsJournalSource`: manual, auto-reversal, recurring, opening balance) are voided from the journal page; anything else from its document.
- `ReverseOn` posts a mirror entry (`AutoReversalSource`, `SourceId` = original). Recurring templates (`RecurringEntry`) compute each date from `StartDate` and the occurrence index, so month ends don't drift; `RecurringEntryService.PostDueAsync` saves each occurrence separately and stops a template at its first error. `RecurringPostingService` (Web) runs it hourly for auto-post templates as actor "system".
- `JournalEntryFilter` can filter by `Source`/`SourceId`; use it rather than scanning entries.
- Opening balances post against "Opening Balance Equity" (created on first use); A/R and A/P are excluded (enter open invoices/bills instead).
- Starter charts are embedded CSVs in `Application/Accounts/Templates`, imported through `ChartImportService`; each has a top-level "Retained Earnings" equity account.
- `AuditLogQuery` filters in memory and diffs top-level JSON fields (null = absent). `Links.ForAuditEntity` maps an entity type to its page; add new entity types there.
- `JournalLinesEditor` (Components/Journal) is the shared debit/credit grid; the parent owns the `JournalLineModel` list and checks it with `JournalLines`.

## Receivables (V1.3)

- Sales lines have a `SalesLineKind`: Item, Note, DiscountPercent (percent of the item lines above it) or DiscountAmount. Discount lines post to the income account "Discounts Given" (`SalesAccounts.GetOrCreateDiscountsAsync`). Build lines with `SalesLineBuilder`, never `SalesLine.FromDrafts` directly in services.
- Terms are `PaymentTerms` (due days plus optional early payment discount) from the customer, copied onto each invoice (`EarlyPaymentDiscountPercent`/`Date`). A payment application has `Amount` (money) and `Discount` (posted Dr Discounts Given); `Settled` is both.
- A `CustomerPayment` has an explicit `Amount`; what isn't applied is customer credit (`Unapplied`). Credit (credit memo balance or unapplied payment) is applied to invoices by `CreditService.ApplyAsync`, which posts nothing; applications carry `AppliedOn` dates so aging and statements work as of a past date. Applying more of the same source to the same invoice adds to the existing application (keeps the first date).
- `CreditMemo` posts the mirror of an invoice (Dr income, Cr A/R) and shares the invoice number sequence. `CustomerRefund` pays credit back (Dr A/R, Cr bank/card) from one credit memo or one payment.
- `Estimate` posts nothing; `InvoiceService` closes it when invoiced (`CreateInvoiceCommand.EstimateId`) and reopens it when that invoice is voided.
- Undeposited funds: payments, receipts, retainers and gifts in an Other current asset account are grouped by `DepositService` into a `BankDeposit` (`Source = bank.deposit`: Dr bank, Cr holding account). Deposited items can't be voided until the deposit is. Kinds outside Sales register an `IUndepositedSource` (marked and cleared in the deposit's save); `Links.ForDeposited` gives each kind's page.
- Cash basis (`ReportLedger`): credit memos and refunds are accrual documents. Payments recognize applied amounts plus discounts against the invoice lines (credit applied later counts on the payment's date), keep the unapplied part in A/R, and include the discount lines as posted. A credit memo refund reverses income on the refund date; a payment refund counts as posted.
- `ReceivablesService` computes aging and statements from the documents, not the ledger. Forms: `FormService` builds `SalesForm`/`StatementForm`, `IFormRenderer` (MigraDoc) renders them. PDFsharp-MigraDoc is pinned to `[6.2.4]`, the last MIT release (6.5+ is AGPL or commercial): never let it be upgraded. Its Core build needs `SystemFontResolver`, which maps the one family forms use ("OpenBook Sans") to a system sans-serif, or to OpenBookSans-Regular/Bold.ttf in a `fonts` folder beside the app. PDFs are served inline at `/api/sales/{kind}/{id}/pdf`.
- Email: `EmailService` with `IEmailSender` (MailKit; "folder" delivery writes .eml files to `mail/` beside the company file). The SMTP password is encrypted by the host's `ISecretProtector` (Data Protection; tests use a marker). Every send writes an `AuditAction.Emailed` record. `RecurringPostingService` also creates (and emails) automatic recurring invoices.
- Scheduled invoice emails: `ScheduledEmail` (Domain/Sales; audit `scheduled_email`, linked to `/sales/scheduled-emails`): the message fixed when scheduled, `SendAt` in UTC (later than now, within a year), Scheduled → Sent / Failed (reason kept; `RetryAsync` puts it back to go on the next run) / Cancelled; never deleted. `ScheduledEmailService.SendDueAsync` sends each due one through `EmailService.SendFormAsync` (so the PDF shows the invoice as it is then) and saves each on its own; an invoice voided since is cancelled, not sent. `ScheduledEmailHostedService` runs it every minute as "system". The invoice email form (`/sales/email/invoices/{id}`) has "Send later" with a server-time `datetime-local`; the invoice page and `/sales/scheduled-emails` list them with cancel / try again (posts in `CollectionEndpoints`). API `/api/sales/invoices/{id}/scheduled-emails` (GET, POST with `SendAt` and optional to/subject/body, defaulting to the usual draft), `/api/sales/scheduled-emails` and `/{id}/cancel|retry`.
- New audit entity types: estimate, credit_memo, refund, deposit, recurring_invoice, email_settings, form_style (a form design; all in `Links.ForAuditEntity`).

## Payables (V1.4)

- `VendorCredit` posts the mirror of a bill (Dr A/P, Cr categories) and reuses `BillLine`. `VendorCreditService.ApplyAsync` applies credit to the vendor's bills without posting (applications carry `AppliedOn`); `VendorRefund` records money the vendor pays back (Dr bank, Cr A/P). A bill's `AmountPaid` includes applied credits.
- `RecurringBill` stores bill line drafts and uses `Recurrence`; `RecurringBillService.CreateDueAsync` enters each bill through `BillService` (recorded as `Bill.RecurringBillId`). The hourly `RecurringPostingService` runs automatic ones.
- `PayablesService`: A/P aging (like A/R, from the documents) and the 1099 summary. 1099 totals are bill payments and vendor expenses dated in the calendar year, excluding card accounts (1099-K). `DefaultThreshold`: $600 through 2025, $2,000 from 2026 (later years are inflation-indexed; the report takes an override).
- Vendors have `Track1099`, `TaxId` (normalized EIN/SSN) and `Form1099Box`. The tax ID is never shown or returned in full: use `MaskedTaxId`; in `VendorDetails` a null `TaxId` keeps the saved one and "" clears it.
- Attachments (`Domain/Attachments`): metadata in `Attachments`, bytes in `AttachmentContents` (cascade delete), in the company file. The content type comes from the extension (`Attachment.AllowedTypes`: no HTML/SVG/scripts); only images and PDFs are served inline, always with `X-Content-Type-Options: nosniff` and a sandboxing CSP. Uploads go through the web form endpoint `/attachments` (antiforgery), not the cookie API. `AttachmentService.EntityTypes` lists what can take files, and `EfAttachmentStore.ExistsAsync` must know each type. Adding/removing writes `Attached`/`Detached` audit records on the owning record. Put `<Attachments EntityType=… EntityId=… />` on new detail pages.
- `BillLinesEditor`/`BillLineModel` (Components/Purchases) is the shared category grid for bills, vendor credits and recurring bills.

## Banking pro (V1.2)

- Statement files: `Ofx.Parse` (Application/Import) reads OFX/QFX/QBO, SGML or XML, with a regex tag scan (no XML parser). `BankFeedService.PreviewAsync` takes OFX or CSV; nothing posts at import.
- `BankFeedItem` is the review queue (Pending / Added / Matched / Excluded). `DedupeKey` is unique per account: `fit:<FITID>`, else a text key of date, amount, payee and reference with `#n` for the nth identical line in one file. Re-importing skips known keys.
- Add stages a `BankTransaction` through `BankingService`; Match links an existing ledger line of the same holder-view amount within 7 days; Reopen (undo) voids the transaction for an added line.
- `BankRule`: first active rule in `Priority` order whose text is in payee or memo (plus direction, amount range, account) wins. AutoAdd rules post at import; others only suggest. A vendor only goes on money-out rules.
- `ReconciliationService.UndoAsync` reopens only the latest completed reconciliation of an account, and only when none is in progress; ticks are kept.
- Checks: `CheckService` lists bank (not card) spends and bill payments; printing renders `CheckForm`s (voucher layout, absolutely positioned MigraDoc frames, `AmountInWords.ForCheck`) and sets `PrintedAt` with an audit record. Printing goes through the web form endpoint `/checks/print` (antiforgery), which binds `IFormCollection`: minimal APIs on .NET 10 can't bind a `string[]` form parameter.
- Blazor `[SupplyParameterFromQuery]` can't bind enums: take a string and `Enum.TryParse`.
- Audit entity types: bank_rule, bank_feed_item, bank_feed_import.

## Sales tax (V1.5)

- Domain in `Domain/SalesTax`: `TaxAgency` (owns a liability account: a subaccount of "Sales Tax Payable", created by `SalesTaxService` on agency creation), `TaxRate` (one agency, percent to 4 decimals, stored as ten-thousandths), `TaxCode` (1–10 rates in print order; "combined" when more than one), `SalesTaxPayment` (`Source = salestax.payment`).
- Tax lines are `SalesLine`s of kind `Tax`, appended after the other lines by `SalesLineBuilder.BuildAsync(drafts, customer, taxCodeId, date)`: one per rate of the code, even when zero, with `TaxRateId`, `Rate` = the percent charged and `IncomeAccountId` = the agency's liability account, so `SalesLine.Postings` credits it and cash-basis allocation covers it. They're never drafted: use `SalesLine.Drafts(lines)` to copy a document's lines (`ToDraft()` throws on a tax line).
- `TaxCalculator` is the one place for the math (the web preview calls it too): taxable amount = taxable item lines less each discount's taxable share; tax = taxable × combined percent rounded once, split by rate with the remainder on the last.
- Command `TaxCodeId`: null takes the customer's code, `Guid.Empty` charges no tax. Documents store `TaxCodeId` and `TaxExemption` (the customer's exemption text when valid on the document date; tax lines are then zero). Recurring invoices use the customer's code; estimates pass theirs to the invoice.
- Line `Taxable` defaults from the item (`Item.Taxable`; existing items were backfilled taxable); `SalesLineDraft.Taxable` null means "the item's setting".
- Inactive codes, rates and agencies can't be charged (`tax.code_inactive`, …); a rate in an active code and an agency with active rates can't be deactivated.
- `SalesTaxReports.LiabilityAsync` works from the documents (accrual): invoices and receipts plus credit memos negated, each counted on every rate of its code; owed figures are the liability accounts' ledger balances. `FilingPeriods.LastCompleted` gives the period to file.
- `FormService.TaxTotals` gives the subtotal/tax rows for screens and PDFs; tax lines never show as ordinary lines.
- Audit entity types: tax_agency, tax_rate, tax_code, sales_tax_payment (attachments allowed on sales_tax_payment and now shown on customers, for certificates).

## Reports, budgets, tax lines (V1.7)

- Every report is a `ReportDefinition` in `ReportCatalog.All` (key, inputs, group) and runs through `ReportCatalog.RunAsync(key, ReportParameters)` to a `ReportTable` (columns with a `ColumnFormat`, rows with depth/style, cells with optional `ReportLink`). The screen (`ReportTableView`), CSV (`ReportCsv`), Excel and PDF (`IReportExporter`: ClosedXML, MigraDoc) all render that table, so exports match the screen. A new report = a definition + a case in `RunAsync`; it gets the generic page `/reports/{key}`, exports and saving for free. Query parameter names are the pages' own (`preset/from/to/basis/asOf/compare/accountId/year/threshold/detail/budgetId/fromMonth/toMonth`).
- Charts on the generic report page: `ReportCharts.Pick(key, table)` (Web/Components/Reports) is opt-in by key: income against expenses per amount column (not "Total") for multi-column P&L, by class and by location; the ten largest positive rows for sales by customer / item, expenses by vendor, giving by donor. `ReportChart` draws it as SVG with the dashboard's `.chart` styles and series colors (legend only for two series, `<title>` tooltips); the table below stays the record.
- Dedicated pages (trial balance, GL, journal, aging, 1099, sales tax) keep their markup and add `<ReportActions Key=…/>` for export/save. Literal `/reports/...` routes win over `/reports/{Key}`.
- Comparisons: `Comparisons.Columns` (previous period, previous year, months, quarters; max 24 columns). Multi-column statements build each column with `FinancialReports.BuildProfitAndLoss/BuildBalanceSheet` and a shared `show` set so every column has the same rows; `StatementTables` zips them and adds `DerivedColumn`s ($ change, %, total).
- Cash flow (indirect): cash = Bank accounts; operating = net income + current assets/liabilities (incl. A/R, A/P, cards); investing = fixed/other assets; financing = long-term liabilities and equity. Net change always equals the bank balance change.
- Sales by customer and expenses by vendor read `ReportLedger` (so they tie to the P&L on either basis) and attribute lines by `Source`/`SourceId` to the document's customer/vendor. Sales by item is document-based (accrual).
- `Budget` (Domain/Reporting): monthly amounts (natural sign, P&L accounts only) for one fiscal year; owned `BudgetLines`; deletable (audit `Deleted`). `SavedReport` stores report key + query string (presets stay relative); saving under an existing name updates it. Audit types `budget`, `saved_report`.
- Tax lines: `TaxLines` catalog per `TaxForm` (from `BusinessType`), keys stored in `Account.TaxLineKey` (P&L accounts only; cleared on a change to a balance sheet type). Unmapped subaccounts use the nearest parent's line in `StatementReports.TaxSummaryAsync`. Keys are stable; relabel lines for new form years, never rekey.
- Grid forms (budget amounts, tax line mapping) and save/delete of saved reports post to `Web/Endpoints/ReportEndpoints.cs` binding `IFormCollection`.

## Inventory (V1.6)

- `ItemType.Inventory` items carry `InventoryAssetAccountId` (other current asset), `CostAccountId` (expense class, usually COGS), `ReorderPoint` and `PurchaseCost`. `ItemService` fills missing accounts with "Inventory Asset" / "Cost of Goods Sold" (`InventoryAccounts`, created on first use; "Inventory Shrinkage" is the default adjustment account). Once an item has movements its type and asset account are locked.
- Stock is an append-only ledger of `InventoryMovement`s (Domain/Inventory). A receipt is its own FIFO layer (`LayerId == Id`); issues and reversals point at a layer. `Fifo.Layers` derives remaining quantity/cost; `Fifo.Take` uses the oldest layers received on or before the date, proportional cost rounded to the cent with the last of a layer taking exactly what's left. Stock can't go negative (`inventory.insufficient`).
- Documents move stock through `InventoryService` in three steps: plan (checks everything: `PlanSaleAsync`, `PlanReturnAsync`, `PlanPurchaseAsync`, `PlanReversalAsync`), stage the entry with the plan's postings appended, then `Apply`. Sales post Dr COGS / Cr inventory asset in their own entry; credit memos restock at the latest sale's average unit cost (else average on hand, else purchase cost). Voids add opposite movements on the document date and are refused once a layer the document opened has been used (`inventory.layer_used`). `InventorySources` names the document types (audit entity types).
- Bills take item lines (`BillLineDraft.ItemId`/`Quantity`): the line posts to the item's asset account and opens a layer at the line amount. Vendor credits and recurring bills refuse item lines. `BillLinesEditor` shows item columns when given `Items` (bills only).
- `InventoryAdjustment` (`Source = inventory.adjustment`, audit `inventory_adjustment`, attachments allowed): increases at a unit cost, decreases at FIFO cost; value change against the adjustment account (Opening Balance Equity for starting stock).
- Cash basis keeps the inventory cost lines of invoices and credit memos as posted (`ReportLedger`): COGS is recognized when stock is sold.
- `EfInventoryStore.ListMovementsAsync` includes unsaved added movements, so several documents in one save see each other's stock.
- Reports: `inventory-valuation` (as of a date, summary or layers, with a tie-out row to the asset accounts) and `inventory-stock` (reorder status) in `ReportCatalog`, built by `InventoryReports`.

## Advanced pricing (L12)

- Domain in `Domain/Pricing/Pricing.cs`: `PriceLevel` (a customer's baseline: `FixedPercent` on every item, or `PerItem` prices; `Customer.PriceLevelId`), `PriceRule` (promotions and exceptions: items (none = all), all customers / chosen customers / chosen levels, date range, quantity range, `Percent`/`Amount`/`SetPrice`, priority, exclusive, optional rounding; targets are owned `PriceRuleTarget`s), `QuantityBreak`s owned by `Item` (percent off or unit price from a quantity), `Company.PriceRounding` (default Cent). ## Segments (L1)

- Domain in `Domain/Segments/Segment.cs`: one `Segment` entity for classes (per line), locations (per transaction; `Company.LocationLabel` renames them, e.g. "Department") and tags (per entry, flat). Classes and locations nest (full names "Parent:Child", max 5 levels, unique among siblings, rules in `SegmentRules`); deactivated, never deleted. `Company.TrackClasses` / `TrackLocations` only show or hide the form fields.
- Segments live beside the ledger, never in it: `LineSegments` (one row per journal line with a class or location) and `EntryTags`. Posted lines stay immutable and their triggers untouched, while segments can be reclassified. `JournalLineDraft.ClassId` and `PostJournalEntryCommand.LocationId` / `TagIds` are written by `PostingEngine.StageAsync` (validated: right kind, active); voids and auto-reversals copy them, so reports by segment net to zero.

Budgets can be for a class and/or location (budget vs. actual and prior-year seeding filter by it). Tag filters on cash basis use the payment's entry tags.
- Web: `SegmentOptions.LoadAsync` (interactive forms, through `Operations`), `ClassSelect` and `LocationField`; the line editors take `Classes` (null hides the column). `<EntryTags EntryId=…/>` on detail pages, `<SegmentFilterFields>` on report filters. Audit entity type `segment`.
- Recurring templates (journal, invoice, bill) store a class per line, a `LocationId` and tags (`Tags`: comma-separated ids as text, at most `Recurrence.MaxTags`; `TagIds` parses them), checked when saved (`PostingEngine.EnsureSegmentsAsync`) and passed to every entry or document they make. ## Migration and scheduled backups (L8)

- Moving in from another program goes through one pipeline (`Application/Import/Migration`): a reader turns the export into `MigrationData` (accounts, customers, vendors, items, transactions in OpenBook's terms), and `MigrationImportService` previews it against the books and imports it all-or-nothing in one `IUnitOfWork` transaction (the old IIF importer's rules: existing names are left alone, transactions become `ledger.import` journal entries, one batch per file). `MigrationReaders.Read(source, bytes, homeCurrency)` picks the reader. Readers never touch the database; accounts named "#1234" are resolved by account number in the planner.
- Readers: `IifImportService.Read` (QuickBooks Desktop IIF; the service is now a thin wrapper), `QbxmlReader` (QuickBooks Desktop SDK responses: accounts, customers, vendors, items, journal entries; jobs and other transactions are reported, not imported), `QuickBooksOnlineReader` (QBO API query JSON; journal lines resolve accounts by id), `GnuCashReader` (XML book, gzip or not; split values are fractions; an account whose type differs from its parent's starts a new top-level branch because OpenBook subaccounts share their parent's type; other currencies are refused), `XeroReader` (chart, contacts or manual journal CSV, recognized by columns), `WaveReader` (accounting transactions CSV) and `FreshBooksReader` (clients CSV). XML is loaded with DTDs prohibited and no resolver; elements are matched by local name with `Named`/`Child`/`Text` (don't call `XDocument.Descendants(string)`, which needs the namespace).
- Page `/import/migrate` (also `/import/quickbooks`, accountant) and `POST /api/import/migrate/{source}` with the raw file as the body (`?dryRun=true` previews). No live QuickBooks Online OAuth connection: the API JSON is saved and uploaded.
- Scheduled backups: `BackupSchedule` (singleton row: daily or weekly at an hour in server time, folder or S3-compatible destination, keep N; the secret key protected by `ISecretProtector` and left out of the data export and audit) and `ScheduledBackupService` (settings, `RunDueAsync`, `RunNowAsync`; outcome kept on the schedule). A run is due when nothing has run since the latest slot, so the first one runs right away. Targets are `IBackupTarget`s in `Infrastructure/Backups`: `FolderBackupTarget` (write then rename) and `S3BackupTarget` (path-style requests signed by `AwsSignatureV4`, tested against the AWS example). Only files named `openbook-scheduled-*` are ever deleted. `ScheduledBackupHostedService` checks every 15 minutes. SQLite only, like manual backups. UI on `/backup` (admin), API `/api/backup/schedule`. Audit entity type `backup_schedule`.

## Inventory costing (L4, slice 2)

- `Item.CostMethod` (`InventoryCostMethod.Fifo` / `Average`, tracked items only, locked once stock has moved). Every stock issue goes through `Costing.Take(item, movements, quantity, date)`: quantity still comes out of FIFO layers (so availability and void checks are unchanged), but average items cost the take at the average on hand on the date (rounded once, spread over the layers; taking everything takes its whole value). Layer costs of average items aren't meaningful one by one; the valuation detail shows one "Weighted average" row for them.
- `ItemType.Bundle` (kit) and `ItemType.Assembly`; `Item.IsInventory` (= `Item.IsTracked(type)`) is true for inventory products and assemblies. Both have `Components` (`ItemComponent`, owned table `ItemComponents`), set with `ItemService.SetComponentsAsync`: bundles take any non-bundle item; assemblies take tracked items only, no cycles. A component's type can't change in a way its parent forbids.
- Bundles sell as one sales line (their own price and income account); `InventoryService.ItemQuantitiesAsync` expands them into tracked components (line quantity × component quantity) for sales, returns and voids, costing to each component's accounts.
- `AssemblyBuild` (`Source = inventory.build`, audit `assembly_build`): `AssemblyBuildService` issues the bill of materials × quantity at each component's cost and receives one layer of the assembly at the total (Dr assembly asset, Cr component assets). Void = unbuild, refused once the built layer has been used. `PreviewAsync` gives needs, on hand and the most buildable.
- `LandedCost` (`Source = inventory.landed_cost`, audit `landed_cost`): spreads an amount from an account (default "Landed Cost Clearing", other current asset, created on first use; never bank, card, A/R or A/P) over the receipts of chosen posted bills, by value or quantity (`LandedCost.Allocate`, last line takes the rounding; receipts ordered by item then id). Each share splits by the layer's remaining quantity: that part becomes an `InventoryMovement.CostAdjustment` (quantity 0) on the layer and Dr the item's asset; the rest Dr its cost of goods sold (stock built into assemblies counts as gone, too). A bill under a landed cost can't be voided; a landed cost can't be voided once its layers have moved since.
- Pending builds (`PendingBuild`, audit `pending_build`): a build saved to finish later posts nothing and holds no stock. `AssemblyBuildService`: `SavePendingAsync`, `BuildWhatYouCanAsync` (builds the most whole units the warehouse allows, the rest pending, one save; output lots are for the built part), `FinishPendingAsync` (an ordinary build on the finish date), `CancelPendingAsync`, `ListPendingAsync` (with today's preview). The build page posts `Input.Mode` = build / partial / pending / finish; `?pending={id}` finishes one. Builds are planned by `InventoryService.PlanBuildAsync`, which also serves auto-builds.
- `Item.AutoBuild` (assemblies without lot or serial tracking): `PlanSaleAsync` builds a sale's shortfall in the warehouse from components inside the sale's own entry (Dr assembly asset, Cr components) before taking the sale; the build's movements belong to the sale, so voiding it undoes both. Receipts planned before a document exists are made with a placeholder source and re-sourced with `InventoryMovement.ForSource` (same id). `PlanReversalAsync` counts a layer as used only when movements from other documents (not voided again) touch it.
- Pages `/inventory/builds/new` (preview by query string, then an `EditForm`), `/inventory/builds/{id}`, `/inventory/landed-costs/new`, `/inventory/landed-costs/{id}`; components grid on the item page posts to `/items/{id}/components` (`Web/Endpoints/InventoryEndpoints.cs`). API under `/api/inventory` (`/items/{id}/components`, `/builds`, `/landed-costs`).

## Stock tracking (L4, slice 3)

- Places: `Warehouse` (one `IsDefault`, "Main", created on first use by `WarehouseService.DefaultAsync`) and `Bin` (in a warehouse). Documents and movements store the default warehouse as **null** (`Warehouse.Key`), so pre-warehouse data needs no backfill; `StockPlace(WarehouseId, BinId)` is a place. `WarehouseService.CheckAsync` turns a chosen id or place into the stored form (active, bin in that warehouse). Deactivated, never deleted; the default can't be.
- `InventoryMovement` carries `WarehouseId`, `BinId` and `Lot` (set on the receipt, copied onto everything that moves it). Costing is still per item across places: `Fifo.Slices` splits each layer by place, and `Fifo.Take(movements, quantity, date, name, StockFilter)` takes from slices the filter allows (`StockFilter.In(warehouse)` = any bin; `At(place)` = exactly that bin or no bin; `.WithLot`). `Costing.Take` passes the filter. Plans that take an item more than once use `InventoryService.TakeAndSimulate` so later takes see earlier ones.
- Invoices, sales receipts, credit memos and bills have `WarehouseId` (commands take `WarehouseId`; `WarehouseField` on the forms, shown once there are two warehouses). Sales take from any bin of the warehouse; receipts arrive outside bins. Adjustment lines take a place (`StockPlaces` lists warehouses and bins for static forms) and lots; builds take a warehouse (components and output) and output lots.
- `StockTransfer` (audit `stock_transfer`, `InventorySources.Transfer`) moves stock between places on the same layers (`InventoryMovement.Transfer`: −q at the source, +q at the destination, cost 0); posts nothing. Void refused once the moved stock has left the destination. A bill/receipt void is refused once its layer has moved anywhere (`PlanReversalAsync` checks the receipt's place too).
- Lots and serials: `Item.Tracking` (`ItemTracking.None/Lot/Serial`, tracked items only, locked once stock has moved). `LotText` parses "A-1 x 3; B-2 x 2" (one lot alone = the whole line) and serials "S1, S2" (whole units, one each) and formats them back. Each lot or serial is its own receipt layer (cost split by quantity, `InventoryService.Split`). Receipts must name them (`lot.required`); a serial can't be received while in stock. Sales take the lots named on the line, else the oldest; the lots actually used are saved on `SalesLine.Lots` / `BillLine.Lots` (`RecordLots`) and shown on screens and PDFs. Bundle components always take the oldest. `InventoryService.LotHistoryAsync` and the inventory page's lookup trace a lot or serial.
- Lot expiry: `LotDetail` (item + lot, `ExpiresOn`), set on the item page or `InventoryService.SetLotExpiryAsync` (lot-tracked items, existing lots). Automatic picks go through `InventoryService.ForPickingAsync`, which adds the expiries to the `StockFilter`: soonest expiry first, expired lots skipped (a named lot is still taken). `ExpiringAsync` lists lots on hand expiring by a date (inventory page: next 30 days).
- Landed costs follow stock into assemblies: the share for a layer's quantity issued to (unvoided) builds goes to the build's assembly layers by quantity, split again into on hand (cost adjustment) and sold (the assembly's cost of goods sold); only what was sold or adjusted goes to the component's cost of goods sold. One level deep.
- Labels: `Code128` (Application/Inventory/Labels.cs: set C for even digit runs of 4+, else set B; `Modules` gives bar/space widths) and `LabelService` → `ILabelRenderer` (`LabelRenderer`, PDFsharp, Letter 3 × 10 of 2⅝" × 1"). Page `/inventory/labels` posts to `/inventory/labels` (PDF). Don't name a page `Labels.razor`: its class hides the `Labels` helper.
- Reports: `ReportInputs.Warehouse` (`warehouseId`, a warehouse's id) limits `inventory-valuation` (detail by bin and lot; no tie-out row) and `inventory-stock` to one warehouse.
- Barcodes: `Item.Barcode` (unique ignoring case, plain printable, ≤ 50) is a picker keyword, so scanning into an item `SearchSelect` and pressing Enter picks it; `ItemService.FindByBarcodeAsync`, API `/api/inventory/items/barcode/{code}`.
- Pages `/inventory/warehouses` (form posts in `InventoryEndpoints`), `/inventory/transfers/new`, `/inventory/transfers/{id}`; stock by place and lot on item pages. API under `/api/inventory` (`/warehouses`, `/bins`, `/stock/places`, `/lots/{lot}`, `/transfers`). Audit types `warehouse`, `stock_transfer`.

## Collections (L3, slice 1)

- Sub-customers: `Customer.ParentId` (rules in `CustomerTree`: max 5 levels, no cycles, full names "Parent:Child", `Ordered` for tree order; names stay unique across all customers). `CustomerService.CheckParentAsync` refuses inactive new parents, cycles and too-deep moves (counting the levels below the customer); a parent with active sub-customers can't be deactivated, nor a sub-customer reactivated under an inactive parent. `BillWithParent`: `CustomerTree.BillTo` walks up to who's billed; the parent's payments and credits can settle billed sub-customers' invoices (`PaymentService.BilledAsync`, used by payments and `CreditService.ApplyAsync`), its statement includes them (a billed sub-customer's statement is the parent's), and reminders go to the parent. A/R aging still lists each customer's own invoices, in tree order; settlements count from any payer.
- Bad debt: `BadDebtWriteOff` (`Source = sales.write_off`, audit `write_off`, attachments allowed) per invoice: Dr "Bad Debts" (expense, created on first use) or a chosen expense/other expense account, Cr the invoice's A/R; settles the invoice through `AmountPaid`, so the invoice can't be voided while it stands. `WriteOffService.WriteOffAsync` takes several invoices in one save (one entry each); void puts the balance back. Aging and statements count write-offs by date. Cash basis drops them entirely (in `AccrualDocuments` with no derivation: the unpaid income was never recognized). Sales tax on written-off invoices stays owed.
- `CollectionSettings` (one row, everything off until saved; audit `collection_settings` on the company): late fees (percent of the overdue balance to 4 decimals + flat amount, grace days, repeat every N days or once, automatic or not) and reminders (schedule of days from the due date, -90..365, at most 6; subject/body templates with `{customer} {invoice} {balance} {due} {days} {when} {company}`, filled by `CollectionSettings.Fill`).
- Late fees: `LateFeeService.DueAsync(today)` lists open invoices (not fees themselves) past `due + grace` whose last fee is older than the repeat period; customers with `NoLateFees` or inactive are skipped. `ChargeAsync` makes one invoice per fee through `InvoiceService` (internal `lateFeeFor` sets `Invoice.LateFeeForInvoiceId`), due on receipt, untaxed, for the "Late Fee" service item (income "Late Fee Income", other income; both created on the first charge and remembered on the settings).
- Reminders: `InvoiceReminder` rows (unique per invoice and step). `ReminderService.DueAsync` picks, per open invoice, the latest step reached that's on or after the invoice date and later than any sent, so a missed step is skipped rather than sent late; `SendAsync` emails the invoice PDF through `EmailService.SendFormAsync`, records each send on its own and keeps going after a failure (stops on email not configured).
- `RecurringPostingService` also charges late fees and sends reminders hourly when they're set to be automatic. Pages `/sales/collections` (what's due today, with ticked rows), `/sales/collections/settings` (accountant), `/sales/write-offs/new` (overdue by N days, or `?invoice=`), `/sales/write-offs/{id}`; customer pages add the parent picker, "bill with parent", no reminders, no late fees and a sub-customer list. Form posts in `Web/Endpoints/CollectionEndpoints.cs`; API under `/api/sales` (`/write-offs`, `/collections/settings`, `/late-fees`, `/reminders`).

## Sales flow (L3, slice 2)

- Partial invoicing (`Domain/Sales/SalesOrder.cs`, `PartialInvoicing`): an invoice made from a sales order or estimate records `Invoice.SourceLines` (owned `InvoiceSourceLines`: source line number + quantity) and `SalesOrderId` (estimates use the existing `EstimateId`). What's invoiced is summed from the source's posted invoices, so voiding an invoice frees its quantities with nothing to undo. Item lines bill by quantity (`ByPercent` scales every item line, 4 decimals, capped at what's left); an amount discount goes whole on the first invoice that bills an item (tracked as quantity 1); percent discounts and notes go on every invoice; tax is recalculated each time. Lines keep the source's price (`ToDraft`, no repricing); lots are kept only when the whole line is billed. `InvoiceService.CreateAsync(..., source: InvoiceSource)` closes the order/estimate when `Completes`; voiding reopens a closed one.
- `SalesOrder` (audit `sales_order`, attachments allowed): posts nothing, holds no stock, own number sequence, customer PO number (copied into the invoice memo as "Your PO …"), warehouse. Open → Closed (all invoiced) or Cancelled (`CancelAsync` stops the rest). Editable only until the first invoice. `SalesOrderService.InvoiceAsync(id, InvoiceFromSourceCommand)`: chosen `Lines`, a `Percent`, or (neither) everything left.
- Progress invoicing: `EstimateService.ProgressInvoiceAsync` (same command); `ConvertToInvoiceAsync` now invoices what's left. An estimate can't be edited after its first progress invoice (`estimate.invoiced`) and closes when fully invoiced. Old estimates invoiced whole have invoices without source lines; they're already closed.
- Retainers (`Retainer`, audit `retainer`, attachments allowed): received into a Bank account or Undeposited Funds (then Make deposit), Dr bank / Cr "Customer Deposits" (other current liability, created on first use), `Source = sales.retainer`. Applications (`sales.retainer_application`, owned `RetainerApplications`, own entry Dr deposits / Cr A/R, settle the invoice via `AmountPaid`; the retainer's customer or a sub-customer billed with it) and refunds (`sales.retainer_refund`, owned `RetainerRefunds`, Dr deposits / Cr bank or card) can each be voided (reversal entry, `IsVoided`); `SourceId` is the retainer for all three. Aging and statements count applications by `AppliedOn`. Cash basis: receipts and refunds as posted; applications are in `AccrualDocuments` and derived as Dr deposits / Cr the invoice's income lines (like a payment).
- Billable expenses (`BillableExpense`, audit `billable_expense`): a category line of a posted bill (`BillLine.LineNumber`, no item, cost > 0) or expense (a debit line of the spend's journal entry other than the bank), marked after posting with a customer and markup (`BillableExpenseService.MarkAsync`; unique per document and line; removable until invoiced, audited `Deleted`). `CreateInvoiceCommand.BillableExpenseIds` adds them as "Billable Expenses" lines (service item, income "Billable Expense Income", untaxed, price source "Billable expense"; created on first use) and sets `InvoiceId`; voiding the invoice clears it. `BillService.VoidAsync` / `BankingService.VoidAsync` call `BillableExpenseService.ReleaseAsync` first: refused if a cost is invoiced, else the marks are removed.
- Pages: `/sales/orders`, `/sales/orders/new`, `/sales/orders/{id}/edit`, `/sales/orders/{id}`; estimates' "Turn into an invoice" is the shared `PartialInvoiceForm` (Components/Sales; posts `mode` rest/percent/lines, `percent`, `qty:{line}`); `/sales/retainers`, `/sales/retainers/new`, `/sales/retainers/{id}`; `/sales/billable`; `BillableLinesPanel` on bill and expense pages; the new invoice form lists the customer's open billable expenses to tick. Form posts in `Web/Endpoints/SalesFlowEndpoints.cs`; API under `/api/sales` (`/orders`, `/estimates/{id}/progress(-invoice)`, `/retainers`, `/billable-expenses`). `PriceNote` hides the list price when the item has none (0).

## Purchasing controls (L3, slice 3)

- `PurchaseOrder` (Domain/Purchases/PurchaseOrder.cs; audit `purchase_order`, attachments allowed; own number sequence): owned `PurchaseOrderLines` (an inventory item, not an assembly, with quantity and unit cost to 4 decimals; or a category line with an amount) and `PurchaseOrderReceipts` (rows per line grouped by `ReceiptNumber`, voidable). Posts nothing; receiving posts nothing either (stock enters the books with the bill). Open → Closed (everything billed) / Cancelled; editable until anything is received or billed.
- Bills from a PO: `PurchaseOrderService.CreateBillAsync(id, BillFromOrderCommand)`; lines given (quantity + the vendor's unit cost, or a category amount) or, by default, what's received and not billed (everything left when nothing is received). The bill records `PurchaseOrderId` and owned `BillSourceLines` (line, quantity, amount); billed totals come from posted bills, so voiding frees them and reopens a closed PO. 3-way match differences (billed more than ordered; more than received when `RequireReceipt`; unit cost, or a category line's running total, over the order beyond `PriceTolerancePercent`) go to `BillService.CreateAsync(..., BillSource)` as hold reasons.
- Receiving into stock (`PurchasingSettings.ReceiveIntoStock`, off by default; `PurchasingSettingsCommand.ReceiveIntoStock` null keeps it): `PurchaseOrderService.ReceiveAsync` also plans the delivery like bill item lines (`InventoryService.PlanPurchaseAsync`, the order's unit costs and warehouse; lot/serial items refused because they need numbers) and posts `Source = purchases.receipt` (`SourceId` = the delivery's `StockSourceId`, movements `InventorySources.PurchaseReceipt`): Dr each item's asset / Cr "Received Not Billed" (other current liability, created on first use). Receipt rows keep `StockSourceId`, `JournalEntryId`, `Value`; `PurchaseOrder.InStock(line)`. A bill from the order bills units already in stock as category lines: Dr "Received Not Billed" at their received value (the remainder of the line's value when it clears the line) plus the cost difference to "Purchase Price Variance" (cost of goods sold); units beyond go in as item lines. `BillSourceLine.AccruedQuantity/AccruedAmount` record this, so voiding the bill frees them. Taking a delivery back reverses its stock and entry, refused once its units are billed or its layer used. Landed costs only reach layers opened by bills.
- Approvals: `PurchasingSettings` (one row; audit `purchasing_settings`): `ApprovalThreshold` (bills with total ≥ it are held), tolerance, `RequireReceipt` (default on), `AllowSelfApproval` (default off). Every bill records `EnteredBy` (the actor); `Bill.Approval` NotRequired / Pending / Approved / Rejected with `HoldReason` (one reason per line), `ApprovedBy/At`, `ApprovalNote`. Existing bills were backfilled NotRequired. `BillPaymentService.PayAsync` refuses bills that aren't `CanBePaid` (`bill.not_approved`). `BillApprovalService` approves (from Pending or Rejected) or rejects (note required); the person who entered a bill can't decide on it unless self-approval is on. Rejected bills are voided the usual way.
- ACH: `VendorBankAccount` (one per vendor; routing number checked with the ABA check digit; account number stored through `ISecretProtector`, shown as last four, excluded from the data export; changes audited on the vendor without the number). `AchSettings` per Bank account (bank routing = immediate destination and ODFI, origin, company ID/name, entry description). `AchService.CreateFileAsync` takes posted bill payments from that account to vendors with bank details, not printed as checks and not sent before, builds a NACHA file with `Ach.Build` (one CCD batch of credits, service class 220, codes 22/32, trace numbers ODFI + sequence, entry hash, padded with 9s to blocks of ten, CRLF), stores it on an `AchBatch` (audit `ach_batch`; file ID modifier A–Z then 0–9 per account per day) and sets `BillPayment.AchBatchId`.
- Pages: `/purchases/orders`, `/purchases/orders/new`, `/purchases/orders/{id}/edit`, `/purchases/orders/{id}` (receive goods, take a receipt back, enter the bill, cancel); `/purchases/approvals` and `/purchases/approvals/settings` (accountant); `/purchases/ach` (accountant: bank details per account, payments to send, files, download at `/purchases/ach/files/{id}`); `VendorBankDetails` on vendor pages (form posts to `/purchases/ach/vendors/{id}`, accountant). `PurchaseOrderForms` renders a PO as a `SalesForm` (`PartyLabel` "VENDOR") at `/purchases/orders/{id}/pdf` and emails it (`/purchases/orders/{id}/email`, audit `Emailed` on the order; API `/api/purchases/orders/{id}/pdf|email`). Bill pages show the PO, approval and hold reasons; pay bills shows held bills unticked. Form posts in `Web/Endpoints/PurchasingEndpoints.cs`; API under `/api/purchases` (`/orders`, `/approvals`, `/ach`).

## Getting paid online (L3, slice 4)

- Online payments (`Domain/Sales/OnlinePayments.cs`): `OnlinePaymentSettings` (one row; Stripe only; secret key and webhook signing secret through `ISecretProtector`, never shown, excluded from the export and audit; deposit account (bank or other current asset, usually Undeposited Funds); `PublicUrl` for return pages; `IsReady` = enabled with all three; admin page `/settings/online-payments`, audit `online_payment_settings`). `IPaymentGateway` (Application) with `StripeGateway` (Infrastructure/Payments: Checkout Sessions over REST, form-encoded, Bearer key, amounts in cents; tests use `FakeStripe` behind it, like `FakeSimpleFinBridge`).
- `PaymentLink` per checkout (unique `SessionId`): `OnlinePaymentService.LinkForInvoiceAsync` reuses an open, unexpired link for the same balance, else creates one (success/cancel URLs `/pay/done|cancelled?invoice=`). Paid links record an ordinary `CustomerPayment` (invoice's customer, applied up to the balance, the rest as credit; reference = PaymentIntent id) with the link marked paid in the payment's own save, so repeats are ignored. Three ways in: the webhook `POST /hooks/stripe` (anonymous, `StripeSignature` HMAC check, 5-minute tolerance; `checkout.session.completed`/`async_payment_succeeded` with `payment_status=paid`, and `expired`), `CheckAsync` (button on the invoice's `OnlinePaymentPanel`), and the `/pay/done` page asking about the invoice's open links. - Customer portal: `PortalAccess` (token `obp_…` shown once, SHA-256 hash stored and excluded from the export, `Hint`, revoked not deleted, last use at most once a minute). `CustomerPortalService`: links per customer (`PortalLinks` on the customer page, created by a form handled in the component; revoke posts to `/customers/{id}/portal/{accessId}/revoke`), `ViewAsync` (open invoices, paid ones of the last year, a 90-day statement; a billed sub-customer sees its parent's account), `InvoiceForAsync` (only invoices of the customer or those billed to it). Pages `/portal/{token}` and `/pay/done|cancelled` are `[AllowAnonymous]` with `PortalLayout` (no app navigation); `/portal/{token}/invoices/{id}/pdf` and `/portal/{token}/invoices/{id}/pay` are anonymous endpoints. `AccessRules` lets any role through `/portal`, `/pay/`, `/hooks`.
- Receipt capture (`Domain/Purchases/ReceiptCapture.cs`, audit `receipt`): `ReceiptService.UploadAsync` checks the file like an attachment first, saves a `ReceiptCapture`, attaches the file (entity type `receipt`), reads it through `IReceiptTextExtractor` (`ReceiptTextExtractor`: PDF text with PdfPig 0.1.16, Apache-2.0; text files; images only through the Tesseract CLI at `OpenBook:Ocr:TesseractPath`, registered by the host; nothing leaves the server) and fills vendor/date/total/tax with `ReceiptParser` (known vendor names win; last non-subtotal "total" line, else the largest amount). `RecordAsync` posts an expense (one split; category given or the vendor's default) and copies the file onto the bank transaction; `DismissAsync`. Pages `/purchases/receipts` (upload, multipart) and `/purchases/receipts/{id}`; API `/api/purchases/receipts` (raw body + `?fileName=`).
- Form posts and the anonymous endpoints live in `Web/Endpoints/OnlineEndpoints.cs`; API: `/api/sales/invoices/{id}/payment-links`, `/api/sales/payment-links/{id}/check`, `/api/settings/online-payments` (admin).

## Document inbox

- `CapturedDocument` (Domain/Documents; audit and attachment entity type `captured_document`; owned `CapturedDocumentLines`): a vendor invoice, customer PO, packing slip or vendor quote (`DocumentKind`; `DocumentKinds.IsFromVendor`, `HasPrices`) with the file attached, what was read (party name as printed, number, dates, `OrderReference` = our PO number on vendor documents, totals, lines with code/description/quantity/unit price/amount) and the matches (`VendorId` or `CustomerId`, `PurchaseOrderId`, each line's `ItemId`). New → Done (`ResultType`/`ResultId`, set by the later slices) or Dismissed (`Restore` puts it back). `Read` stores a reading leniently (cuts and rounds what nobody typed); `Review` checks a person's corrections strictly.
- `DocumentCaptureService.UploadAsync(kind, fileName, stream, useClaude)` checks the file like an attachment, saves it, reads it and matches it; `ReadAgainAsync` replaces the fields (and corrections). Reading: Claude when `DocumentReadingSettings.IsReady` (one row, admin page `/settings/document-reading`, audit `document_reading_settings`; API key through `ISecretProtector`, left out of the export and audit; model default `claude-opus-5-5`) and the uploader didn't untick it; on any `DocumentReadException` it falls back to the server and says why in `ReadNote`. Server: `IReceiptTextExtractor` text, then `DocumentParser` (Domain: labelled references, dates, totals, item lines from trailing numbers where quantity × price = amount; packing slips need a product code or ordered/shipped columns). `DocumentMatching`: party by name, PO by number ignoring prefixes ("PO-1004" = "1004"), items by barcode/name, PO line description, then the longest item name inside the description.
- `DocumentItemCode` (table `DocumentItemCodes`, unique per party and code): saving a review remembers the item chosen for each coded line as that vendor's or customer's code; matching tries learned codes first.
- `DocumentConversionService` (each in one `IUnitOfWork` transaction; copies the file onto the record, marks the document Done with an `Updated` audit): `MakeBillAsync` (vendor invoice; with a PO, lines with the order's items, or a category line with the same description, bill the order's lines through `PurchaseOrderService.CreateBillAsync` and everything else goes in `BillFromOrderCommand.Extra`, outside the 3-way match; without one, a plain bill: inventory items into stock, other lines to `DocumentAccounts` (per line, default, else the vendor's default category); tax and shipping become "Sales tax" / "Shipping" lines; refused when the lines, tax and shipping don't add up to the document's total), `MakeSalesOrderAsync` (customer PO; the document's prices, `AutoPrice` where there's none; their PO number as `CustomerReference`; priced lines need an item, unpriced ones without become notes), `ReceiveAsync` (packing slip; each line to the first order line with its item and something left to receive; note "Packing slip …") and `MakePurchaseOrderAsync` (quote; inventory items as item lines, the rest as category lines; memo "Quote …"). The review page's "make" panel posts to `/documents/{id}/bill|sales-order|receive|purchase-order` (closing password supported); API `POST /api/documents/{id}/bill|sales-order|receive|purchase-order`.
- `ClaudeDocumentReader` (Infrastructure/Documents, official `Anthropic` SDK, Apache-2.0): file as a PDF/image/text block, structured output against a fixed JSON schema, effort medium, server-side refusal fallback for models that take it; `Parse` maps the JSON. Tests use `FakeClaude` (registered by `LedgerDatabase`).
- Pages `/documents` (upload: multipart, kind, "Read it with Claude"; list) and `/documents/{id}` (file preview, editable fields and lines posting `desc:i/sku:i/qty:i/price:i/amount:i/item:i` + `rows`, read again, dismiss/restore); form posts in `Web/Endpoints/DocumentEndpoints.cs`. API `/api/documents` (upload takes the raw body with `?kind=&fileName=&claude=`), `/api/settings/document-reading` (admin); scope area `documents`.

## Projects and time (L5, slice 1)

- Domain in `Domain/Projects/Projects.cs`. `Project` is one row per customer (`CustomerId` unique): the project is a customer record, usually a sub-customer billed with its parent (`ProjectService.CreateAsync` makes one inside an `IUnitOfWork` transaction, copying the parent's terms, tax code and price level), so invoices, receipts and credit memos need nothing new. Status, dates, revenue/cost/hours budgets. Audit `project`.
- `Worker` (audit `worker`): name (unique ignoring case), cost rate, optional bill rate, optional `Username` (one active worker per user; `WorkerService.ForCurrentUserAsync`) and vendor. Deactivated, never deleted.

## Fixed assets and loans (L5, slice 2)

- Domain in `Domain/Assets`. `FixedAsset` (audit `fixed_asset`): asset, accumulated depreciation and expense accounts (`Guid.Empty` in the details = "Accumulated Depreciation" / "Depreciation Expense", created by `AssetAccounts` on first use), cost, salvage, in-service date, `DepreciationMethod` (StraightLine, DecliningBalance with `DecliningPercent`, Macrs with `MacrsClass`, None), and `PriorDepreciation` through `PriorThrough` for assets bought before OpenBook. Creating one posts nothing (the purchase is a bill/expense/journal entry). Once depreciation is posted only name, number and description can change.
- `Depreciation.Schedule` gives one amount per calendar month from the in-service month, adding up exactly to `Base` (cost − salvage; MACRS ignores salvage) by cumulative rounding. MACRS: Pub 946 half-year tables (3–20 year), mid-month formula for 27.5/39-year; each tax year (calendar years) spread evenly over its months. `ScheduledThrough(asset, date)` = prior depreciation + schedule months ending after `PriorThrough` and on or before the date.
- `DepreciationRun` (`Source = assets.depreciation`, audit `depreciation_run`, owned `DepreciationRunLines`): `DepreciationService.RunAsync(through)` posts each active asset's due amount (scheduled − prior − posted) in one entry, Dr expense / Cr accumulated per asset. Only the latest posted run can be voided, and not once one of its assets is disposed.
- Disposal (`FixedAsset.DisposalSource = assets.disposal`, `SourceId` = asset): posts depreciation due through the date (kept as `DisposalDepreciation`), Dr accumulated, Dr proceeds (Bank or Other current asset), Cr asset cost, gain/loss to "Gain or Loss on Disposal of Assets" (other income). `UndoDisposalAsync` voids it.
- `Loan` (audit `loan`, owned `LoanPayments`): monthly, `Amortization.Payment` rounds up to the cent so the term repays it; optional proceeds entry (`Source = assets.loan`: Dr bank/asset, Cr the liability). Payments (`assets.loan_payment`, `SourceId` = loan) split interest = one month on the current balance, the rest principal; in date order; only the latest can be voided. Terms are locked once a payment exists. Interest defaults to "Interest Expense".
- Reports `fixed-assets` (as of), `depreciation-schedule` (year, by quarter), `loans`. Pages `/assets` (register, run depreciation, runs), `/assets/new`, `/assets/{id}`, `/assets/{id}/edit`, `/assets/runs/{id}`, `/loans`, `/loans/{id}` (accountant to change). Form posts in `Web/Endpoints/AssetEndpoints.cs`; API under `/api/assets` (`/depreciation`, `/loans`).

## Offline capture (L9, slice 4)

- Device side: `wwwroot/capture.html` + `capture.js`, a static page (no data in the HTML, so the service worker may cache it and serve it offline; it's in `SHELL` with `capture.js` and `/app.css`). Drafts (time, mileage, expense with optional photo, receipt photo, invoice or estimate) and the cached lists live in IndexedDB `openbook-capture`, sealed with an AES-GCM key generated non-extractable and kept in the same database. Encrypt before opening an IndexedDB transaction (a transaction closes if it awaits anything else). Each draft gets `crypto.randomUUID()`. Sync on load, on `online`, every minute and on "Send now"; 401 keeps drafts and asks to sign in; 410 wipes the database. The JS checks mirror the server's main rules; the server decides.
- Server side: `CaptureDevice` (per user, revoked never deleted; audit `capture_device`) and `CaptureDraft` (key = the device's id, so a resend returns the stored outcome; audit `capture_draft` naming the device). `CaptureService.SyncAsync(userId, deviceId, drafts)` enters each draft in its own DI scope through `TimeService`, `MileageService`, `BankingService` (+ `AttachmentService` for a photo), `ReceiptService`, `InvoiceService` or `EstimateService` (kinds `Invoice`/`Estimate`: customer, date, memo and item lines; a line without a rate is `AutoPrice`d, and the server numbers and taxes it, so an invoice posts on sync); a `DomainException` leaves it `NeedsAttention` with the message. Entered drafts drop their photo from the stored payload (`Compact`); `CaptureDrafts.Payload` is left out of the data export. A revoked device gets `capture.device_revoked` (410 from the API). A device records the sign-in session that registered it (`CaptureDevice.SessionId`; null through an API key), and revoking it ends that session unless it's the caller's own. The revoke form's "also sign out my other sessions" box, like the "Sign out all other sessions" button on `/account/password`, calls `AuthService.EndOtherSessionsAsync` (new security stamp, so every other cookie is refused on its next request) and re-issues the current browser's cookie. A signed-out device asks the anonymous `GET /capture/device-status/{id}` (`IsRevokedAsync`; unknown ids answer false) when it gets 401, and wipes itself if revoked. API keys aren't affected by ending sessions. `ListsAsync` gives what the forms need (workers, customers, services, active items, pay-from and expense accounts, vendors, this year's mileage rate), never balances or secrets.
- API `/api/capture` (`/devices`, `/lists`, `/sync`, `/drafts`, retry/dismiss); scope area `capture`. Page `/capture` (drafts needing attention: retry, dismiss; the user's devices: remove access); form posts are mapped in `Program.cs`.

A pledge can't be voided once paid on; `CancelRestAsync` writes off the unpaid part instead (`Pledge.CancelSource`, accrual only, Dr income / Cr receivable on its class; `UndoCancelAsync` voids it), after which no more payments are taken. Paid amounts are summed from posted gifts (`GiftService.Paid`). `RecurringGift` (audit `recurring_gift`, `RecurringGiftService`, page `/nonprofit/recurring`, API `/api/nonprofit/recurring-gifts`): a donor, amount, bank or holding account, optional income account, class and pledge, on the shared `Recurrence` schedule; `CreateDueAsync` records each occurrence through `GiftService.RecordAsync` (reference "Recurring"), saving each on its own and stopping a template at its first error; the hourly `RecurringPostingService` runs automatic ones.
- Letters: `DonorLetter` (Application/Forms) rendered by `IFormRenderer.Render(IReadOnlyList<DonorLetter>)` (a section per letter, pages numbered per letter). `GiftService.AcknowledgmentAsync` / `YearStatementAsync` / `YearStatementsAsync` (all donors, one PDF); wording: per-gift quid pro quo sentence or "No goods or services were provided…", in-kind note, and the 501(c)(3) sentence with the EIN from `GiftSettings` (one row, audit `gift_settings`). Emailing goes through `EmailService.SendMessageAsync`; an emailed acknowledgment marks the gift `AcknowledgedAt` (audit `Emailed`); statements are audited `Emailed` on the customer. `GiftReports`: `giving-by-donor`, `lapsed-donors` (year), `open-pledges` (as of).
- Pages `/nonprofit/gifts`, `/nonprofit/gifts/new` (`?pledge=`, `?donor=`), `/nonprofit/gifts/{id}` (letter PDF at `/nonprofit/gifts/{id}/letter`), `/nonprofit/pledges`, `/nonprofit/pledges/new`, `/nonprofit/pledges/{id}`, `/nonprofit/thanks` (unthanked gifts, statements by year: `/nonprofit/statements/{year}` and `/{year}/{donorId}` PDFs), `/nonprofit/settings` (accountant). Gifts, pledges, thanks and statements need the standard role to change; the rest of `/nonprofit` the accountant role. API `/api/nonprofit/gifts`, `/pledges`, `/statements/{year}/{donorId}`, `/settings`.
- Grants (slice 3, `Domain/Nonprofit/Grants.cs`, `GrantService`, audit `grant`): funder = customer; `ClassId` is the grant (null in `GrantCommand` creates a top-level class named after it with `FunctionalArea.Program`); spending = expense lines on that class or its subclasses within `StartsOn`–`EndsOn` (accrual), by account against owned `GrantBudgetLines` (`GrantPosition`). Unconditional: `AwardEntryId` (`Source = nonprofit.grant`: Dr "Grants Receivable" / Cr income, both on the class). Conditional: nothing at award; `RecognizeAsync(through)` posts min(spent, award) − recognized (`nonprofit.grant_recognition`). Receipts (`nonprofit.grant_receipt`: Dr bank / Cr receivable) are capped at the award; on a conditional grant the part beyond the receivable (`Grant.AdvancePartOf`) credits "Refundable Advances" (other current liability, `AdvanceAccountId`, created on first use) and recognitions debit that advance first (`AdvanceUsedBy`); each row keeps its `AdvancePart`. A receipt whose advance has been earned since, or a recognition the funder has paid since, can't be voided. Receipts and recognitions are owned rows with their entry, voided individually; `SourceId` is the grant for all three sources. Receivable = an existing "Grants Receivable" (other current asset or A/R), else a new other current asset; income defaults to "Grants". `grants` and `form-990-expenses` reports in `NonprofitReports` (Part IX from each expense account's Form 990 tax line, nearest parent's when unmapped, by functional area). Chart CSVs take a "Tax line" column (keys like `n.9.7`); the nonprofit template maps its accounts.
- Pages `/nonprofit/grants`, `/nonprofit/grants/new`, `/nonprofit/grants/{id}` (budget grid posts `account:{i}`/`amount:{i}`, receive, recognize, void rows with `VoidLine`, close/reopen/void); accountant role to change. API `/api/nonprofit/grants` (`/{id}/budget`, `/receipts`, `/recognize`, `/close`, `/void`).
- Pages `/nonprofit` (purposes with a release form per row, releases, classes and their areas) and `/nonprofit/releases/{id}`; a class's area on its segment page (posts `/segments/{id}/functional-area`); the account form shows the restricted box in the nonprofit edition (or when already set). Form posts in `Web/Endpoints/NonprofitEndpoints.cs`; `/nonprofit` needs the accountant role to change. API `/api/nonprofit` (`/purposes`, `/releases`, `/functional-classes`; scope area `nonprofit`) and `PUT /api/segments/{id}/functional-area`.

## Pickers

- Interactive forms choose customers, vendors, items, categories and accounts with `SearchSelect` (Components/Search): type any part of a name (every word must match the label, detail or keywords, ignoring case and accents; names starting with the text first), arrows and Enter to choose (`wwwroot/searchselect.js`), Esc or Tab to leave; leaving with an exact name typed chooses it. Build options with `PickerOptions.Customers/Vendors/Items/Accounts` (accounts grouped by class, searchable by number) and cache them per source list in editors. Bind with `@bind-Value` (Guid?) or `OnChange` for handlers written for a select's `ChangeEventArgs`; `EmptyText` adds a "none" choice. Plain `<select>` is still right for short fixed lists (kinds, classes, frequencies).
- Static (server-rendered) forms get the same picker by adding `data-search` to a `<select>`/`InputSelect` (`searchselect.js`): a search box goes in front and the hidden select still carries the value, so the form works without script. An empty-value option is the "none" choice, optgroups become headings, `data-keywords` on an option is searched too. It's re-added after every enhanced load; never use it on interactive pages (use `SearchSelect`) or on multi-selects.
